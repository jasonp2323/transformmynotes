# M17 · Multi-note & notebook-wide generation

> Size: XL · Depends on: M13, M15, M16, M6

## Goal

Generalise the input scope of every generation type introduced in M13–M16 from a single note
to an arbitrary set of notes — up to an entire notebook/collection. A user can tap "Generate
from notebook" on any collection visible in the M6 library, or hand-pick individual notes
across notebooks with a new note-set picker UI, then run any of the four material types
(flashcards, quiz, assignment, study guide / summary) against the combined bodies. Large
multi-note inputs that exceed the model's practical context window are handled transparently
by a chunked map-reduce synthesis pass inside the existing M13 async job. Every generated
artifact traces back to its source note(s) via the `sourceNoteIds` array (already a field on
the `STUDYSET#` item from M13). Cost controls bound Bedrock spend on big runs and require the
user to confirm before dispatch.

## In scope

- **Notebook-wide input**: a "Generate from notebook" entry point on M6's library screen that
  pre-selects all notes in the chosen collection and routes to the generation flow. Aggregates
  each note's Markdown body from S3 and stitches them into a single logical input.
- **Arbitrary note-set picker UI**: a dedicated modal / sheet that lets the user search and
  check individual notes across notebooks, then launch generation against the selection.
- **Large-context handling in the async job**: chunked map-reduce synthesis when the combined
  body exceeds the context threshold; cross-note deduplication of generated artifacts.
- **Multi-source provenance**: every generated artifact (card, quiz question, assignment
  prompt, summary section) records which source note(s) it came from; `sourceNoteIds` becomes
  a multi-element array in all four material types' output schemas.
- **Cost controls**: per-run note cap, token-budget estimate shown before the run starts, and
  a confirm-before-generate dialog. Tightly coupled to M13's per-user rate-limit infrastructure.
- Key builders, dynalite integration tests, and Playwright E2E coverage for all new access
  patterns.

## Out of scope

- Real-time streaming of partial map-reduce results to the UI (job is fire-and-poll, same as
  M13's existing async flow).
- Cross-user / shared-notebook generation (user's own notes only).
- Smart notebook-level deduplication of *already accepted* artifacts across prior runs (that
  is a future curation feature).
- Scheduling recurring generation runs (e.g. "regenerate weekly").
- Notebook-level rate-limit dashboards; M13's existing per-user limit is reused without a new
  UI surface.
- Generation from notes in formats other than Markdown (PDFs, images — those are M4's capture
  concern).

## Architecture & decisions

### Multi-element `sourceNoteIds` — already ready

M13 defined `STUDYSET#<ulid>` with `sourceNoteIds: string[]`. In M13–M16 the array always had
exactly one entry. M17 writes multiple entries; no DynamoDB schema migration is required.
Every downstream reader (M14 card accept, M15 quiz, M16 summary/assignment) that today reads
`sourceNoteIds[0]` must be updated to treat the full array as the canonical source reference.

### S3 body aggregation

The async job (in `infra/jobs.ts`) fetches each note's Markdown body from S3 using
`storageKeys.noteMarkdown(sub, noteId)` (from `packages/core/src/db/keys.ts`). Bodies are
fetched in parallel (Promise.all), trimmed, and separated by a `---` horizontal rule before
being handed to the generation pass.

### Context window / token budget estimation

The model identified by `BEDROCK_MODEL_ID` has a practical per-request token budget. M17
introduces a token estimator:

```typescript
// packages/core/src/study/tokenBudget.ts
export function estimateTokens(texts: string[]): number
// Approximates total input tokens: ~4 chars per token across the combined texts.
// Used for the pre-run estimate and for deciding whether map-reduce is needed.
```

**Threshold constants** (exported from `tokenBudget.ts`, configurable via SST secret
`MULTI_NOTE_CONTEXT_LIMIT` — defaults to `60_000` input tokens):

```
DIRECT_LIMIT   = MULTI_NOTE_CONTEXT_LIMIT   (fit-in-one-pass threshold)
HARD_CAP       = 200_000 tokens             (absolute reject; user must narrow selection)
```

If `estimatedTokens <= DIRECT_LIMIT`: the aggregated body is fed directly to the generation
call (same as single-note flow, `maxTokens` per M13's existing config).

If `estimatedTokens > DIRECT_LIMIT && <= HARD_CAP`: map-reduce mode is activated (see below).

If `estimatedTokens > HARD_CAP`: the job rejects with `status: "too_large"` before any
Bedrock call; the route surfaces this to the UI as a 422.

### Map-reduce synthesis

Implemented inside the M13 async job function as a separate code path triggered by the
`mapReduce: true` flag on the `STUDYSET#` item.

#### Map phase

1. Split the per-note bodies into chunks of at most `DIRECT_LIMIT / 2` estimated tokens each
   (a note is never split mid-paragraph — chunk boundaries fall on blank lines). Each chunk
   retains its source note's `noteId`.
2. For each chunk, call `generate()` with a *map-phase system prompt* instructing the model to
   extract raw candidates from the chunk only — no synthesis, no deduplication yet.
   - Flashcards: extract up to 15 candidates per chunk (`maxTokens: 2048`).
   - Quiz questions: extract up to 10 candidates per chunk.
   - Summary / study guide: extract key facts and headings per chunk as a bullet list.
   - Assignment: extract testable objectives per chunk.
3. Map calls run sequentially (not in parallel) to respect `withBedrockRetry` and avoid
   Bedrock throttling. Each call is wrapped with `withBedrockRetry` from `retry.ts`.
4. Each candidate carries `sourceNoteIds: string[]` — the one (or more) note IDs that
   contributed to the chunk.

#### Reduce phase

After all map calls succeed, the partial results are concatenated and passed to a single
*reduce-phase call* with a synthesis prompt:

> "You are given a list of draft [material type] candidates extracted from multiple study
> notes. Synthesise them into a final, high-quality set. Remove duplicates (same concept
> expressed differently counts as a duplicate). Merge complementary candidates where sensible.
> Return only the final set via the tool call."

- Flashcards: reduce to at most 40 cards (`maxTokens: 4096`).
- Quiz: reduce to at most 30 questions.
- Summary: reduce to a coherent Markdown document (`maxTokens: 8192`).
- Assignment: reduce to at most 20 objectives.

The reduce call's output schema is the same tool-use schema as each material type's existing
single-note generation schema, extended to include `sourceNoteIds` as a required array field
per artifact.

#### Cross-note deduplication heuristic

Before the reduce call, a lightweight dedup pre-filter runs on the raw map-phase candidates:

1. Normalise each candidate's `front` (or question stem): lowercase, strip punctuation,
   collapse whitespace.
2. Compute pairwise Jaccard similarity on word-trigrams between all normalised candidates.
3. If similarity ≥ 0.75, keep only the candidate with the longer/richer `back` (or answer
   context) and merge their `sourceNoteIds` arrays (union).

This runs in-process (no extra Bedrock call). Implemented as a pure function
`deduplicateCandidates<T extends { front?: string; question?: string; sourceNoteIds: string[] }>(candidates: T[]): T[]`
in `packages/core/src/study/dedup.ts`, fully unit-tested.

### `STUDYSET#` item additions

Two new attributes on the M13 `STUDYSET#` item (additive, backward-compatible):

```
mapReduce        boolean?   true when the map-reduce code path was used
chunkCount       number?    number of map-phase calls executed
inputNoteCount   number?    length of sourceNoteIds at dispatch time
```

No new GSI. No new table.

### Note-set picker data model

The picker does not introduce new DynamoDB items. It queries the existing M6
`GET /api/notes` endpoint (list-recent + search) to populate the selectable note list.
Selected note IDs are held in ephemeral client state and passed to the generation route as
`sourceNoteIds: string[]`.

### Updated generation route

`POST /api/study/generate` (M13) gains three new request fields:

```typescript
{
  type:           "flashcards" | "quiz" | "assignment" | "summary";
  sourceNoteIds:  string[];    // 1–N note IDs, all owned by the caller
  notebookId?:    string;      // optional — if provided, server resolves all note IDs in the notebook
  dryRun?:        boolean;     // if true, return { estimatedTokens, estimatedCost } without dispatching
}
```

`noteId` (single-note field from M13–M16) is deprecated but still accepted; if present and
`sourceNoteIds` is absent, the server normalises it to `sourceNoteIds: [noteId]`.

**`dryRun: true`** is the cost-estimate mode: the route fetches all note bodies (or resolves
the notebook's note list), runs `estimateTokens`, and returns an estimate without calling
Bedrock or writing a `STUDYSET#` item. The UI uses this to show the confirm dialog.

### Infra changes

- `infra/secrets.ts`: add `sst.Secret("MULTI_NOTE_CONTEXT_LIMIT")` with an empty string
  default that the job interprets as `60_000`. Seed the real value in both Console
  environments.
- `infra/db.ts`: no new tables or GSIs.
- `infra/jobs.ts`: the existing M13 async job Lambda gains additional IAM permissions for
  `s3:GetObject` on the notes prefix for all source notes (already scoped to the notes bucket;
  no new policy needed if the existing role already covers `markdown/users/*`). Confirm and
  add if absent.
- No new `sst.Secret` beyond `MULTI_NOTE_CONTEXT_LIMIT`.

### Key builder additions (`packages/core/src/db/keys.ts`)

```typescript
// Multi-note batch fetch query (base table, same PK partition as user's notes)
// Used by the job to fetch note metadata for all sourceNoteIds in one BatchGetItem.
noteMultiGetKeys(userSub: string, noteIds: string[]): BatchGetKey[]
  // Returns [{ pk: "USER#<sub>", sk: "NOTE#<noteId>" }, ...] for BatchGetItem
```

### GSI additions

None. All new access patterns use existing indexes or direct PK/SK lookups.

### 3. (L) Large-context handling: chunking + map-reduce synthesis in the async job + cross-note dedup

**What to build:**

- `packages/core/src/study/tokenBudget.ts`: `estimateTokens(texts: string[]): number`;
  exports `DEFAULT_CONTEXT_LIMIT = 60_000` and `HARD_CAP_TOKENS = 200_000`. Reads
  `MULTI_NOTE_CONTEXT_LIMIT` from env (via `process.env.SST_RESOURCE_MULTI_NOTE_CONTEXT_LIMIT_value`)
  to override the default. Pure function; unit-tested with edge cases (empty array, single
  long text, 100 short texts).
- `packages/core/src/study/chunk.ts`: `chunkNotes(notes: Array<{noteId: string; body: string}>, limitTokens: number): Array<{noteIds: string[]; body: string}>` — splits the note list into chunks that each fit within `limitTokens`, never splitting mid-paragraph. Pure function; unit-tested with a fixture of 5 notes where notes 2 and 3 must land in the same chunk and note 4 alone exceeds the limit (triggers a single-note chunk with a warning).
- `packages/core/src/study/dedup.ts`: `deduplicateCandidates<T>(candidates: T[], getKey: (t: T) => string): T[]` — Jaccard trigram dedup with merge of `sourceNoteIds`. Pure function; unit-tested: 3 candidates where two are near-duplicates → returns 2 with merged `sourceNoteIds`; 3 entirely distinct candidates → returns 3 unchanged.
- Update the M13 async job in `infra/jobs.ts` / `packages/core/src/study/generate.ts` to:
  1. After body aggregation (Phase 1), call `estimateTokens`.
  2. If `estimatedTokens <= DIRECT_LIMIT`: run existing single-pass generation.
  3. If `estimatedTokens > DIRECT_LIMIT && <= HARD_CAP`: run map-reduce:
     - Call `chunkNotes` to get chunks.
     - For each chunk sequentially: call `generate()` with the map-phase system prompt for
       the relevant material type; collect `RawCandidate[]` with `sourceNoteIds`.
     - Call `deduplicateCandidates` on the combined map-phase output.
     - Call `generate()` once with the reduce-phase system prompt and the deduped candidates.
     - Write the final output to the `STUDYSET#` item with `mapReduce: true`,
       `chunkCount: N`, `inputNoteCount: M`.
  4. If `estimatedTokens > HARD_CAP`: set `STUDYSET#` status to `"too_large"` without
     Bedrock calls.
- Add `dryRun` support to `POST /api/study/generate`: if `dryRun: true`, return
  `{ estimatedTokens, estimatedCostUsd, mapReduceNeeded: boolean }` after fetching bodies
  (no Bedrock, no `STUDYSET#` write). Cost estimate: `estimatedTokens * 0.000003` USD
  (approximate; labelled "estimated" in the UI).
- `infra/secrets.ts`: add `sst.Secret("MULTI_NOTE_CONTEXT_LIMIT")`.

**Acceptance criteria:**

- `estimateTokens` unit tests: 400-char text → 100 tokens; empty array → 0.
- `chunkNotes` unit test: a 5-note fixture with known token counts produces the correct chunk
  groupings; a note whose body alone exceeds the limit gets its own chunk with a logged warning.
- `deduplicateCandidates` unit tests: near-duplicate pair (Jaccard ≥ 0.75) merges into one
  item with union `sourceNoteIds`; distinct pair returns both unchanged; empty input returns
  empty array.
- Integration test (`packages/core/test/mapReduce.integration.test.ts`): seed 3 notes in

  3-item reduce result; assert the `STUDYSET#` item written has `mapReduce: true`,
  `chunkCount: N`, and `sourceNoteIds` covering all 3 notes.
- `dryRun: true` returns a token estimate without writing any DynamoDB item; calling the
  endpoint twice produces no side effects.
- `estimatedTokens > HARD_CAP` sets `STUDYSET#` status to `"too_large"` and no Bedrock call
  is made.
- `npm run test:unit` and `npm run test:integration` pass.

  - Estimated token count.
  - Estimated cost (USD, one decimal place, e.g. "~$0.02").

## Risks / open questions

- **Map-reduce quality degradation.** Breaking a note set into chunks and running separate
  extraction passes can cause thematically important concepts that span chunk boundaries to be
  lost or weakened. Mitigation: keep chunk overlap of 200 tokens (last paragraph of chunk N
  is also prepended to chunk N+1) to preserve inter-chunk context. Document this as a known
  quality trade-off; consider a future single-pass summarise-then-generate pre-step.
- **Bedrock throttling on sequential map calls.** With 20 chunks, sequential map calls at
  ~2–5 s each can make a job run for 40–100 s, hitting the Lambda timeout. Mitigation: keep
  Lambda timeout at 5 minutes for the generation job (already set in M13); monitor P95
  durations on `pr-<N>` before production. If chunk counts routinely exceed ~20, add a
  configurable `MAX_CHUNKS` guard that rejects the run before any Bedrock calls.
- **`sourceNoteIds` on pre-M17 artifacts.** `STUDYSET#` items written before M17 have
  `sourceNoteIds: [noteId]` (single-element). The provenance UI must treat a missing or
  single-element array gracefully — hide the provenance subtitle for single-source artifacts
  rather than rendering "From: Note A" on every card. Add a `isSingleSource` computed flag to
  the UI component.
- **Dedup heuristic false positives.** The Jaccard trigram similarity at 0.75 threshold may
  merge two conceptually distinct but lexically similar candidates (e.g. two vocabulary cards
  with the same root word). Accepted for M17. A future refinement could use semantic
  embedding similarity (Bedrock Titan embeddings) instead.
- **Token estimator accuracy.** The 4-chars-per-token approximation underestimates for
  CJK/Arabic scripts. For the current user base (pt-BR / EN notes) this is acceptable.
  Document the approximation as a known limitation; re-evaluate if the user base diversifies.
- **Cost estimate reliability.** Bedrock pricing changes; the hard-coded `$0.000003/token`
  constant will drift. Surface estimates as "approximate" in the UI copy. Consider sourcing
  the rate from a new `sst.Secret("BEDROCK_INPUT_TOKEN_COST_USD")` to allow updates without a
  code deploy.
- **Large notebooks in the note-cap boundary.** A notebook with 80 notes will be truncated to
  50 by the cap. The UI should show "Generating from 50 of 80 notes (limit reached)" in the
  confirm dialog rather than silently dropping notes. Implement the truncation server-side
  (newest 50 by ULID) and surface the truncation count to the client in the `dryRun` response.
