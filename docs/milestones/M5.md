# M5 · Review & Notion-like Editor

> Size: XL · Depends on: M4 (Capture → Transcribe, S3 bucket, TranscriptionJob, Bedrock OCR)

## Goal

Complete the first-use journey: after M4 returns a Markdown transcription, the user reviews
it on the `TranscriptionStacked` / `TranscriptionSegmented` screen (Original ↔ Clean side
by side or toggled), edits in a Notion-like block editor (TipTap/ProseMirror) as the primary
surface with a raw-Markdown secondary toggle, then saves — writing the Markdown body to S3
and the note metadata to DynamoDB, arriving at the `StateSuccess` screen.

The editor is the product's differentiated experience: headings, tables, bullet and numbered
lists, bold/italic, and the gold `==highlight==` mark all round-trip faithfully through the
Markdown<>editor serialization layer. Low-confidence words (those the OCR flagged as `[?]`)
are underlined in amber and tappable. Tags can be added before save. The SUCCESS state
confirms how many highlights were captured and opens the permanent `NoteView`.

This milestone is XL and should be broken into phases by the implementing lead, committing +
pushing after each phase. Suggested phases:
- **Phase 1**: Notes DynamoDB table + key builders + integration tests + storageKeys (no UI).
- **Phase 2**: Markdown<>TipTap round-trip serialization layer + unit tests (no UI).
- **Phase 3**: Review-before-save screen (TranscriptionStacked / Segmented ports + block editor).
- **Phase 4**: Save action + SUCCESS state + NoteView route.

## Architecture & decisions

### DynamoDB Notes table

Defined in `infra/db.ts`. This is the permanent record; the `TranscriptionJob` ephemeral item
(M4, `JOB#` SK prefix) lives in the same table under the same PK.

```
Table: Notes  (single-table design, PK + SK)

Item shape:
  PK:              USER#<cognitoSub>
  SK:              NOTE#<ulid>            ← ULID = time-ordered, same ulid as the job/s3Key
  GSI1PK:          USER#<cognitoSub>      ← user-recency GSI (list all notes for a user)
  GSI1SK:          NOTE#<ulid>            ← ULID lexicographic = time-ordered desc
  GSI2PK:          TAG#<tag>              ← tag GSI (find all notes with a given tag)
  GSI2SK:          USER#<cognitoSub>#NOTE#<ulid>
  title:           string
  groupId?:        string                 ← future group/course feature
  tags:            string[]
  status:          "original" | "clean"
  words:           number
  highlights:      number                 ← count of ==marks== in the saved Markdown
  langPair:        string                 ← e.g. "pt-BR → en"
  ocrConfidence:   number                 ← 0–100
  bodyS3Key:       string                 ← markdown/users/<sub>/<ulid>.md
  originalImageS3Key: string             ← images/users/<sub>/<ulid>.jpg
  createdAt:       ISO-8601
  updatedAt:       ISO-8601
```

**GSI definitions** (add to `infra/db.ts`):

```
GSI1: name = "UserNotesByTime"
  hash key:  GSI1PK   (USER#<sub>)
  range key: GSI1SK   (NOTE#<ulid>)     ← descending scan = newest first
  projection: ALL

GSI2: name = "NotesByTag"
  hash key:  GSI2PK   (TAG#<tag>)
  range key: GSI2SK   (USER#<sub>#NOTE#<ulid>)
  projection: KEYS_ONLY                 ← tag queries return ids; caller fetches items
```

Document both GSIs in `CLAUDE.md` under "Persistence" when M5 lands.

### Markdown ↔ TipTap serialization (`packages/core/src/editor/`)

Files:
- `serialize.ts` — `markdownToDoc` + `docToMarkdown`.
- `extensions.ts` — re-exports the TipTap extension set used by both the editor component
  and the serializer (so they share one extension registry).
- `highlight-mark.ts` — custom TipTap `Mark` for `==text==` / `highlight`.
- `low-confidence-node.ts` — custom TipTap `Node` for `[?]` replacements.

**`markdownToDoc` strategy**: parse Markdown line-by-line using the same logic as
`renderMarkdown` in `ds-helpers.jsx`, but produce TipTap `JSONContent` nodes instead of
HTML strings. Do NOT use `remark`/`unified` — the Markdown dialect is narrow and a hand-rolled
parser keeps the bundle small and testable.

Supported constructs (must all round-trip):
- `##` / `###` / `####` headings → `heading` node (level 2/3/4)
- `- ` / `* ` bullet items → `bulletList` + `listItem`
- `1. ` numbered items → `orderedList` + `listItem`
- `| col | col |` tables → `table` + `tableRow` + `tableHeader` / `tableCell`
- `> ` blockquote → `blockquote`
- `---` → `horizontalRule`
- `**text**` → `bold` mark
- `*text*` → `italic` mark
- `` `text` `` → `code` mark
- `==text==` → `highlight` mark (custom)
- plain paragraph text → `paragraph`

**`docToMarkdown` strategy**: recursive TipTap `JSONContent` tree walker. Each node type maps
to a Markdown string. Marks are applied innermost-first (`==**bold highlight**==` →
`==**bold highlight**==`). Tables emit pipe-delimited rows with a separator row after the
header. No trailing newlines inside list items.

**Normalisation contract**: `docToMarkdown(markdownToDoc(md))` must equal `md` after:
- Stripping leading/trailing whitespace per line
- Collapsing multiple blank lines to one
- Ensuring a single trailing newline

This contract is asserted in unit tests for the `NOTE_MD` fixture and 10+ edge cases.

### Save route handler (`POST /api/notes/save`)

Location: `packages/application/app/api/notes/save/route.ts`

Auth: `proxy.ts` middleware.

Request body:
```ts
{
  jobId:    string;    // ULID — must exist as a TranscriptionJob for this user
  title:    string;    // user-entered or auto-derived from first heading
  markdown: string;    // final edited Markdown from docToMarkdown(editor.getJSON())
  tags:     string[];
}
```

Logic:
1. Validate inputs; look up `TranscriptionJob` by `sub` + `jobId`; reject if not found.
2. Derive metadata from the Markdown via `postprocessMarkdown`:
   - `wordCount`, `langPair`, `ocrConfidence`
   - `highlights` = count of `==...==` spans in the Markdown
3. Write Markdown body to S3: `PutObjectCommand` to `markdown/users/<sub>/<ulid>.md`
   (overwrite if exists — idempotent re-save).
4. `PutItem` the Note record to DynamoDB (all fields including GSI keys).
   - For each tag in `tags`, the GSI2 keys (`TAG#<tag>`, `USER#<sub>#NOTE#<ulid>`) must be
     set on the item. A single DynamoDB item can have at most one GSI2PK/SK, so tags are
     modelled differently: each unique tag gets its own DynamoDB item with
     `PK = TAG#<tag>`, `SK = USER#<sub>#NOTE#<ulid>`, `noteId = <ulid>`. These
     tag-index items are written in a `TransactWriteItems` call alongside the main Note item
     (one transaction, up to 10 tags per note). The main Note item's `tags` attribute is the
     plain `string[]` used for display; the tag-index items are used only for GSI2 queries.
5. Update `TranscriptionJob` `status → "done"`.
6. Return `{ noteId, title, wordCount, highlights, langPair, ocrConfidence }`.

Idempotent: re-posting the same `jobId` overwrites the S3 body and DynamoDB item safely.

### PATCH `/api/notes/[noteId]` (NoteView edit save)

Accepts `{ markdown, tags, title }`. Same serialization + DynamoDB + S3 logic as `save`, but
updates an existing Note item rather than creating one. Updates `updatedAt`. Deletes stale
tag-index items (items for removed tags) and creates new ones (for added tags) in a
`TransactWriteItems` call.

## Risks / open questions

- **TipTap table + mobile keyboard**: TipTap's `Table` extension can conflict with mobile
  virtual keyboard repositioning (the editor jumps when the keyboard appears). Mitigate with
  `touch-action: pan-y` on the editor wrapper and `scrollIntoView` on focus; test on real
  iOS Safari before marking phase 3 done.
- **`TransactWriteItems` tag limit**: DynamoDB transactions cap at 100 items per call. With
  one Note item + up to N tag-index items, N ≤ 99. Enforce a max of 20 tags per note in the
  route handler and surface a validation error to the UI.
- **`docToMarkdown` and ProseMirror mark ordering**: when multiple marks overlap (e.g.
  bold + highlight), ProseMirror's schema must declare precedence. If `highlight` and `bold`
  both apply, the serialized output must be deterministic (`==**text**==` not `**==text==**`).
  Define mark priority in `extensions.ts` and assert it in a unit test.
- **Stale tag-index items on PATCH**: if a note is re-saved after deleting all tags, the
  old tag-index items must be deleted. The PATCH handler derives the delta, but a race
  condition (two simultaneous PATCHes) could leave orphan items. Mitigate with a
  `ConditionExpression` on the main Note item's `updatedAt` (optimistic lock) and surface a
  409 Conflict to the UI.
- **`cognito-local` in the E2E harness** (from CLAUDE.md): the token-mint recipe requires
  `ALLOW_USER_PASSWORD_AUTH` on the app client; confirm this is set in the local harness
  setup for the M5 E2E test.
- **S3 presigned URL TTL on slow connections**: the presigned PUT URL issued in M4 has a
  5-minute TTL. If the user reviews for >5 min before saving, the background S3 write in the
  save route must re-upload the markdown (not use the original presigned URL). The save route
  uses server-side `PutObject` (not the presigned URL), so this is not a risk — but confirm
  the save route always writes directly via SDK, never via the client's presigned URL.
