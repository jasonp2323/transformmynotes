# M27 · Manual & explicit flashcard creation

> Size: L · Depends on: M8 (SM-2 review deck), M14 (AI flashcards, `origin` field)

## Goal

Make flashcard **creation** obvious and add user-authored (non-AI) cards.

Today the only discoverable "make cards" affordance in a note is the **AI flashcards**
button. The highlight→card path is hidden behind a vague **"Add to review deck"** button
that silently no-ops when the note has no `==highlights==` (it just shows a neutral toast),
so users reasonably conclude card creation "doesn't work". And there is **no way to write
your own card** at all — `origin` only supports `'highlight' | 'ai'`.

M27 delivers three things:

1. **Explicit highlight generation** — relabel the highlight button to say what it does
   ("Generate from highlights") and make its dependency on `==highlights==` visible up front,
   not a surprise after tapping.
2. **Manual card authoring** — a "type your own front/back" flow with a new
   `origin: "manual"`, reachable from **both** a note (NoteView) and a dedicated area on the
   **Review** tab.
3. **Standalone cards** — a manual card may attach to a note (`sourceNoteId`) **or** stand
   alone (deck-only, no note). The Review deck groups standalone cards under an "Other / no
   note" section.

All created cards remain ordinary `CARD#` items: same SM-2 fields, same `ByDue` GSI5 query,
same flip-and-grade session UI from M8.

## In scope

- Extend the `CARD#` item `origin` union to `'highlight' | 'ai' | 'manual'`, and make
  `sourceNoteId` **optional** (manual standalone cards have none). Backward-compatible — no
  migration; absent `origin` still reads as `"highlight"`.
- `POST /api/cards` — create a manual card from `{ front, back, sourceNoteId? }`, written with
  SM-2 defaults (due immediately) and `origin: "manual"`.
- `DELETE /api/cards/[cardId]` — delete a card the caller owns (so users can remove
  mistyped manual cards).
- Manual create UI: a shared front/back form, reachable from (a) NoteView (pre-attached to
  that note) and (b) a "+ New card" entry on the Review overview (with an optional note
  picker).
- Explicit highlight-generation button on NoteView: relabel "Add to review deck" →
  "Generate from highlights", with an up-front empty/guidance state when the note has no
  highlights (so the no-op is explained, not silent).
- Review deck overview: render standalone (`sourceNoteId` absent) cards under an
  "Other / no note" group, and pass `origin` through the `GET /api/cards/due` response so the
  deck can distinguish card sources.
- Auto-prune guard: `origin: "manual"` cards are **never** auto-deleted on highlight removal
  (same protection AI cards already have).
- Unit tests for new pure logic (key-builder / card-item construction), a dynalite
  integration test for the create + due round-trip, and a browser UI test for the create
  flow.

## Out of scope

- Editing an already-created card's `front`/`back` from the deck (creation + delete only this
  milestone; inline edit of existing cards is a follow-up).
- AI involvement of any kind in the manual flow (no suggestions, no autocomplete).
- Bulk/CSV import of cards, or importing from external decks (Anki, Quizlet).
- A provenance **badge + filter** on the deck (the abandoned M14.3 scope) — M27 only adds the
  minimum deck handling needed for standalone cards; a badge/filter is a separate future
  decision.
- Changing the highlight extraction algorithm or the SM-2 / FSRS scheduling.
- Rich media on cards (images, audio) — front/back are plain text only.

## Architecture & decisions

### CARD item shape extensions

Building on M14's `origin` field:

```
origin        'highlight' | 'ai' | 'manual'   (default: 'highlight' when absent)
sourceNoteId  string | undefined              now OPTIONAL — absent on standalone manual cards
```

`sourceNoteId` becomes optional **only** for the item type; existing highlight/AI cards always
carry it, so no migration is needed. The `ByDue` GSI5 (`gsi5pk = USER#<sub>`,
`gsi5sk = DUE#<ISO dueAt>`) is keyed by user, not note, so standalone cards appear in the due
query exactly like any other card — **no new index**.

### Key builder / item construction

`buildCardItem` (`packages/core/src/db/cards.ts`) already constructs the item and conditionally
writes `origin`. Extend it so:

- `origin: 'manual'` is accepted.
- `sourceNoteId` is optional: when absent, the attribute is omitted from the item (never
  written as an empty string — DynamoDB string attributes must be non-empty, and the deck
  grouping treats "attribute absent" as standalone).

No inline `pk`/`sk`/`gsi5*` strings — all keys stay in `keys.ts` (`cardKeys`). Manual cards
reuse `cardItemKey` and `cardsByDueQuery` unchanged.

### Create route — `POST /api/cards`

```
POST /api/cards
Body: { front: string; back: string; sourceNoteId?: string }
Response (201): { cardId: string }
```

1. Auth via `proxy.ts` (JWT). 401 without a token.
2. `zod`-validate: `front` non-empty ≤ 300 chars, `back` non-empty ≤ 600 chars (mirrors the
   AI card limits), `sourceNoteId` optional ULID.
3. If `sourceNoteId` is present, read the Note item and assert `PK === USER#<sub>` (403 if not
   owned, 404 if missing). If absent, the card is standalone.
4. Generate a ULID `cardId`; write a `CARD#<cardId>` item via `buildCardItem` with:
   `front`, `back`, optional `sourceNoteId`, `origin: 'manual'`, SM-2 defaults
   (`ease: 2.5`, `interval: 0`, `dueAt: now`, `createdAt`, `updatedAt`), and the GSI5
   `DUE#<now ISO>` keys (due immediately, like seeded highlight cards).
5. Return `{ cardId }` with 201.

### Delete route — `DELETE /api/cards/[cardId]`

```
DELETE /api/cards/[cardId]
Response (200): { deleted: true }
```

1. Auth (401 without token).
2. `getCard(sub, cardId)`; 404 if absent. Ownership is implicit in the PK (`USER#<sub>`), so a
   card owned by another user is simply not found for this caller → 404.
3. `DeleteItem` on the `CARD#<cardId>` key. Returns `{ deleted: true }`.

(Delete is origin-agnostic — a user can delete any of their own cards — but the UI surfaces it
on manual cards only this milestone.)

### Auto-prune guard

`syncCardsForNote` / the highlight diff logic (`cards.ts`, the `if (card.origin === 'ai')`
skip around line 202) must also skip `origin: 'manual'`. Simplest correct form: only consider a
card for highlight-orphan pruning when `origin === 'highlight'` (or absent). Anything else —
`'ai'` or `'manual'` — is never auto-deleted.

### Due route — `origin` passthrough + optional note

`GET /api/cards/due` currently maps `{ cardId, sourceNoteId, front, back, … }` and assumes
`sourceNoteId` is always a string. Update it to:

- include `origin` (defaulting absent → `'highlight'`) in the mapped response, and
- pass `sourceNoteId` through as optionally-absent (do not coerce to `''`).

This is additive — no existing field is removed.

### Deck overview — standalone group

`ReviewDeck`'s `groupByNote` groups strictly by `sourceNoteId` and assumes it is present. Update
the grouping so cards with no `sourceNoteId` collect into a single synthetic "Other / no note"
group (stable key, e.g. `__standalone__`) rendered after the note groups. Starting a session
from that group reviews the standalone cards. Note-attached manual cards continue to fall into
their note's existing group, indistinguishable from highlight/AI cards in the session itself.

### UI — manual create form

A shared, presentational `CardForm` (front `<textarea>` + back `<textarea>` + Save/Cancel,
Save disabled until both non-empty) used by both entry points:

- **NoteView** — add a "+ Add card" entry in the action bar (near the existing
  "Generate from highlights" / "AI flashcards" buttons). Opens the form pre-bound to the
  current `noteId`; on save → `POST /api/cards` with that `sourceNoteId` → success toast.
- **Review tab** — add a "+ New card" entry on the overview. Opens the form with an **optional
  note picker** (search/select an existing note, or "No note" for standalone) → `POST /api/cards`
  → success toast + refresh the overview so the new card's group appears.

Form factor (modal vs. full screen) is the implementer's call per the DS conventions; on a
375 px viewport the two textareas must have comfortable tap targets (see the M14 mobile note).

### Explicit highlight button

On NoteView, rename the **"Add to review deck"** button to **"Generate from highlights"** (or
similarly explicit copy) and make the highlight dependency visible *before* the tap:

- When the note body contains no `==highlights==`, the button surfaces guidance up front —
  e.g. helper text / an inline hint ("Highlight text in your note, then generate cards from
  it"), rather than only reacting with a neutral toast after the request returns.
- When highlights exist, behaviour is unchanged (`POST /api/notes/[noteId]/cards/refresh`,
  `origin: 'highlight'`).

No backend change — this is copy + an empty-state affordance driven off the note's current
highlight presence.

### Infra / secrets

None. No new table, GSI, secret, or IAM action (`PutItem`/`DeleteItem`/`Query` on the Notes
table are already permitted). No Bedrock — manual cards never call a model.

## Milestone acceptance criteria (DoD)

- CI green: lint, typecheck, `test:unit`, `test:integration`.
- Deployed to `pr-<N>` without errors; no schema/GSI change (Notes table `ByDue` GSI5 handles
  manual cards unchanged).
- `POST /api/cards` creates a `CARD#` item with `origin:'manual'`, due immediately, optionally
  attached to an owned note; `DELETE /api/cards/[cardId]` removes an owned card.
- A user can create a card by typing front/back from **both** a note and the Review tab; a
  standalone card (no note) is reviewable from the deck's "Other / no note" group.
- The highlight-generation button reads "Generate from highlights" and explains the highlight
  requirement up front; it still creates `origin:'highlight'` cards when highlights exist.
- Manual cards flow through the existing M8 flip-and-grade session and grade route with no
  special-casing; auto-prune never deletes a manual card.
- All card writes use `keys.ts` builders (no inline keys); new pure logic has unit tests; the
  new access pattern has a dynalite integration test; the create + deck flows have browser UI
  tests.
- No new `sst.Secret`, table, GSI, or IAM action.

## Risks / open questions

- **Empty-string `sourceNoteId`.** DynamoDB rejects empty string attributes and the deck
  grouping keys on attribute presence — the create path must **omit** `sourceNoteId` entirely
  for standalone cards, never write `''`. Covered by a unit test on `buildCardItem`.
- **Deck grouping assumes a note.** `groupByNote` currently assumes `sourceNoteId` is always
  present; the standalone group must be added carefully so existing note grouping and the
  note-title lookup are untouched. Unit-test the mixed fixture.
- **Note picker scale.** The Review-tab "+ New card" note picker needs the user's note list;
  for users with many notes it should search/paginate rather than load all. For M27 a simple
  searchable list over the existing notes query is acceptable; revisit if note counts grow.
- **Delete is destructive + irreversible.** `DELETE /api/cards/[cardId]` hard-deletes; the UI
  must confirm before deleting (no undo this milestone).
- **Highlight empty-state detection.** Showing the up-front hint requires knowing whether the
  note has `==highlights==`; derive it from the already-loaded note body on the client rather
  than adding a round-trip.

## Manual test plan

Test on the deployed `pr-<N>` stage:

1. **Explicit highlight button — no highlights.** Open a note with no `==highlights==`. Expect
   the action bar shows "Generate from highlights" and an up-front hint explaining you must
   highlight text first — *before* tapping.
2. **Explicit highlight button — with highlights.** Add `==highlights==`, save, tap
   "Generate from highlights". Expect highlight cards created and a success toast; they appear
   in the Review deck under that note.
3. **Create a card from a note.** In NoteView tap "+ Add card", type a front + back, save.
   Expect a success toast and the card appears in the deck grouped under that note.
4. **Create a standalone card from the Review tab.** On the Review overview tap "+ New card",
   leave the note as "No note", type front/back, save. Expect it appears under "Other / no
   note" and is reviewable in a session.
5. **Create a note-attached card from the Review tab.** "+ New card", pick an existing note,
   save. Expect it groups under that note.
6. **Review + grade a manual card.** Start a session including a manual card; flip and grade.
   Expect identical behaviour to highlight/AI cards; after grading "Good"/"Easy" it leaves the
   due list.
7. **Manual cards survive highlight edits.** Edit a note that has both highlight and manual
   cards; remove a `==highlight==` and save. Expect the orphaned highlight card is pruned but
   the manual card remains.
8. **Delete a card.** From the deck, delete a manual card (confirm the prompt). Expect it
   disappears from the deck and does not return.
9. **Validation.** Try to save with an empty front or back. Expect Save disabled; very long
   text is rejected/limited per the 300/600-char limits.
