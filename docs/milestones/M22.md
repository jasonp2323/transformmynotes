# M22 · Offline support (PWA app shell → offline-first → static export)

> Size: XL · Depends on: M10 (launch), M12 (Android Capacitor shell)

## Goal

Make TransformMyNotes usable on flaky or absent connectivity, delivered **incrementally** so value lands early and the heavy architectural decision is deferred behind an explicit gate. Today the app is **server-rendered Next.js (SSR) on Lambda** loaded over the network — both in the browser and inside the Capacitor Android shell (which is a thin WebView onto `app.transformmynotes.com` via `server.url`, with **no offline capability**). This milestone adds, in order:

1. a **PWA service-worker app shell** + branded offline page — instant launches and a graceful offline experience, with **no change to the SSR architecture** (benefits the website *and* the Android shell automatically);
2. an **offline read cache** so previously-viewed notes and the library render without a connection;
3. **offline mutations + sync** so notes can be created/edited offline and reconciled on reconnect;
4. a **decision gate** on the full **static export / SPA decouple + Capacitor static bundle** — the only path to launching the app with *zero* network — which is an architecture fork that may spin out into its own milestone.

The guiding principle: **earn offline capability without throwing away the "every web deploy is instantly live in the app" benefit** of the current `server.url` design. Aggressive caching must be versioned and update-prompted so users are never stuck on stale UI.

## In scope

- A **service worker** (Workbox, via `next-pwa` or a hand-rolled SW) that precaches the app shell + static assets and provides a runtime caching strategy, registered in `packages/application`.
- A **web app manifest** (`manifest.webmanifest`) and a **branded offline fallback page**; wiring the Capacitor shell's `www/offline.html` network-error fallback so the Android app shows brand UI instead of the raw WebView error.
- A **service-worker update UX** ("a new version is available — reload") so the SW never traps users on stale UI (preserving the instant-deploy benefit).
- **Offline read cache**: runtime caching of note/library `GET` responses + an IndexedDB read store so `NoteView`/Library hydrate from cache when offline, with an "offline / showing cached" indicator.
- **Offline mutations + sync**: an IndexedDB mutation queue, Background Sync replay on reconnect, a conflict-resolution model (version/`updatedAt`-guarded last-write-wins with surfaced conflicts), and an **offline capture queue** (photo capture is stored and the upload→Bedrock transcribe deferred until online).
- **Auth-aware caching**: never serve one user's cached data to another; purge caches + IndexedDB on sign-out.
- A **spike + decision doc** for the static-export fork: feasibility of `output: 'export'` / a client-rendered SPA vs. the current SSR app, what breaks, effort estimate, and a go/no-go recommendation.
- (Only **if** the spike says go) decoupling the frontend into a static/client SPA against the existing Lambda API, a **pure client-token auth model** replacing the server middleware gate, and **bundling static assets into the APK** (dropping `server.url` for a bundled `webDir`).

## Out of scope

- **Offline AI generation**: OCR/transcribe (Bedrock), study-material generation, and TTS (Polly) are server-only and remain online-only — offline merely *queues* the request.
- **Real-time collaboration / CRDT merge**: conflict handling is simple version-guarded LWW with user-surfaced conflicts, not operational-transform/CRDT multi-writer merge.
- **Multi-device offline sync guarantees** beyond the single-device queue + reconnect replay.
- **iOS**: any Capacitor static-bundle work targets the existing Android shell only.

## Architecture & decisions

### Why a service worker first (and not a static export)

A static export (`output: 'export'`) cannot work against the current app without a rewrite: the auth middleware (`packages/application/proxy.ts`) verifies the Cognito JWT **server-side** on every request, and the app depends on **API routes + DynamoDB** and **SSR pages** — none of which survive a no-server static export. A **service worker**, by contrast, layers on top of the existing SSR app with no architectural change: it precaches the shell and caches responses at the edge of the WebView/browser. This is why Phases 1–3 come first and deliver real offline value without the fork.

The Capacitor Android WebView (Chromium) supports service workers, so the same SW benefits the native shell automatically — no `packages/mobile` change is needed for Phases 1–3 (consistent with the M12 rule: web changes need no new APK).

### The staleness trade-off (critical)

The current `server.url` model means **every web deploy is instantly live in the app**. A service worker that caches the shell risks serving **stale UI** after a deploy. The SW therefore must use a **versioned precache + an explicit update flow** (`skipWaiting`/`clientsClaim` gated behind a user "reload to update" prompt, or a short-TTL network-first strategy for the document) so the instant-deploy advantage is preserved. This is a first-class design constraint, not an afterthought.

### The static-export fork (Phase 4 — decision-gated)

True "launch with zero network" requires the frontend to be static/client-rendered and bundled into the APK. That means: (a) decouple the UI into a client SPA that calls the existing Lambda API, (b) move auth to a pure **client-token** model (no server middleware redirect), (c) switch Capacitor from `server.url` to a bundled `webDir`. This is a large, product-wide architecture change (it affects the website too), so Phase 4 begins with a **spike + go/no-go decision doc**; if "go", it likely graduates into its own milestone (provisionally **M23**) rather than ballooning M22.

## Sub-issues — dependency phases (waves)

Phases are sequential; **tasks within a phase are independent and built in parallel** by Sonnet subagents.

### M22.1 · Phase 1 — PWA app shell + offline fallback (no SSR change)

1. **(M) M22.1.1 — Service worker + Workbox precache + registration.** Add a Workbox-based service worker (via `next-pwa` or hand-rolled) that precaches the app shell + Next static assets and registers in the app; choose runtime strategies (network-first for documents to keep deploys fresh, cache-first for hashed static assets). Unit-test the SW config / strategy selection where pure.
2. **(S) M22.1.2 — Web app manifest + branded offline page + Capacitor `www/offline.html`.** Add `manifest.webmanifest` (icons reuse the M12 brand art, `display: standalone`, theme `#FAF8F3`), a branded offline fallback page served by the SW when the network and cache both miss, and wire the Capacitor shell's `www/offline.html` so the Android app shows brand UI on connection loss.
3. **(S) M22.1.3 — SW update UX + lifecycle.** "New version available — reload" prompt wired to the SW `waiting`/`controllerchange` lifecycle so users are never trapped on stale UI; document the versioning strategy. Tests for the update-prompt logic.

### M22.2 · Phase 2 — Offline read cache (view notes & library offline)

1. **(M) M22.2.1 — Runtime caching of note/library GET responses.** Stale-while-revalidate caching in the SW for the read API surface (library list, note metadata/body), with a cache-key + eviction policy. Integration-style test of the caching rule where feasible.
2. **(M) M22.2.2 — IndexedDB read store + read-through data layer.** An IndexedDB note cache and a read-through layer so `NoteView`/Library hydrate from cache when offline; an "offline / showing cached" UI indicator. Pure cache logic unit-tested.
3. **(S) M22.2.3 — Auth-aware caching + purge on sign-out.** Namespace caches per user (`sub`), never serve cross-user data, and clear SW caches + IndexedDB on sign-out. Tests for the purge + namespacing.

### M22.3 · Phase 3 — Offline mutations & sync

1. **(L) M22.3.1 — Offline mutation queue + Background Sync replay.** IndexedDB-backed queue of pending mutations (note create/edit), replayed via Background Sync (and a foreground reconnect fallback) when connectivity returns; idempotent replay. Unit tests for queue + replay ordering.
2. **(M) M22.3.2 — Conflict-resolution model.** Version/`updatedAt`-guarded last-write-wins on the API + client, with surfaced conflicts (don't silently clobber a newer server copy). Integration test of the conflict guard round-trip.
3. **(M) M22.3.3 — Offline capture queue.** Store captured photos locally and defer the upload→Bedrock transcribe until online; "will process when you're back online" UX. (Bedrock is server-only — offline only queues.)

### M22.4 · Phase 4 — Decision gate: static export / SPA decouple (architecture fork)

1. **(M) M22.4.1 — Spike + go/no-go decision doc.** Assess `output: 'export'` vs a client-rendered SPA: enumerate exactly what breaks (`proxy.ts` middleware, SSR pages, API-route coupling), the auth-model change required, the Capacitor `webDir` switch, and an effort estimate. Output a recommendation. **This task gates the rest of the phase** — run it first.
2. **(L) M22.4.2 — (if go) Client-token auth model.** Replace the server-side middleware gate with a pure client-token model the SPA can run offline-capably. (Spun out / scheduled only on a "go".)
3. **(L) M22.4.3 — (if go) Static bundle + Capacitor `webDir` switch + CI.** Build the static frontend, bundle it into the APK (drop `server.url`), and update the Android build. (Spun out / scheduled only on a "go" — likely promoted to its own milestone M23.)

## Milestone acceptance criteria (DoD)

- `npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run test:integration`, and the E2E suites pass on each phase's merge PR; no regressions to the online experience.
- **Phase 1:** the app registers a service worker; a cold launch serves the cached shell instantly; losing connectivity shows the **branded offline page** (in both the browser and the Android shell), not the raw WebView error; a post-deploy "new version available" prompt appears and reloading picks up the new build (no stale-UI trap).
- **Phase 2:** a note opened while online can be re-opened **offline** and renders from cache; the library list renders offline; an "offline / cached" indicator is shown; signing out purges cached data (no cross-user leakage).
- **Phase 3:** a note edited offline is queued and **syncs on reconnect**; a conflicting newer server copy is surfaced rather than clobbered; a photo captured offline is queued and transcribes once back online.
- **Phase 4:** a committed **decision doc** with a clear go/no-go on static export; if "go", the follow-on work is scheduled (likely as M23) with its own spec.

## Risks / open questions

- **Stale-UI vs instant-deploy:** the biggest risk — a naive precache defeats the `server.url` "deploys are instantly live" benefit. Mitigation: network-first for the document, versioned precache, and an enforced update prompt. Validate after a real deploy that clients pick up the new build promptly.
- **Auth + caching security:** caching authenticated responses risks cross-user leakage; namespace by `sub` and purge on sign-out. A future client-token model (Phase 4) has its own token-storage security considerations.
- **Conflict resolution scope creep:** offline edit + sync can balloon into CRDT territory; M22 deliberately caps it at version-guarded LWW with surfaced conflicts.
- **Service worker + Capacitor quirks:** SW scope, update timing, and cache storage limits behave subtly differently inside the Android WebView vs a browser — verify on a real device (tie into M12.4-style QA).
- **Phase 4 is product-wide, not mobile-only:** the static-export fork changes the web app's core architecture, so it's gated behind a spike and may become its own milestone rather than being forced into M22.

## Manual test plan

Exercise each phase with the browser dev-tools "Offline" toggle and on a real Android device (airplane mode), against a deployed `pr-<N>` stage.

1. **Shell offline (P1):** load the app online once, then go offline and relaunch → branded offline/app-shell UI appears, not a browser error.
2. **Update prompt (P1):** deploy a change, reopen the app → "new version available" prompt appears; reloading shows the new build.
3. **Read offline (P2):** open a note + the library online, go offline, navigate back to them → they render from cache with an "offline" indicator.
4. **Sign-out purge (P2):** sign out, sign in as a different user offline-then-online → no cached data from the first user is visible.
5. **Edit + sync (P3):** edit a note offline → change is queued; reconnect → it syncs; force a conflicting server edit → conflict is surfaced.
6. **Capture offline (P3):** capture a photo offline → queued with "will process when online"; reconnect → it uploads and transcribes.
7. **Android (P1–P3):** repeat the above in the Capacitor Android shell in airplane mode.
