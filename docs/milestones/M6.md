# M6 · Notebook library & full-text search

> Size: L · Depends on: M5

## Goal

Deliver the primary library screen — the user's home base after sign-in. The screen
ports `NotebookHome` from the design system exactly: greeting line with live review-card
count, search input, All / Review / Shared segmented tabs, a "Recent" section of
`NoteCard` tiles, the gradient-fill capture FAB, and the mobile bottom nav. Empty and
offline states (from `screens-states.jsx`) are also shipped in this milestone so the
library is production-ready for all connectivity conditions.

Full-text search is implemented server-side with a lightweight, serverless strategy:
a per-user inverted-token index maintained in DynamoDB (written on every note
save/update). Queries combine the token index with title/snippet match so results are
fast without any external search service. Note View (read-only, Original/Clean toggle,
tags, action bar) is also landed here so users can open any note from the library.

## Architecture & decisions

### Data model additions

No new DynamoDB tables are introduced. All access patterns use the existing Notes table
defined in M5 (`PK=USER#<sub>`, `SK=NOTE#<ulid>`).

#### list-recent access pattern

Query the Notes table directly on the primary key:

```
PK = USER#<sub>
SK begins_with NOTE#
ScanIndexForward: false   (newest ULID first — ULIDs are lexicographically monotonic)
Limit: 20
```

No new GSI required — ULID sort keys on the base table give recency order for free.

Key builder additions to `packages/core/src/db/keys.ts`:

```typescript
// Notes table key builders (additive to M5)
noteListRecentQuery(userSub: string): QueryInput   // PK + SK prefix, desc, limit 20
```

#### Full-text search — per-user inverted token index

Strategy: on every note save or update, tokenise `title + bodyText` (lowercase, strip
punctuation, deduplicate, discard stop-words). Write one item per unique token into
the same Notes table under a new item type:

```
PK  = USER#<sub>
SK  = TOKEN#<token>#NOTE#<noteId>
GSI1-PK  = USER#<sub>
GSI1-SK  = TOKEN#<token>
attrs: noteId, title, snippet (first 160 chars of body), updatedAt
```

At query time: for each term in the search string, `query GSI1` where
`PK=USER#<sub>` and `SK begins_with TOKEN#<term>`. Collect the union of matching
`noteId`s, then fetch the note metadata items in a `BatchGetItem` call and rank by
`updatedAt` descending. Title-prefix bonus: if the term matches the note title prefix,
boost that note to the top of results (client-side re-rank after fetch).

GSI definition (`infra/db.ts`):

| GSI | PK | SK | Purpose |
|-----|----|----|---------|
| `ByToken` | `USER#<sub>` (GSI1-PK) | `TOKEN#<token>#NOTE#<noteId>` (GSI1-SK) | Per-user token lookup for full-text search |

Key builders to add to `packages/core/src/db/keys.ts`:

```typescript
tokenItemKey(userSub: string, token: string, noteId: string): PrimaryKey
tokenQueryKey(userSub: string, term: string): QueryInput   // GSI1, begins_with TOKEN#<term>
```

Token normalisation logic (`packages/core/src/search/tokenise.ts`) — pure function,
unit-tested.

Stop-word list: a compact, hardcoded English + Spanish set (~100 words) so the index
stays lean. Stored as a constant, not in DynamoDB.

On note delete: write a `TransactWrite` that removes all `TOKEN#*#NOTE#<noteId>` items
for that note (query first to enumerate them, then batch-delete).

#### NoteView — open-by-id

Route: `GET /api/notes/[noteId]` (App Router route handler). Server reads Cognito sub
from the verified JWT, calls `ddb.get({ PK: noteKey(sub), SK: noteId })`, 404s if
the item does not exist or belongs to a different user. Never trusts a client-supplied
owner identifier.

Body content (Markdown) is stored in S3 (`bodyS3Key` on the note item). The route
handler fetches the S3 object and returns body + metadata as JSON. The Note View page
is a Server Component that pre-renders the Markdown server-side and streams it.

### API routes / route handlers

| Route | Method | Description |
|-------|--------|-------------|
| `GET /api/notes` | GET | List recent notes (`list-recent`). Query param `?q=<term>` enables search. Returns `{ notes: NoteMetadata[] }`. |
| `GET /api/notes/[noteId]` | GET | Open by id. Returns note metadata + Markdown body. |
| `DELETE /api/notes/[noteId]` | DELETE | Delete note + all token index items + S3 objects. |

### Infra changes

- `infra/db.ts`: add the `ByToken` GSI to the Notes table definition.
- `infra/application.ts`: ensure the app's IAM policy includes `dynamodb:Query` on the
  new GSI ARN.
- No new `sst.Secret` entries required.

### Security notes

- Every note read/delete route verifies the Cognito JWT (via `proxy.ts`) and checks
  that `note.PK === userKey(sub)` before returning data. A mismatched sub returns 403.
- S3 bucket for note bodies is private; the application IAM role has `s3:GetObject`
  only for its own prefix (`notes/<stage>/`). Pre-signed URLs are not exposed to the
  client — the route handler fetches and returns the body inline.
- Token index items inherit the same PK (`USER#<sub>`) so they are never accessible
  across users by DynamoDB IAM condition keys.

## Risks / open questions

- **S3 body fetch latency in SSR.** If the Markdown body is large (>50 KB), the SSR
  edge latency may be noticeable. Mitigation: stream the S3 body via Next.js streaming
  SSR; add a `Content-Length` guard (reject bodies >500 KB).
- **Token index write cost.** A note with 500 unique tokens creates 500 DynamoDB items.
  With a page size of 20 notes and 500 tokens each, a user's index could reach 10 000
  items quickly. Monitor table size; consider a token-frequency cutoff (skip tokens
  appearing in >80% of the user's notes as they are not discriminating).
- **Stop-word list completeness.** The hardcoded EN+ES list may miss domain-specific
  common words (e.g. "que", "del"). Accept initial imperfection; make the list
  extensible without a schema change.
- **Offline state management.** The offline banner relies on `navigator.onLine` which
  can be unreliable. If a more reliable offline strategy is needed, a service worker
  will be required (out of scope for M6).
- **ULID sort for recency.** ULID monotonicity guarantees recency order only if clocks
  are not skewed. Since ULIDs are generated server-side in a single region, this is
  safe; document it as a constraint.
