# M12 · Android app (Capacitor)

> Size: L · Depends on: M10

## Goal

Deliver a native Android app that wraps `app.transformmynotes.com` and ships to the Google Play Store. The implementation uses **Capacitor's `server.url`** to load the live hosted Next.js app inside a native WebView — avoiding the impossibility of statically bundling an SSR application — while the Capacitor native bridge still exposes genuine device capabilities: specifically the **native Android camera** for the photograph-a-note capture flow, with secure-storage and push-notification hooks for future milestones. The result is a thin native shell that stays in sync with every web deployment automatically, with one high-value native upgrade — camera access — that justifies Play Store distribution and meaningfully exceeds a bare web-wrapper.

The new code lives in a new npm workspace: `packages/mobile`. It is a pure client artifact (a Gradle/Android project produced by Capacitor) and has no SST entrypoint. The `deploy.yml` workflow is untouched; Android builds run in a separate `android.yml` CI workflow triggered by a `mobile-v*` tag or `workflow_dispatch`.

## In scope

- **`packages/mobile` Capacitor project scaffold**: `@capacitor/core`, `@capacitor/android`, `@capacitor/cli`, `capacitor.config.ts` with `server.url = https://app.transformmynotes.com`, application id `com.transformmynotes.app`, dev-override mechanism for pointing at a `pr-<N>` or local URL.
- **Native camera integration** (`@capacitor/camera`): the capture flow in `packages/application` branches on `Capacitor.isNativePlatform()` — native shell uses the Capacitor Camera plugin (gallery picker or photo capture), browser uses the existing `<input type="file" accept="image/*" capture>` / getUserMedia path. Camera permission declared in `AndroidManifest.xml`. This is the single most valuable native capability for Play Store approval.
- **WebView navigation allow-list**: restrict in-WebView navigation to `transformmynotes.com` origins only; external links open in the system browser via `Browser.open()` (Capacitor Browser plugin or `android:allowedUriSchemes` config) — the shell must not become an open web browser.
- **App Links / Digital Asset Links**: `assetlinks.json` served from `https://app.transformmynotes.com/.well-known/assetlinks.json` with the release signing key's SHA-256 fingerprint, so Android App Links from `transformmynotes.com` URLs open in the native app and Cognito Hosted-UI OAuth redirects return correctly to the app rather than to the system browser.
- **Android app configuration**: `applicationId = com.transformmynotes.app`, `versionCode` and `versionName` tied to the web app's release version (read from `package.json`), adaptive app icon (foreground + background layers), `@capacitor/splash-screen` with brand warm-ivory background + gold brandmark, `@capacitor/status-bar` themed to the brand's dark-text-on-ivory palette, safe-area inset handling (status bar + navigation bar) via CSS `env(safe-area-inset-*)` already present in the mobile shell.
- **Gradle build config**: release build variant, ProGuard rules for Capacitor, signing config reading keystore from env/file, `bundleRelease` Gradle task producing a signed `.aab`.
- **CI `android.yml` workflow**: sets up JDK 17 + Android SDK (via `setup-java` + `android-actions/setup-android` or manual SDK install), runs `npm ci`, `npx cap sync android`, and `./gradlew bundleRelease`; signing keystore decoded from `ANDROID_KEYSTORE_BASE64` secret; triggered on `mobile-v*` tag push or `workflow_dispatch`; produces the `.aab` as a workflow artifact. Does not interfere with `deploy.yml`.
- **Play Store release prep runbook**: store listing (screenshots, short description, full description), privacy policy URL (link `transformmynotes.com/privacy`), data-safety form, internal-testing track as first release target. Documented as a runbook section; actual Play Console steps are manual out-of-band actions not automated in CI.
- **Push notifications hook** (`@capacitor/push-notifications` + FCM): scoped to a single sub-issue, treated as optional in this milestone. If implementing, requires a Firebase project, `google-services.json` in `packages/mobile/android/app/`, a `FIREBASE_SERVER_KEY` secret, and `POST_NOTIFICATIONS` permission in the manifest. If deferred, the sub-issue is parked in Backlog with a clear interface hook so M13+ can pick it up without touching this milestone's merged code.
- **Mobile dev/run documentation**: `packages/mobile/README.md` (how to run on an emulator, how to point at a `pr-<N>` URL, how to generate a debug APK, how to run the Capacitor `sync` after a dependency update). Brief addendum to `CLAUDE.md` noting the workspace layout and the `android.yml` trigger.
- **QA on a real device or emulator**: device/emulator smoke-test against the signed debug APK covering every test-plan step in this document.

## Out of scope

- **iOS app**: the Capacitor project is deliberately Android-only for M12. iOS is the obvious next step — Capacitor makes it largely additive (add `@capacitor/ios`, run `npx cap add ios`, configure Xcode signing, submit to the App Store). Treat as M13.
- **Full offline support / static bundle**: the `server.url` approach requires an active network connection. Bundling the web app as a static Capacitor assets folder is not feasible for an SSR Next.js app without a full architectural shift to a static export or a dedicated API layer. Accepted limitation; an open question for a future offline-capable iteration.
- **Native rewrite of any screens**: this is a wrapper milestone. No screens are ported to native React Native or Kotlin/Compose. All UI continues to render in the WebView.
- **Deep native features beyond camera (and optional push)**: no native file system access beyond capture, no native editor, no native biometric auth, no geolocation, no NFC.
- **Play Store automated upload**: the CI workflow produces a `.aab` artifact but does not upload to Play Console. Automated supply-chain integration (e.g. `fastlane supply`) is a post-launch operational concern.
- **Per-`pr-<N>` native builds**: the CI `android.yml` is not triggered on every PR push. PR-stage testing is done manually by pointing `server.url` at the `pr-<N>` URL via the dev-override mechanism.

## Architecture & decisions

### Capacitor scaffold and `server.url` rationale

The app at `app.transformmynotes.com` is a **server-rendered Next.js (SSR) app** (deployed as `sst.aws.Nextjs` — Lambda@Edge + CloudFront), not a static export. Capacitor's default bundling approach (copying a `www/` static folder into the APK) cannot work here: there is no `next export` output, and every route handler, auth middleware (`packages/application/proxy.ts`), and API route requires a server. The only viable Capacitor approach is to set `server.url` in `capacitor.config.ts` so the WebView loads the live hosted site:

```ts
// packages/mobile/capacitor.config.ts
import { CapacitorConfig } from '@capacitor/cli';

const config: CapacitorConfig = {
  appId: 'com.transformmynotes.app',
  appName: 'TransformMyNotes',
  webDir: 'www',          // Required by Capacitor even when server.url is set;
                          // a minimal placeholder index.html lives here so
                          // `npx cap sync` succeeds.
  server: {
    url: process.env.CAPACITOR_SERVER_URL ?? 'https://app.transformmynotes.com',
    cleartext: false,     // HTTPS only in production; set to true only for
                          // http:// local dev URLs when CAPACITOR_SERVER_URL is set.
    androidScheme: 'https',
  },
};

export default config;
```

Setting `CAPACITOR_SERVER_URL=https://pr-5.pr.transformmynotes.com` (or a local `http://192.168.x.x:3002`) before running `npx cap sync android` + `npx cap run android` points the shell at a different URL for dev testing — no code change required.

**Trade-off accepted**: the app requires network access. An offline launch screen is added (`@capacitor/splash-screen`) so the wait while the WebView loads feels native, but there is no offline fallback. This is documented in the Play Store data-safety form and is an open question for a future offline iteration.

### Native camera integration

The capture flow in `packages/application` currently uses `<input type="file" accept="image/*" capture="environment">` for mobile browsers. Inside the Capacitor shell, this still technically works, but the native `@capacitor/camera` plugin delivers a significantly better UX (native Android camera intent, gallery picker, permission dialog handled by the OS) and is the primary native value-add that justifies Play Store distribution over a browser bookmark.

The web app adds a detection branch using `Capacitor.isNativePlatform()` (imported from `@capacitor/core`, which is a `devDependency` / optional import in `packages/application`). Because `@capacitor/core` is not bundled into the web app in production (it would be a dead import on the web), the pattern is:

```ts
// packages/application — capture utility (e.g. src/lib/capture.ts)
export async function pickImage(): Promise<File> {
  // Dynamic import so @capacitor/core is never bundled for the web
  if (typeof window !== 'undefined') {
    const { Capacitor } = await import('@capacitor/core').catch(() => ({ Capacitor: null }));
    if (Capacitor?.isNativePlatform()) {
      const { Camera, CameraResultType, CameraSource } = await import('@capacitor/camera');
      const photo = await Camera.getPhoto({
        quality: 90,
        resultType: CameraResultType.Blob,
        source: CameraSource.Prompt, // lets user choose camera or gallery
      });
      return new File([photo.blob!], `capture-${Date.now()}.jpg`, { type: 'image/jpeg' });
    }
  }
  // Web fallback: programmatically trigger the hidden file input
  return triggerFileInputPicker();
}
```

`packages/application/package.json` adds `@capacitor/core` and `@capacitor/camera` as **optional peer dependencies** (not in the main `dependencies` — the tree-shaking / dynamic import pattern prevents them from being bundled for web builds). They are installed as `devDependencies` in `packages/mobile` and available at runtime in the Android WebView via the Capacitor bridge.

`AndroidManifest.xml` must declare `<uses-permission android:name="android.permission.CAMERA" />` and `<uses-feature android:name="android.hardware.camera" android:required="false" />` (the `required="false"` allows the app to install on devices without a rear camera, e.g. some Chromebooks).

### Cognito auth inside the WebView and App Links

Since the shell loads the real hosted site, Amplify Auth works exactly as on the web — cookies set by the Next.js auth flow persist across WebView page loads within the same session. `packages/application/proxy.ts` verifies the Cognito JWT on every server request; no changes are needed to the server-side auth logic.

**OAuth/Hosted-UI redirect**: if the user signs in via the Cognito Hosted UI (`https://auth.transformmynotes.com`) and Cognito redirects back to `https://app.transformmynotes.com/...`, the redirect must land back in the native app's WebView rather than opening the system browser. This is handled with Android App Links (verified deep links):

1. Serve `/.well-known/assetlinks.json` from `https://app.transformmynotes.com` (a static Next.js route in `packages/application/app/.well-known/assetlinks.json/route.ts` returning the JSON with the release signing certificate SHA-256 fingerprint).
2. Add an `<intent-filter>` with `android:autoVerify="true"` in `AndroidManifest.xml` targeting `https://app.transformmynotes.com` — this registers the app as the verified handler for that origin.
3. The Capacitor `AndroidScheme = https` config means WebView-internal navigation to `app.transformmynotes.com` URLs stays in-app; only external origins trigger `Browser.open()`.

The SHA-256 fingerprint in `assetlinks.json` must match the release signing key. It is derived from the keystore: `keytool -list -v -keystore release.keystore -alias <alias>`. After rotating the signing key, the `assetlinks.json` must be updated and a new release pushed before App Links verification passes again.

### Android app configuration, icons, splash, safe-area, navigation allow-list

**App icons**: generate adaptive icons using Android Studio's Image Asset Studio or the `@capacitor/assets` CLI tool (`npx capacitor-assets generate --android`). Source files: `packages/mobile/resources/icon-foreground.png` (brandmark on transparent, 1024×1024), `packages/mobile/resources/icon-background.png` (warm ivory, 1024×1024). The legacy round/square icons at each density bucket (`mipmap-*dpi`) are generated automatically.

**Splash screen**: `@capacitor/splash-screen` with `launchShowDuration: 1500` and `backgroundColor: #FAF8F3` (the brand warm ivory). The splash image is the gold brandmark centered on ivory. Config in `capacitor.config.ts` under the `SplashScreen` plugin key.

**Status bar**: `@capacitor/status-bar` initialized in the web app on `deviceready` / `app.ready`: `StatusBar.setStyle({ style: Style.Light })` (dark text on light background, matching the brand) and `StatusBar.setBackgroundColor({ color: '#FAF8F3' })`. Guard with `Capacitor.isNativePlatform()`.

**Safe-area insets**: the `MobileShell` component in `packages/application/src/components/shells/MobileShell.tsx` already renders the bottom nav and FAB slot. The CSS layer needs `padding-top: env(safe-area-inset-top)` on the shell container and `padding-bottom: env(safe-area-inset-bottom)` on the bottom nav to avoid content sitting under the status bar or Android navigation bar. Add `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` in `packages/application/app/layout.tsx` to enable `env(safe-area-inset-*)` in the WebView.

**Navigation allow-list**: in `capacitor.config.ts`, set `server.allowNavigation` to `['*.transformmynotes.com']`. The Capacitor `@capacitor/browser` plugin handles external link opening — any `<a href>` targeting a non-`transformmynotes.com` origin is intercepted by the native layer and opened in the system browser (Chrome Custom Tab on Android). Implement the interception via a `window.open` override or the Capacitor `App.addListener('appUrlOpen', ...)` hook in `packages/application`.

**versionCode / versionName strategy**: `versionName` mirrors the npm workspace root `version` field in `package.json` (e.g. `1.12.0`). `versionCode` is a monotonically increasing integer managed in `packages/mobile/android/app/build.gradle` — increment it on every Play Store submission. A helper script (`packages/mobile/scripts/bump-version.ts`) reads the root `package.json` version and writes the matching `versionName` + an incremented `versionCode` to `build.gradle`, so a release tag (`mobile-v1.12.0`) triggers the CI workflow with consistent version metadata.

**applicationId**: `com.transformmynotes.app`. This is permanent — changing it after Play Store submission requires a new app listing.

### Push notifications (optional sub-issue)

`@capacitor/push-notifications` wraps Firebase Cloud Messaging (FCM). To implement: add a Firebase project, download `google-services.json` into `packages/mobile/android/app/`, add the `POST_NOTIFICATIONS` runtime permission (Android 13+), initialize FCM in the web app under `Capacitor.isNativePlatform()`, and store the FCM registration token in the user's DynamoDB `UserData` record via a `PATCH /api/user/push-token` route. Server-side push dispatch would be a new infra module (`infra/push.ts`) using the Firebase Admin SDK.

**Recommendation: defer push to M13.** Including FCM setup in M12 significantly expands scope and the Firebase dependency adds complexity to both the Gradle build and the server-side infra. The sub-issue is drafted below for completeness but is marked deferred; the Capacitor project is structured so adding push notifications later requires no changes to M12's merged code (a `devDependencies` install + new plugin config is sufficient).

### CI `android.yml` workflow

A new workflow at `.github/workflows/android.yml` builds the release `.aab`. It is completely independent of `deploy.yml` — it does not deploy any SST resources and is not triggered by PR events or master pushes.

Trigger: `push` with `tags: ['mobile-v*']` or `workflow_dispatch`. A `mobile-v*` tag is pushed manually after a web release has deployed and been verified.

Key steps:
1. Checkout + `actions/setup-java@v4` (JDK 17, Temurin distribution — required by Android Gradle Plugin 8+).
2. `npm ci` (installs all workspaces including `packages/mobile`).
3. Decode the signing keystore: `echo "$ANDROID_KEYSTORE_BASE64" | base64 --decode > release.jks`.
4. `npx cap sync android` (from `packages/mobile`) — copies the `www/` placeholder and syncs native plugins.
5. `cd packages/mobile/android && ./gradlew bundleRelease` with Gradle properties set for the keystore path, password, and key alias via `-P` flags or a `local.properties` file written in the step (never committed).
6. Upload `packages/mobile/android/app/build/outputs/bundle/release/app-release.aab` as a workflow artifact with 30-day retention.

Signing secrets (GitHub Actions, set under Settings → Secrets and variables → Actions):
- `ANDROID_KEYSTORE_BASE64` — base64-encoded `.jks` / `.keystore` file.
- `ANDROID_KEYSTORE_PASSWORD` — the keystore password.
- `ANDROID_KEY_ALIAS` — the key alias within the keystore.
- `ANDROID_KEY_PASSWORD` — the key password (may equal the keystore password).

The keystore is the single most critical secret: **losing it means you can never update the Play Store app listing**. Store a backup copy in a secure location (e.g. AWS Secrets Manager under the production stage) independently of the GitHub secret.

### Play Store release prep runbook

This is a manual out-of-band process performed by the developer in the Play Console (play.google.com/console). Automate nothing here for M12.

1. **Create app**: new application in Play Console, package name `com.transformmynotes.app`, default language Brazilian Portuguese (pt-BR) as primary, English (en-US) as secondary.
2. **Store listing**: short description ≤ 80 chars ("Photograph your handwritten notes and get clean, searchable Markdown instantly."); full description ≤ 4000 chars. Screenshots: 2–8 phone screenshots (1080×1920 minimum), 1 feature graphic (1024×500). App icon: 512×512 PNG (the adaptive icon foreground on a solid ivory background).
3. **Privacy policy**: link to `https://transformmynotes.com/privacy` (ensure this URL exists on the marketing site — if not, add a placeholder page as part of M12's acceptance).
4. **Data safety form**: declare: no data shared with third parties; data collected — name, email address (account management, app functionality, required, no opt-out); photos (app functionality, required, no opt-out, not sent to third parties beyond AWS S3 in the developer's account); no precise location collected. Answer "no" to financial info, health info, messages.
5. **Content rating**: complete the rating questionnaire (expects a utilitarian productivity app — all answers "no" to violence, mature content; target "Everyone").
6. **Internal testing track**: upload the `.aab` from the CI artifact, create an internal test release, add internal testers by Google account email. Verify the app installs and runs before promoting to closed/open testing.
7. **Promote to production**: after internal testing passes, create a production release. Google typically reviews in 1–3 business days for established accounts; first-time submissions may take longer. Policy note: see Risk #2 in Risks / open questions about Play Store thin-wrapper policy.

## Risks / open questions

- **`server.url` requires network**: unlike a fully-bundled Capacitor app, this shell cannot function offline. If the user has no network connection, the WebView shows a "No internet connection" error page. Mitigation: the splash screen is shown while the WebView loads (masking the load time on slow connections); consider adding a simple offline HTML page in `www/` as a network-error fallback. Open question: is a future offline-capable iteration warranted, and what would it require (static export feasibility, service worker, or a separate API package)?
- **Play Store thin-wrapper policy**: Google Play's [Spam and Minimum Functionality policy](https://support.google.com/googleplay/android-developer/answer/9899234) can reject apps that are "simply a WebView of a website" without added native value. Mitigate by: (1) genuinely using the native camera plugin (demonstrable native capability), (2) adding the push-notification hook (even if the server-side dispatch is M13), (3) ensuring the Play Store listing clearly describes the app's unique value (handwriting OCR, spaced repetition). If Google rejects the first submission, the appeal path is to add more native features before resubmission.
- **Digital Asset Links SHA-256 fingerprint mismatch**: if the `assetlinks.json` fingerprint does not exactly match the installed app's signing certificate, App Links verification fails silently — Cognito OAuth redirects open in the system browser instead of the app. Mitigation: derive the fingerprint from the actual release keystore (never the debug keystore) before publishing `assetlinks.json`; verify App Link association with `adb shell pm get-app-links com.transformmynotes.app` after installation.
- **Keystore loss is unrecoverable**: Google Play enforces app signing by the original keystore — if the release keystore is lost, the app listing can never be updated (only a new listing with a new `applicationId`). Mitigation: back up `release.jks` and its password to AWS Secrets Manager under the production stage immediately after creation; store a second encrypted copy offline.
- **Cognito Hosted UI redirect back into the app**: the `assetlinks.json` + App Links approach handles verified HTTPS deep links, but the Cognito Hosted UI redirect URI must be registered in the Cognito app client (`infra/auth.ts`) as `https://app.transformmynotes.com/auth/callback` (or whichever callback path Amplify uses). Verify the registered redirect URIs include this path before testing sign-in via the Hosted UI on Android.
- **Next.js SSR session cookies in WebView**: Amplify Auth uses `localStorage` on the web but the Next.js middleware (`proxy.ts`) reads a `CognitoIdToken` cookie. Confirm the cookie is set correctly by the sign-in flow when running inside the Android WebView (WebView respects `Set-Cookie` headers from the same origin). If Amplify writes only to `localStorage` and not to a cookie, the server-side `proxy.ts` middleware will redirect every page to `/login`. Mitigation: the existing cookie-based sign-in pattern used by the `packages/application` middleware must be verified in the WebView during sub-issue 10's QA pass.
- **iOS deferred**: the Capacitor project is Android-only for M12. Adding iOS will require macOS CI runner time, an Apple Developer account ($99/year), and Xcode build configuration. Recommend M13.
- **`versionCode` drift**: if multiple developers trigger the `android.yml` workflow independently against different base commits, `versionCode` in `build.gradle` can diverge. Mitigation: treat the `build.gradle` `versionCode` as a file that is always incremented via the `bump-version.ts` script on the release coordinator's machine, committed, and then tagged — never auto-incremented by CI itself.
