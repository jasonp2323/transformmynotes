# M12 · Android app (Capacitor)

> Size: L · Depends on: M10

## Goal

Deliver a native Android app that wraps `app.transformmynotes.com` and is **distributed as a directly-installable, signed APK (sideload)** — hosted on GitHub Releases (and/or linked from the marketing site) — **outside any app store**. The implementation uses **Capacitor's `server.url`** to load the live hosted Next.js app inside a native WebView — avoiding the impossibility of statically bundling an SSR application — while the Capacitor native bridge still exposes genuine device capabilities: specifically the **native Android camera** for the photograph-a-note capture flow, with secure-storage and push-notification hooks for future milestones. The result is a thin native shell that stays in sync with every web deployment automatically, with one high-value native upgrade — camera access — that makes it meaningfully better than a bare web bookmark.

> **Distribution decision (updated):** this milestone deliberately does **NOT** publish to the Google Play Store. The app is delivered as a signed `.apk` that users install directly ("sideload"). This removes the Play Console account, the data-safety/content-rating forms, the App-Store review cycle, and the thin-wrapper-policy risk entirely. The trade-offs (install friction, OS "unknown sources" warning, no automatic store updates) are accepted and documented under Risks. Publishing to an app store later remains an additive option.

The new code lives in a new npm workspace: `packages/mobile`. It is a pure client artifact (a Gradle/Android project produced by Capacitor) and has no SST entrypoint. The `deploy.yml` workflow is untouched; Android builds run in a separate `android.yml` CI workflow triggered by a `mobile-v*` tag or `workflow_dispatch`.

## In scope

- **`packages/mobile` Capacitor project scaffold**: `@capacitor/core`, `@capacitor/android`, `@capacitor/cli`, `capacitor.config.ts` with `server.url = https://app.transformmynotes.com`, application id `com.transformmynotes.app`, dev-override mechanism for pointing at a `pr-<N>` or local URL.
- **Native camera integration** (`@capacitor/camera`): the capture flow in `packages/application` branches on `Capacitor.isNativePlatform()` — native shell uses the Capacitor Camera plugin (gallery picker or photo capture), browser uses the existing `<input type="file" accept="image/*" capture>` / getUserMedia path. Camera permission declared in `AndroidManifest.xml`. This is the single most valuable native capability and the reason the shell is worth installing.
- **WebView navigation allow-list**: restrict in-WebView navigation to `transformmynotes.com` origins only; external links open in the system browser via `Browser.open()` (Capacitor Browser plugin or `android:allowedUriSchemes` config) — the shell must not become an open web browser.
- **App Links / Digital Asset Links**: `assetlinks.json` served from `https://app.transformmynotes.com/.well-known/assetlinks.json` with the release signing key's SHA-256 fingerprint, so Android App Links from `transformmynotes.com` URLs open in the native app and Cognito Hosted-UI OAuth redirects return correctly to the app rather than to the system browser. (Verified App Links work for sideloaded APKs too — verification depends only on the hosted `assetlinks.json` matching the installed APK's signing certificate, not on the distribution channel.)
- **Android app configuration**: `applicationId = com.transformmynotes.app`, `versionCode` and `versionName` tied to the web app's release version (read from `package.json`), adaptive app icon (foreground + background layers), `@capacitor/splash-screen` with brand warm-ivory background + gold brandmark, `@capacitor/status-bar` themed to the brand's dark-text-on-ivory palette, safe-area inset handling (status bar + navigation bar) via CSS `env(safe-area-inset-*)`.
- **Gradle build config**: release build variant, ProGuard rules for Capacitor, signing config reading keystore from env/file, an `assembleRelease` Gradle task producing a signed `.apk`.
- **CI `android.yml` workflow**: sets up JDK 17 + Android SDK, runs `npm ci`, `npx cap sync android`, and `./gradlew assembleRelease`; signing keystore decoded from `ANDROID_KEYSTORE_BASE64` secret; triggered on `mobile-v*` tag push or `workflow_dispatch`; produces the signed `.apk` as a workflow artifact **and attaches it to the GitHub Release** for the tag (so users have a stable download URL). Does not interfere with `deploy.yml`.
- **APK distribution & install (sideload) runbook**: how a release is published (tag `mobile-v*` → CI attaches `app-release.apk` to the GitHub Release), the end-user install instructions (download the APK, allow "install unknown apps" for the browser/files app, install), the update story (a new signed APK installs over the old one **only if signed with the same keystore**), and the privacy-policy link (`transformmynotes.com/privacy`). Documented as a runbook section in `packages/mobile/README.md`.
- **Push notifications hook** (`@capacitor/push-notifications` + FCM): scoped to a single sub-issue, **deferred to M13**. Only the interface hook ships in M12; no Firebase project, `google-services.json`, or FCM secret.
- **Mobile dev/run documentation**: `packages/mobile/README.md` (how to run on an emulator, how to point at a `pr-<N>` URL, how to generate a debug APK, how to run the Capacitor `sync` after a dependency update, how to cut a signed release APK). Brief addendum to `CLAUDE.md` noting the workspace layout and the `android.yml` trigger.
- **QA on a real device or emulator**: device/emulator smoke-test against the signed debug/release APK covering every test-plan step in this document.

## Out of scope

- **App-store distribution (Google Play / Apple App Store)**: deliberately not used in M12 — the app is distributed by direct signed-APK sideload. Publishing to the Play Store later is an additive option (it would re-introduce the Play Console listing, data-safety form, content rating, and an `.aab` bundle build); the Apple App Store additionally needs an iOS Capacitor target. Neither is part of this milestone.
- **iOS app**: the Capacitor project is deliberately Android-only for M12. iOS is the obvious next step — Capacitor makes it largely additive (`@capacitor/ios`, `npx cap add ios`, Xcode signing). Treat as a later milestone.
- **Full offline support / static bundle**: the `server.url` approach requires an active network connection. Bundling the web app as a static Capacitor assets folder is not feasible for an SSR Next.js app without a full architectural shift to a static export or a dedicated API layer. Accepted limitation; an open question for a future offline-capable iteration.
- **Native rewrite of any screens**: this is a wrapper milestone. No screens are ported to native React Native or Kotlin/Compose. All UI continues to render in the WebView.
- **Deep native features beyond camera (and the deferred push hook)**: no native file system access beyond capture, no native editor, no native biometric auth, no geolocation, no NFC.
- **In-app auto-update**: the sideload model has no store-managed updates. M12 does not build an in-app "a new version is available" updater (see Risks for the open question); users get new versions by installing the latest published APK.

## Architecture & decisions

### Capacitor scaffold and `server.url` rationale

The app at `app.transformmynotes.com` is a **server-rendered Next.js (SSR) app** (deployed as `sst.aws.Nextjs` — Lambda@Edge + CloudFront), not a static export. Capacitor's default bundling approach (copying a `www/` static folder into the APK) cannot work here: there is no `next export` output, and every route handler, auth middleware (`packages/application/proxy.ts`), and API route requires a server. The only viable Capacitor approach is to set `server.url` in `capacitor.config.ts` so the WebView loads the live hosted site:

```ts
// packages/mobile/capacitor.config.ts
import { CapacitorConfig } from '@capacitor/cli';

const config: CapacitorConfig = {
  appId: 'com.transformmynotes.app',
  appName: 'TransformMyNotes',
  webDir: 'www',          // Required by Capacitor even when server.url is set;
                          // a minimal placeholder index.html lives here so
                          // `npx cap sync` succeeds.
  server: {
    url: process.env.CAPACITOR_SERVER_URL ?? 'https://app.transformmynotes.com',
    cleartext: false,     // HTTPS only in production; set to true only for
                          // http:// local dev URLs when CAPACITOR_SERVER_URL is set.
    androidScheme: 'https',
  },
};

export default config;
```

Setting `CAPACITOR_SERVER_URL=https://pr-5.pr.transformmynotes.com` (or a local `http://192.168.x.x:3002`) before running `npx cap sync android` + `npx cap run android` points the shell at a different URL for dev testing — no code change required.

**Trade-off accepted**: the app requires network access. An offline launch screen is added (`@capacitor/splash-screen`) so the wait while the WebView loads feels native, but there is no offline fallback. This is an open question for a future offline iteration.

### Native camera integration

The capture flow in `packages/application` currently uses `<input type="file" accept="image/*" capture="environment">` for mobile browsers. Inside the Capacitor shell, this still technically works, but the native `@capacitor/camera` plugin delivers a significantly better UX (native Android camera intent, gallery picker, permission dialog handled by the OS) and is the primary native value-add that makes the installed shell better than a browser bookmark.

The web app adds a detection branch using `Capacitor.isNativePlatform()` (imported from `@capacitor/core` via a dynamic import so it is never bundled into the web build):

```ts
// packages/application — capture utility (lib/capture/pick-image.ts)
export async function pickImage(opts: { webFallback: () => Promise<File> }): Promise<File> {
  if (typeof window !== 'undefined') {
    const cap = await import('@capacitor/core').catch(() => null);
    if (cap?.Capacitor?.isNativePlatform()) {
      const { Camera, CameraResultType, CameraSource } = await import('@capacitor/camera');
      const photo = await Camera.getPhoto({
        quality: 90,
        resultType: CameraResultType.Uri,  // NB: the plugin has no `Blob` result type
        source: CameraSource.Prompt,        // lets user choose camera or gallery
      });
      const blob = await (await fetch(photo.webPath!)).blob();
      return new File([blob], `capture-${Date.now()}.jpg`, { type: blob.type || 'image/jpeg' });
    }
  }
  // Web fallback: reuse the existing hidden <input type="file"> picker.
  return opts.webFallback();
}
```

`packages/application/package.json` declares `@capacitor/core` and `@capacitor/camera` (and the other plugins used via dynamic import) as **optionalDependencies** — the dynamic-import pattern keeps them out of the web production bundle. They are installed as `dependencies` in `packages/mobile` and available at runtime in the Android WebView via the Capacitor bridge.

`AndroidManifest.xml` declares `<uses-permission android:name="android.permission.CAMERA" />`, `<uses-permission android:name="android.permission.READ_MEDIA_IMAGES" />`, and `<uses-feature android:name="android.hardware.camera" android:required="false" />` (the `required="false"` allows the app to install on devices without a rear camera).

### Cognito auth inside the WebView and App Links

Since the shell loads the real hosted site, Amplify Auth works exactly as on the web — cookies set by the Next.js auth flow persist across WebView page loads within the same session. `packages/application/proxy.ts` verifies the Cognito JWT on every server request; no changes are needed to the server-side auth logic.

**OAuth/Hosted-UI redirect**: if the user signs in via the Cognito Hosted UI (`https://auth.transformmynotes.com`) and Cognito redirects back to `https://app.transformmynotes.com/...`, the redirect must land back in the native app's WebView rather than opening the system browser. This is handled with Android App Links (verified deep links):

1. Serve `/.well-known/assetlinks.json` from `https://app.transformmynotes.com` (a Next.js route at `packages/application/app/.well-known/assetlinks.json/route.ts` returning the JSON with the release signing certificate SHA-256 fingerprint).
2. Add an `<intent-filter>` with `android:autoVerify="true"` in `AndroidManifest.xml` targeting `https://app.transformmynotes.com` — this registers the app as the verified handler for that origin.
3. The Capacitor `AndroidScheme = https` config means WebView-internal navigation to `app.transformmynotes.com` URLs stays in-app; only external origins trigger `Browser.open()`.

The SHA-256 fingerprint in `assetlinks.json` must match the keystore that signed the installed APK (`keytool -list -v -keystore release.jks -alias <alias>`). Because there is no Play App Signing in the sideload model, this is simply the **release keystore's own** fingerprint — there is no separate Google-managed cert to also list. After rotating the signing key, `assetlinks.json` must be updated and a new release published before App Links verification passes again.

**Fingerprint configuration — NOT a secret.** The SHA-256 fingerprint is a **public** value (it is published verbatim in `assetlinks.json` for the world to read), so it is **not** an `sst.Secret` — a declared-but-unset `sst.Secret` throws `SecretMissingError` at deploy for every stage (the documented `DEV_COGNITO_USER_POOL_ID` trap). It is threaded into the app as a plain env var: `ANDROID_SIGNING_FINGERPRINT`, read via `process.env` in `infra/application.ts` (omitted from the app environment when unset) and forwarded from a GitHub Actions repository **variable** in `deploy.yml`. The `assetlinks.json` route throws (500) at request time if it is unset, so a missing value fails loudly without blocking deploys. Set the repo variable once the release keystore exists.

### Android app configuration, icons, splash, safe-area, navigation allow-list

**App icons**: generated with `@capacitor/assets` (`npx capacitor-assets generate --android`) from source art in `packages/mobile/assets/`: `icon-foreground.png` (gold brandmark on transparent, 1024×1024) and `icon-background.png` (warm ivory, 1024×1024), plus `splash.png`/`splash-dark.png`. The legacy round/square icons and the per-density splash buckets are generated automatically.

**Splash screen**: `@capacitor/splash-screen` with `launchShowDuration: 1500` and `backgroundColor: #FAF8F3` (the brand warm ivory). The splash image is the gold brandmark centered on ivory. Config in `capacitor.config.ts` under the `SplashScreen` plugin key.

**Status bar**: `@capacitor/status-bar` initialized on `deviceready` / app init: `StatusBar.setStyle({ style: Style.Light })` (dark text on light background) and `StatusBar.setBackgroundColor({ color: '#FAF8F3' })`. Guarded with `Capacitor.isNativePlatform()`.

**Safe-area insets**: `padding-top: env(safe-area-inset-top)` on the mobile shell container (`.tmn-shell--mobile`) and `padding-bottom: env(safe-area-inset-bottom)` on the bottom nav (`.tmn-bottomnav`) so content and the bottom nav clear the status bar and Android gesture bar. `<meta name="viewport" content="… viewport-fit=cover">` (via the Next.js `viewport` export in `app/layout.tsx`) enables `env(safe-area-inset-*)` in the WebView.

**Navigation allow-list**: `server.allowNavigation: ['*.transformmynotes.com']` in `capacitor.config.ts`. A capturing document click listener (in the `NativeBridge` client component, under `isNativePlatform()`) intercepts `<a>` clicks to non-`transformmynotes.com` origins and opens them via `@capacitor/browser` `Browser.open()` (Chrome Custom Tab). The same component registers a back-button handler (`window.history.back()` while history remains, else `App.exitApp()`).

**versionCode / versionName strategy**: `versionName` mirrors the npm workspace root `version` field in `package.json`. `versionCode` is a monotonically increasing integer in `packages/mobile/android/app/build.gradle` — increment it on every published release. The helper `packages/mobile/scripts/bump-version.ts` reads the root `package.json` version and writes the matching `versionName` + an incremented `versionCode`, so a release tag (`mobile-v1.12.0`) triggers CI with consistent version metadata.

**applicationId**: `com.transformmynotes.app`. Permanent — changing it means a fresh install with a different package name.

### Push notifications (deferred to M13)

`@capacitor/push-notifications` wraps Firebase Cloud Messaging (FCM). Full integration (Firebase project, `google-services.json`, `POST_NOTIFICATIONS` permission, `PATCH /api/user/push-token` + `UserData.fcmToken`, server-side dispatch via Firebase Admin SDK in a new `infra/push.ts`) is **deferred to M13**. M12 ships only the interface hook: `registerForPushNotifications()` (no-op off-native) + a `/api/user/push-token` stub route returning `501`. No Firebase dependency, `google-services.json`, or FCM secret is added in M12.

### CI `android.yml` workflow

A new workflow at `.github/workflows/android.yml` builds the signed release `.apk`. It is completely independent of `deploy.yml` — it deploys no SST resources and is not triggered by PR events or master pushes.

Trigger: `push` with `tags: ['mobile-v*']` or `workflow_dispatch`. A `mobile-v*` tag is pushed manually after a web release has deployed and been verified.

Key steps:
1. Checkout + `actions/setup-java@v4` (JDK 17, Temurin — required by Android Gradle Plugin 8+).
2. `npm ci` (installs all workspaces including `packages/mobile`).
3. Decode the signing keystore: `echo "$ANDROID_KEYSTORE_BASE64" | base64 --decode > release.jks`.
4. `npx cap sync android` (from `packages/mobile`) — copies the `www/` placeholder and syncs native plugins.
5. `cd packages/mobile/android && ./gradlew assembleRelease` with the keystore path, password, and key alias passed via `-P` flags (never committed).
6. Upload `packages/mobile/android/app/build/outputs/apk/release/app-release.apk` as a workflow artifact (30-day retention) **and attach it to the GitHub Release** for the tag so there is a stable public download URL for sideloading.

Signing secrets (GitHub Actions, set under Settings → Secrets and variables → Actions):
- `ANDROID_KEYSTORE_BASE64` — base64-encoded `.jks` / `.keystore` file.
- `ANDROID_KEYSTORE_PASSWORD` — the keystore password.
- `ANDROID_KEY_ALIAS` — the key alias within the keystore.
- `ANDROID_KEY_PASSWORD` — the key password (may equal the keystore password).

Separately, the **public** `ANDROID_SIGNING_FINGERPRINT` (the SHA-256 of the above keystore's cert, for `assetlinks.json`) is a GitHub Actions **variable** consumed by `deploy.yml` — not a signing secret and not used by `android.yml`.

The keystore is the single most critical secret: **losing it means a new APK can no longer install over an existing install** (signature mismatch — users would have to uninstall first). Store a backup copy in a secure location (e.g. AWS Secrets Manager under the production stage) independently of the GitHub secret.

### APK distribution & install (sideload) runbook

This is the distribution path that replaces an app-store listing. It is mostly automated by `android.yml` plus a one-time end-user instruction page.

1. **Publish a release**: bump the version (`npm run bump-version -w packages/mobile`), commit, then push a `mobile-v<x.y.z>` tag. `android.yml` builds the signed `app-release.apk`, uploads it as a run artifact, and attaches it to the GitHub Release for that tag.
2. **Provide the download**: link the GitHub Release's `app-release.apk` asset from wherever users are directed (e.g. a "Get the Android app" link on `transformmynotes.com`, or a direct link shared with testers). A short-lived internal distribution to a tester group works the same way — just share the Release URL.
3. **End-user install instructions** (document these on the download page): download the `.apk` on the device → when prompted, allow the browser/Files app to "install unknown apps" (Settings → Apps → Special access) → open the downloaded file → Install. On first launch Android may show Play Protect scanning; that is expected for sideloaded apps.
4. **Updates**: publishing a newer `mobile-v*` release produces a higher `versionCode` APK; installing it over the existing app updates in place — **provided it is signed with the same release keystore** (otherwise the install is rejected as a signature mismatch).
5. **Privacy policy**: keep `https://transformmynotes.com/privacy` live and linked from the download page (good practice and required if the app is ever submitted to a store later).

## Risks / open questions

- **`server.url` requires network**: unlike a fully-bundled Capacitor app, this shell cannot function offline. With no connection the WebView shows a "No internet connection" error page. Mitigation: the splash screen masks load time on slow connections; consider a simple offline HTML page in `www/` as a network-error fallback. Open question: is a future offline-capable iteration warranted, and what would it require?
- **Sideload friction & trust warnings**: installing outside an app store requires the user to enable "install unknown apps" and dismiss a Play Protect scan prompt — higher friction and lower trust than a store install, and no store-managed auto-update. Mitigation: a clear install-instructions page; keep the download on a trusted `transformmynotes.com` link / signed GitHub Release. Open question: is an in-app "update available" checker worth adding (poll the latest `versionCode` and prompt to download the new APK)?
- **No automatic updates**: users do not get updates pushed the way a store would deliver them; they must install each new APK. Mitigation: because the UI is loaded from `server.url`, **web changes ship instantly without an APK update** — only native-shell changes (plugins, manifest, icons, `versionCode`) actually require a new APK, which is rare. This substantially softens the no-auto-update concern.
- **Digital Asset Links SHA-256 fingerprint mismatch**: if `assetlinks.json` does not exactly match the installed APK's signing certificate, App Links verification fails silently — Cognito OAuth redirects open in the system browser instead of the app. Mitigation: derive the fingerprint from the actual release keystore (never the debug keystore) and set the `ANDROID_SIGNING_FINGERPRINT` repo variable before publishing; verify with `adb shell pm get-app-links com.transformmynotes.app` after installation.
- **Keystore loss breaks in-place updates**: with no Play App Signing, an APK signed with a different key will not install over an existing install (signature mismatch) — users would have to uninstall/reinstall. Mitigation: back up `release.jks` and its password to AWS Secrets Manager under the production stage immediately after creation; store a second encrypted copy offline.
- **Cognito Hosted UI redirect back into the app**: the Cognito app client (`infra/auth.ts`) must register the redirect URI Amplify uses (e.g. `https://app.transformmynotes.com/auth/callback`). Verify the registered redirect URIs include it before testing Hosted-UI sign-in on Android.
- **Next.js SSR session cookies in WebView**: the middleware (`proxy.ts`) reads a `CognitoIdToken` cookie. Confirm the sign-in flow sets that cookie inside the Android WebView (WebView respects `Set-Cookie` from the same origin). If Amplify wrote only to `localStorage`, `proxy.ts` would redirect every page to `/login` — verify during the QA pass.
- **iOS deferred**: Android-only for M12. Adding iOS needs macOS CI runner time, an Apple Developer account, and Xcode config.
- **`versionCode` drift**: if multiple people trigger `android.yml` against different base commits, `versionCode` can diverge. Mitigation: always bump via `bump-version.ts` on the release coordinator's machine, commit, then tag — never auto-increment in CI.

## Manual test plan

Perform on a physical Android device (or AVD Pixel profile, API 33+) using the debug APK (`./gradlew assembleDebug`) or the signed release `.apk` from the CI artifact / GitHub Release. The `CAPACITOR_SERVER_URL` for manual testing should point at a deployed `pr-<N>` stage or the production URL.

1. **Install and launch** — install the `.apk` via `adb install app-debug.apk` or by sideloading (download + "install unknown apps" + Install). Tap the app icon. Expected: the splash screen (warm-ivory background, gold brandmark) appears for ~1.5s, then the app shell loads showing the sign-in page. No browser address bar or navigation chrome is visible.

2. **Sign in** — enter valid Cognito credentials. Expected: Amplify Auth completes sign-in within the WebView; the app navigates to `/dashboard` without opening an external browser. Status bar shows dark icons on warm ivory. No "Not Secure" warning.

3. **Dashboard renders correctly** — verify `/dashboard` renders note cards with correct layout. Expected: content sits below the status-bar safe-area inset; the bottom navigation sits above the gesture-bar safe-area inset.

4. **Native camera capture** — tap the capture FAB. Expected: the native Android camera picker dialog appears (OS-level, not a browser `<input>` dialog) offering "Take Photo" and "Choose from Gallery". Take a photo. Expected: the photo is accepted and returned to the upload flow.

5. **Photo upload and transform** — confirm the photo uploads (progress visible) and the note enters a "Transforming…" state; after Bedrock completes, the note appears in the library as clean Markdown.

6. **Back-button navigation** — on the note view, press the Android back button. Expected: navigates back to the dashboard (WebView history). Press back again at the dashboard root. Expected: the app exits rather than navigating further.

7. **External link handling** — tap an external link (e.g. an attribution/"Learn more" link). Expected: a Chrome Custom Tab opens over the app; the shell is not navigated to the external URL. Closing the Custom Tab returns to the app.

8. **Session persistence** — background the app, wait 30s, re-open. Expected: session still active; dashboard loads without re-sign-in. Background 10+ minutes and re-open. Expected: Amplify silently refreshes the token if expired; no fall-back to sign-in unless the refresh token expired.

9. **App Links verification** — open Chrome and navigate to `https://app.transformmynotes.com`. Expected: Android prompts to open in the TransformMyNotes app (or opens it directly if fully verified). Alternatively, `adb shell pm get-app-links com.transformmynotes.app` shows `STATE_VERIFIED` for `app.transformmynotes.com`. (Requires `ANDROID_SIGNING_FINGERPRINT` matching the installed APK's signing key.)

10. **Adaptive icon** — long-press the app icon on the launcher. Expected: the icon clips to the launcher's mask (circle, rounded square, etc.) showing the gold brandmark foreground on the ivory background, with no white corners bleeding outside the mask.

11. **Offline graceful degradation** — disable Wi-Fi and mobile data. Launch or re-open. Expected: the WebView shows a "No internet connection" error state (browser default or a custom `www/offline.html`). No crash, no blank screen.

12. **CI build verification** — push a `mobile-v<x.y.z>` tag. Expected: `.github/workflows/android.yml` triggers and completes; `deploy.yml` does not trigger. The signed `app-release.apk` is attached to the GitHub Release for the tag; download and confirm it installs on a device via sideload.
