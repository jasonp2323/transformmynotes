# M25 · Study Progress & Insights (a per-user dashboard of how studying trends over time)

> Size: L (borderline XL) · Depends on: M8 (review deck / SM-2 cards), M13 (study sets), M5/M6 (notes). Soft: M15 (quizzes) — the quiz write-point hook lands only once M15 persists attempts.

## Goal

Give each user a dedicated `/progress` page that shows **how their studying is trending over time** — not a single snapshot, but real over-time curves and accurate streaks. Three lenses:

- **Activity & consistency** — current streak, longest streak, active-days calendar/heatmap, reviews-per-day.
- **Mastery & performance** — quiz-score trend, flashcard retention (% good grades), average-ease trend, and "mastered cards" count.
- **Content & coverage** — notes created over time, study sets generated, totals by type, top tags/subjects.

This is **per-user only** (no admin/cohort analytics, no social/leaderboards).

## In scope

- An **immutable study-event log** appended on the existing study write-points (card review, quiz attempt, note created, study set created).
- A **dedicated `StudyEvents` DynamoDB table** with a stream, consumed by a **rollup aggregator** that maintains per-day snapshots; a **nightly cron** finalizes derived fields (streak, retention rate).
- **Lifetime counters + current streak** kept on the existing `UserProfile` item so the page header is a single read.
- A read API `GET /api/progress?range=<7d|30d|90d|365d>` and the `/progress` page with charts + headline stat cards, plus a nav entry point.
- Pure aggregation/streak/retention logic with unit tests; dynalite integration tests for every new access pattern.

## Out of scope

- Goals, weekly targets, achievement badges (future milestone).
- Admin / cohort / cross-user analytics; leaderboards or social comparison.
- Data export (CSV/PDF).
- **Backfill** of activity from before the event log exists — the dashboard accumulates from launch forward (called out as a known limitation; see Risks).

## Architecture & decisions

### Locked decisions

1. **Event-log → nightly rollup (not compute-on-read).** A compute-on-read query over current card state is cheaper but can only show a snapshot — it cannot produce true over-time trends or accurate streaks, which is the whole point. We use the immutable-event-log + daily-snapshot pattern, mirroring the M23 metering design so the codebase stays consistent.
2. **Dedicated `StudyEvents` table** (not the Notes single-table). Keeps append-only analytics writes and their stream consumer off the hot domain table; independent TTL and scaling; mirrors M23's dedicated `Usage` table.
3. **All four mastery metrics ship** in M25: quiz-score trend, retention rate, average-ease trend, mastered-cards count — all derivable from the captured events.

### `StudyEvents` table (new — `infra/db.ts`)

```typescript
export const studyEvents = new sst.aws.Dynamo("StudyEvents", {
  fields: { pk: "string", sk: "string" },
  primaryIndex: { hashKey: "pk", rangeKey: "sk" },
  stream: "new-and-old-images",
  ttl: "expiresAt",          // set only on raw EVENT# items; DAY# snapshots never expire
});
```

Linked from `infra/application.ts` (writers + read API) and `infra/jobs.ts` (stream consumer + cron). No GSI needed initially — every read is a single-partition `USER#<sub>` query; cross-user fan-out is explicitly out of scope.

Three item shapes share the table, all under `pk = USER#<sub>`:

- **Raw event item** — `sk = EVENT#<ISO-8601>#<ulid>`, append-only, never updated. Carries a `kind` (`REVIEW` | `QUIZATTEMPT` | `NOTE_CREATED` | `STUDYSET_CREATED`) plus kind-specific fields:
  - `REVIEW` — `grade`, `prevEase`/`newEase`, `prevIntervalDays`/`newIntervalDays`, `cardId`, `reviewedAt`.
  - `QUIZATTEMPT` — `quizId`, `score` (0–1), `durationMs`, `gradedAt`.
  - `NOTE_CREATED` — `noteId`, `tags`.
  - `STUDYSET_CREATED` — `studySetId`, `type` (`flashcards`|`quiz`|`assignment`|`summary`).
  - Carries `expiresAt` (raw events TTL after a retention window, e.g. 400 days — daily snapshots are the durable record).
- **Daily snapshot item** — `sk = DAY#<YYYY-MM-DD>` (user-local day; see Risks for timezone). Counters incremented by the stream consumer and finalized by the cron: `reviews`, `cardsReviewed`, `correctReviews`, `easeSum`/`easeCount`, `quizAttempts`, `quizScoreSum`, `notesCreated`, `studySetsCreated`, plus derived `retentionRate` and `avgQuizScore`. Never expires.
- **Cursor/meta item** (optional) — `sk = META#STREAK` mirrors lightweight rollup bookkeeping if needed; the canonical streak lives on the profile.

Key builders go in a new `progressKeys` object in `packages/core/src/db/keys.ts` (never inline `pk`/`sk` strings):

- `progressKeys.eventItem(sub, ts, id)` → raw event key.
- `progressKeys.dayItem(sub, date)` → snapshot key.
- `progressKeys.dayRangeQuery(sub, fromDate, toDate)` → `begins_with`/`BETWEEN` range over `DAY#` for the read API.
- `progressKeys.eventScanForDay(sub, date)` → range over `EVENT#<date>` (cron finalize / replay).

### Event capture (hot-path writers)

Append a `REVIEW` / `QUIZATTEMPT` / `NOTE_CREATED` / `STUDYSET_CREATED` event at each existing write-point. The write is **fire-and-additional**: a failed event append must never fail the underlying study action (wrap in try/catch, log, move on — the snapshot can be reconciled by the cron from raw events). Write-points (from the current code):

- **Card review** — `recordCardReview()` in `packages/core/src/db/cards.ts` (called from `app/api/cards/[cardId]/grade/route.ts`). The SM-2 update already has prev/new ease + interval in hand → emit `REVIEW`.
- **Quiz attempt** — the M15 attempt-persist function (`ATTEMPT#…` write). **M15 is not yet implemented**; M25.1 adds the `QUIZATTEMPT` event in the same change that lands M15's attempt write, or behind a thin helper M15 calls. If M15 is still unbuilt when M25 ships, this hook is stubbed and tracked, not faked.
- **Note created** — `putNote()` in `packages/core/src/db/notes.ts` → emit `NOTE_CREATED`.
- **Study set created** — `putStudySet()` (queued from `app/api/study/generate/route.ts`) → emit `STUDYSET_CREATED`.

### Rollup aggregator + cron (`infra/jobs.ts`)

- **`progressAggregator`** — a Lambda subscribed to the `StudyEvents` stream, filtered to `INSERT` of `EVENT#` items (SK prefix filter, exactly the M23 `subscribe(..., { filters })` pattern). For each event it `UpdateCommand`s the matching `DAY#` snapshot with atomic `ADD` increments (`reviews +1`, `correctReviews +grade≥good`, `easeSum +newEase`, `quizScoreSum +score`, …). Idempotency: keyed by event ulid where it matters; double-delivery tolerance documented.
- **Nightly finalize cron** — recomputes derived snapshot fields (`retentionRate = correctReviews/reviews`, `avgQuizScore = quizScoreSum/quizAttempts`), updates the profile **current streak / longest streak / lastStudyDay**, and can re-derive a day's snapshot from raw `EVENT#` items if the stream missed one (self-healing).

### Lifetime counters on `UserProfile` (`packages/core/src/auth/profile.ts`)

Additive attributes on the existing `PROFILE` item (M24's `aiProfile` precedent — no new table):
`studyStreakDays`, `longestStreakDays`, `lastStudyDay` (YYYY-MM-DD), `totalReviewsLifetime`, `totalCardsMastered`, `totalQuizAttemptsLifetime`. The header reads these in one `getUserProfileBySub()` call.

### Read API + page

- **`GET /api/progress?range=30d`** — authed (`getAuthenticatedSub()`), `runtime='nodejs'`, `dynamic='force-dynamic'`. One `dayRangeQuery` over `DAY#` snapshots + one profile read; returns `{ profile: {...lifetime/streak}, days: [{date, reviews, retentionRate, avgQuizScore, ...}], totals: {...} }`. Validates `range` against an allow-list (400 otherwise).
- **`/progress` page** — server component reads cookies/verifies ID token, renders `<AppShell>` + a client `<ProgressScreen>`. Charts via **`recharts`** (new dep on `packages/application`, per the M23 plan): activity heatmap/calendar, reviews-per-day bar, quiz-score line, ease/retention line; plus headline stat cards (streak, total reviews, mastered cards, avg score). Empty state for new users (no data yet) and loading skeletons. Add a nav entry point.

## Definition of Done (milestone)

- A user who reviews cards / takes quizzes / creates notes & study sets sees those reflected on `/progress` within a day (snapshot) and on the streak header.
- Streak, retention rate, average ease, mastered-cards count, and the activity calendar render correctly over a chosen range; range switch works.
- `npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run test:integration` all green; new access patterns covered by dynalite tests; the page has a real browser UI test.
- Event appends are fail-soft (never break the underlying study action); the cron self-heals a missed day.

## Risks / open questions

- **Timezone of "a day".** Streaks/heatmaps are user-perceived per local day. MVP: bucket by UTC day, or store the user's tz on the profile and bucket by it. Decide in M25.2; document the choice. (Leaning: store tz on profile, fall back to UTC.)
- **No historical backfill.** The dashboard starts empty and accumulates forward — pre-launch activity isn't shown. Surfaced in the empty state.
- **M15 dependency (soft).** Quiz-score trend needs M15's attempt persistence. If M15 hasn't landed, M25 ships with the quiz hook stubbed and the quiz-score chart shows an empty/"coming soon" state — the other three mastery metrics don't depend on it.
- **Stream double-delivery.** Atomic `ADD` increments are not naturally idempotent; rely on the nightly self-heal (re-derive from raw `EVENT#` items) as the correctness backstop, and document the at-least-once tolerance.
- **Raw-event growth.** TTL raw `EVENT#` items after a retention window (e.g. 400 days); `DAY#` snapshots are the durable record.
