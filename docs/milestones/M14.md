# M14 · AI flashcards → review deck

> Size: L · Depends on: M13, M8

## Goal

Let the user generate flashcard candidates from any note's Markdown body using Bedrock
Converse tool-use, review and refine them before committing, then push the accepted cards
directly into the existing M8 SM-2 review deck — identical `CARD#` items, same due-count
query, same flip-session UI. A provenance field (`origin: "ai"`) and a small badge + filter
on the Review overview complete the integration without polluting the deck with unreviewed
AI output.

## In scope

- Bedrock Converse tool-use generation: prompt → `{ front, back, sourceSpan? }[]` from a
  note's Markdown body (`bodyS3Key`), built on M13's `packages/core/src/study/generate.ts`
  wrapper; system prompt tuned for flashcard extraction.
- Review-before-accept UI: list generated cards, allow inline edit of `front`/`back`, discard
  individual cards, then accept the survivors.
- Persist accepted cards as `CARD#` items in the Notes table with SM-2 defaults and an
  `origin: "ai"` provenance field; extend `CARD` item shape and key builders accordingly.
- Auto-prune rule: AI cards (`origin: "ai"`) are **never** auto-deleted on highlight removal —
  only `origin: "highlight"` orphan cards (those with no `lastReviewedAt`) are pruned by the
  M8 diffing logic.
- Deck UI: provenance badge on each card in the Review overview and a 3-way filter
  (All / Highlights / AI).

## Out of scope

- Generating cards from multiple notes at once (batch generation).
- AI-assisted grading or answer evaluation.
- Editing already-accepted AI cards from the generation flow (use the existing card view).
- Automatic periodic re-generation when a note is updated.
- Customising the number of cards requested per generation run.
- Card deduplication across generation runs (re-running generates fresh candidates; user
  discards duplicates in the review-before-accept step).
- Algorithm changes to SM-2 or FSRS.

## Architecture & decisions

### CARD item shape extensions

Two new attributes are added to the existing `CARD#` item (fully backward-compatible — existing
`origin: "highlight"` cards omit these fields and the reader treats absence as `"highlight"`):

```
origin          string   "highlight" | "ai"    (default: "highlight" when absent)
studySetId?     string   ULID of the M13 StudySet that produced this card; present when
                         origin === "ai", absent otherwise
```

The `GSI3 ByDue` index definition and all existing key builders remain unchanged. No
DynamoDB migration is needed — new fields are invisible to existing queries.

**Auto-prune rule (clarification of M8 logic):** the M8 diff-on-save logic that deletes
removed-highlight orphan cards must check `origin !== "ai"` before deleting. AI cards have
no highlight to track, so they must be excluded from prune consideration entirely —
regardless of whether `lastReviewedAt` is set.

### Generation — M13's wrapper

M13 provides `packages/core/src/study/generate.ts`, a typed Converse tool-use wrapper:

```typescript
// Assumed interface from M13:
generate<T>(opts: {
  systemPrompt: string;
  userMessage: string;
  toolName: string;
  toolDescription: string;
  toolSchema: JSONSchema;
  modelId: string;
}): Promise<T>
```

M14 adds a thin flashcard-specific layer at
`packages/core/src/study/generateFlashcards.ts`:

```typescript
interface RawFlashcard {
  front: string;       // question or cloze phrase
  back: string;        // answer or full sentence context
  sourceSpan?: string; // optional verbatim excerpt from the Markdown body
}

export async function generateFlashcards(
  markdownBody: string,
  noteId: string,
): Promise<RawFlashcard[]>
```

**Tool-use JSON schema** passed to `generate()`:

```json
{
  "type": "object",
  "properties": {
    "cards": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["front", "back"],
        "properties": {
          "front":      { "type": "string", "maxLength": 300 },
          "back":       { "type": "string", "maxLength": 600 },
          "sourceSpan": { "type": "string", "maxLength": 300 }
        }
      },
      "minItems": 1,
      "maxItems": 20
    }
  },
  "required": ["cards"]
}
```

**System prompt** (English, stored as a constant in `generateFlashcards.ts` and exported for
unit tests):

> You are a spaced-repetition flashcard author. Given a Markdown study note, produce up to
> 20 high-quality flashcard pairs. Rules: (1) Each `front` is a concise question or cloze
> phrase (≤ 300 chars). (2) Each `back` is the correct answer, with brief context if helpful
> (≤ 600 chars). (3) Focus on testable facts, vocabulary, and key concepts — not trivia or
> meta-commentary about the note. (4) If the note contains `==highlighted==` terms, each
> highlight MUST become at least one card. (5) Output only via the tool call — no prose.

**`inferenceConfig.maxTokens`**: 2048 (flashcards are short; 4096 is wasteful here).

Bedrock is called with `withBedrockRetry` (from `packages/core/src/ocr/retry.ts`, reused as-is)
and `Resource.BEDROCK_MODEL_ID.value` (same secret as OCR; no new secret required).

### Generation route

Reuse M13's `POST /api/study/generate` route, adding `type: "flashcards"` to the request
discriminant. M13 already dispatches on `type`; M14 adds a `"flashcards"` branch:

```
POST /api/study/generate
Body: { noteId: string; type: "flashcards" }
Response: { studySetId: string; cards: RawFlashcard[] }
```

The route:
1. Verifies ownership of `noteId` (reads the Note item; asserts `PK === USER#<sub>`).
2. Fetches the note's Markdown body from S3 via `bodyS3Key`.
3. Calls `generateFlashcards(markdownBody, noteId)`.
4. Creates a `STUDYSET#<ulid>` item (M13 data model) with `type: "flashcards"`,
   `status: "done"`, and a `cards` attribute holding the `RawFlashcard[]` as JSON.
5. Returns `{ studySetId, cards }`.

Auth: `proxy.ts` middleware (JWT verified). Returns 403 for non-owner `noteId`.

### Accept route

```
POST /api/study/[studySetId]/accept-cards
Body: { accepted: { front: string; back: string }[] }
Response: { created: number }
```

The route:
1. Looks up the `STUDYSET#<studySetId>` item; asserts `sub` ownership.
2. For each entry in `accepted`: generates a ULID `cardId`, writes a `CARD#<cardId>` item
   with:
   - All standard M8 fields: `cardId`, `sourceNoteId` (from the StudySet), `front`, `back`,
     `ease: 2.5`, `interval: 1`, `dueAt: now` (due immediately), `createdAt`, `updatedAt`.
   - New fields: `origin: "ai"`, `studySetId`.
   - GSI3 keys: `GSI3PK = USER#<sub>`, `GSI3SK = DUE#<now ISO>` (due immediately, same as
     highlight cards seeded with `dueAt = createdAt`).
3. Writes all cards via `BatchWriteItem` (up to 20 items — within the 25-item batch limit).
4. Returns `{ created: N }`.

Cards are written to the Notes table (same table as all `CARD#` items from M8).

### Key builder additions

Add to `packages/core/src/db/keys.ts` (Notes table section):

```typescript
// No new index needed — AI cards reuse GSI3 ByDue and the base-table
// cardsByNoteQuery (filtered by PK + SK begins_with CARD#).
// cardItemKey, cardsByDueQuery, cardsByNoteQuery from M8 are unchanged.
```

No new GSI. No new table. No new `sst.Secret`.

### Infra changes

None beyond what M8 already provisioned. The Notes table with `ByDue` GSI3 is already
defined; `BatchWriteItem` on that table is already IAM-permitted from M8
(`dynamodb:BatchWriteItem` on the Notes table ARN must be confirmed present in
`infra/application.ts` — add if absent, no-op if already there).

## Sub-issues (granular tasks)

1. **(M) Flashcard generation: `generateFlashcards.ts` + unit tests**

   Implement `packages/core/src/study/generateFlashcards.ts` per the spec above. The module
   calls M13's `generate()` wrapper with the flashcard tool schema and system prompt. Reads the
   model id from `Resource.BEDROCK_MODEL_ID.value`; throws loudly if unset. Unit-test in
   `packages/core/test/generateFlashcards.unit.test.ts` with `vi.mock` on
   `packages/core/src/study/generate.ts`:
   - Happy path: mocked `generate()` returns 3 cards → `generateFlashcards` returns them
     unchanged.
   - System prompt exported constant contains the five rules verbatim.
   - Tool schema enforces `minItems: 1`, `maxItems: 20`, and both `front` and `back` as
     required strings.
   - `inferenceConfig.maxTokens` is asserted to be `2048` (not 4096).
   - Empty `cards` array from the model throws a structured error (not a silent empty return).
   - `withBedrockRetry` is called: a `ThrottlingException` on the first attempt is retried.

   Route addition: add a `"flashcards"` branch to the existing M13
   `POST /api/study/generate` route handler. The branch:
   - Reads and validates `noteId` from the request body (`zod`).
   - Fetches the Note item (ownership check) and its `bodyS3Key` content from S3.
   - Calls `generateFlashcards(markdownBody, noteId)`.
   - Creates the `STUDYSET#` item with `type: "flashcards"` and `status: "done"`.
   - Returns `{ studySetId, cards: RawFlashcard[] }`.

   Acceptance criteria:
   - `npm run test:unit` green; ≥ 6 unit test cases on `generateFlashcards.ts`.
   - `POST /api/study/generate` with `{ noteId, type: "flashcards" }` and a valid JWT
     returns `{ studySetId, cards }` (tested with mocked Bedrock in a unit test on the route
     handler).
   - Returns 403 for a `noteId` owned by a different user.
   - Returns 404 if `noteId` does not exist.
   - Throws (500) rather than returning an empty array when the model returns no cards.
   - No inline model id or system prompt strings outside of `generateFlashcards.ts`.

2. **(M) Review-before-accept UI**

   New page: `packages/application/app/(authed)/notes/[noteId]/generate-cards/page.tsx`.

   Flow:
   1. On mount, `POST /api/study/generate` with `{ noteId, type: "flashcards" }`. Show a
      loading skeleton (same `StateProcessing` motif from M4 — "Generating flashcards…").
   2. Render the returned `cards` as an editable list:
      - Each card shows `front` (top, Newsreader serif) and `back` (below, smaller) inside a
        DS card surface.
      - Inline-edit: tapping either field opens a `<textarea>` replacing the display text;
        blur commits the edit to local state.
      - Discard button (trash icon, danger ghost) removes the card from the local list with
        a subtle exit animation.
      - A "0 of N cards remaining" counter updates as cards are discarded.
   3. "Accept N cards" primary CTA: disabled when 0 cards remain. Calls
      `POST /api/study/[studySetId]/accept-cards` with the current (possibly edited) list.
   4. On success: toast "N cards added to your review deck" + navigate back to NoteView.
   5. "Cancel" ghost CTA discards all and navigates back to NoteView (no API call).

   Entry point: add an "AI flashcards" button to the NoteView action bar (alongside the
   existing "Add to review deck" button). Tapping navigates to
   `/notes/[noteId]/generate-cards`.

   Acceptance criteria:
   - Loading state shows while `POST /api/study/generate` is in flight; error state shown if
     the API returns non-2xx (with a "Try again" retry CTA).
   - Cards render with correct front/back; inline-edit changes persist in local state.
   - Discarding all cards disables the "Accept" CTA.
   - "Accept N cards" calls `POST /api/study/[studySetId]/accept-cards` with exactly the
     remaining (and possibly edited) card objects.
   - Toast and navigation fire on success.
   - Browser UI test: render the page with mocked API responses; assert edit, discard, and
     accept flows produce the correct API calls and UI transitions.

## Risks / open questions

- **M13 interface stability.** M14 calls M13's `generate()` wrapper directly. If M13's
  function signature changes during implementation, `generateFlashcards.ts` needs updating.
  Mitigation: lock the `generate()` interface as a formal TypeScript `export type` in M13 so
  callers fail at compile time rather than runtime if it drifts.
- **Model quality variance.** Bedrock may return fewer than the requested number of cards, or
  cards that are duplicates of existing `CARD#` items in the deck. For M14, this is acceptable
  UX — the review-before-accept step lets the user discard low-quality or duplicate output.
  A future iteration could add a deduplication pass against `cardsByNoteQuery` results.
- **`BatchWriteItem` limit.** The accept route allows up to 20 cards, which is within the
  DynamoDB `BatchWriteItem` 25-item cap. If the cap is ever raised above 20 cards per
  generation, switch to multiple batches or a `TransactWriteItems` with conditional checks.
  Document the 20-card cap as a known limit in the route handler.
- **S3 fetch latency in the generation route.** Fetching the full note body from S3 adds
  100–400 ms to the generation request. For M14 this is acceptable (the user is waiting for
  a Bedrock call anyway); if note bodies become large, consider caching the body in the Note
  DynamoDB item up to a size threshold.
- **Review-before-accept UX on mobile.** Inline editing of `front`/`back` fields via a
  `<textarea>` requires a reliable tap target on a phone. Test on a 375 px viewport; if the
  textarea is too cramped, switch to a full-screen edit modal per card.
- **`origin` field absent on pre-M14 cards.** The `ByDue` query may return cards written
  before M14 that have no `origin` field. The deck filter must treat `origin === undefined`
  as `"highlight"` (the pre-M14 default). Codify this as a type guard in the filter logic and
  in a unit test.

## Manual test plan

Test on the deployed `pr-<N>` stage:

1. **Generate flashcards from a note.** Open a note that has Markdown content (ideally with
   several `==highlighted==` terms). Tap the "AI flashcards" button in the NoteView action
   bar. Expected: the generate-cards page loads and shows a "Generating flashcards…" spinner
   while the Bedrock call is in flight.

2. **Review generated cards.** After generation completes. Expected: a list of up to 20 cards
   each showing a `front` and `back`. Every `==highlighted==` term in the note appears as at
   least one card's `front`.

3. **Inline edit a card.** Tap the `front` field of any card. Expected: a `<textarea>`
   appears with the current text; editing it and blurring commits the change; the updated text
   shows in the display.

4. **Discard a card.** Tap the trash icon on one card. Expected: the card exits with an
   animation; the "N cards remaining" counter decrements; "Accept N cards" CTA title updates.
   Discard all cards. Expected: "Accept 0 cards" CTA is disabled.

5. **Accept cards.** With at least one card remaining, tap "Accept N cards". Expected: a
   toast confirms "N cards added to your review deck"; the page navigates back to NoteView.

6. **Cards appear in Review tab.** Navigate to the Review tab. Expected: the due-card count
   has increased by N; the note appears in the grouped overview. Starting a review session
   shows the accepted AI cards; card flip and grade buttons work identically to highlight
   cards.

7. **AI provenance badge.** In the Review overview. Expected: the note-group entry for the
   note whose AI cards were just accepted shows an "AI" badge. A note-group with only
   highlight-origin cards shows no such badge.

8. **3-way filter — AI only.** Select "AI" in the SegmentedControl. Expected: only cards with
   `origin: "ai"` appear in the session; highlight-origin cards are hidden. Switch to
   "Highlights". Expected: only `origin: "highlight"` cards appear. Switch to "All". Expected:
   both kinds appear. Reload the page. Expected: the last selected filter is still active.

9. **Auto-prune does not affect AI cards.** Edit the note whose AI cards were accepted;
   remove or add `==highlights==` and save. Navigate to Review tab. Expected: the AI cards
   are still present in the deck, unchanged.

10. **Error / retry.** On a dev stage, temporarily set `BEDROCK_MODEL_ID` to an invalid value
    (or simulate a 500 from the generate route). Tap "AI flashcards" on a note. Expected: an
    error state appears on the generate-cards page with a "Try again" CTA; no unhandled
    exception or blank screen.
