# M18 · Audio for flashcards & notes (Brazilian-Portuguese TTS)

> Size: L · Depends on: M8, M13, M14

## Goal

Give users the ability to **hear** their Brazilian-Portuguese flashcards and study content.
Pronunciation practice is central to language acquisition; reading alone is not enough.
Amazon Polly (neural engine, pt-BR voices) synthesises MP3 audio on demand for any card
front/back or written study text. Audio is cached by content hash in S3 so identical text
is never re-synthesised — Polly charges per character. A play button appears in the M8
`/review` card-flip session and in the study-material viewers introduced by M13/M16.

## In scope

- `packages/core/src/tts/polly.ts` — Polly client wrapper (`synthesizeSpeech` → `Uint8Array`
  MP3 bytes), `packages/core/src/tts/retry.ts` — `withPollyRetry` (same interface as
  `withBedrockRetry`), `packages/core/src/tts/hash.ts` — content-hash helper
  (`sha256(text + voiceId + engine)` → hex string).
- Audio pointer item in the `UserData` table: `SK=AUDIO#<hash>`, holding the S3 key, voice,
  char count, and timestamps. Key builders in `packages/core/src/db/keys.ts`.
- Dynalite integration test for the audio pointer write→read round-trip.
- S3 storage key `audio/users/<sub>/<hash>.mp3` in `storageKeys` (extending `keys.ts`).
- IAM additions in `infra/application.ts`: `polly:SynthesizeSpeech` scoped to the pt-BR
  neural engine ARN; `s3:PutObject` + `s3:GetObject` extended to include the `audio/users/*`
  prefix on the existing `NotesBucket`.
- `POST /api/audio/synthesize` — owner-authenticated, returns a playable URL for the cached
  or newly synthesised MP3. Enforces per-user rate and length caps.
- `POLLY_VOICE_ID` and `POLLY_ENGINE` as `sst.Secret` entries — fail loud if unset; default
  values seeded in both Console environments.
- Optional SSML `<prosody rate>` wrapping, configurable per-request.
- Play button (▶) in the M8 `/review` card-flip session on the card front and back.
- Play button in the study-material text viewers introduced by M13/M16.
- `<audio>` element fed the synth endpoint URL; loading spinner on first synthesis; instant
  play on cache hit.
- Voice selection surface (default voice shown; user can swap to Vitória or Thiago).
- Unit tests for the Polly wrapper (mocked client), hash helper, and SSML builder.
- Playwright E2E: sign in → open a review card → tap ▶ → audio element plays (mock endpoint).

## Out of scope

- Non-pt-BR languages (no `en-US` or `es-ES` voice selection in M18).
- Full offline audio caching / service-worker prefetch.
- Download / export of synthesised MP3 files.
- Background pre-synthesis of the full deck (lazy on-demand only in M18).
- Audio for marketing pages.
- Pronunciation scoring or speech-recognition feedback.
- Batch synthesis jobs.

## Architecture & decisions

### Polly voice & engine configuration

Voice id and engine are **not hardcoded**. Two `sst.Secret` entries in `infra/secrets.ts`:

```ts
export const pollyVoiceId = new sst.Secret("POLLY_VOICE_ID");
export const pollyEngine  = new sst.Secret("POLLY_ENGINE");
```

Seed in both Console environments:

```bash
npx sst secret set POLLY_VOICE_ID Camila --stage production
npx sst secret set POLLY_ENGINE   neural --stage production
npx sst secret set POLLY_VOICE_ID Camila   # fallback (pr-<N>)
npx sst secret set POLLY_ENGINE   neural   # fallback
```

Available pt-BR neural voices: `Camila` (female, default), `Vitória` (female, alternative),
`Thiago` (male). All three support `Engine: "neural"` and `LanguageCode: "pt-BR"`.

Read server-side and fail loudly on startup (matching the `BEDROCK_MODEL_ID` pattern in
`packages/core/src/ocr/bedrock.ts`):

```ts
const voiceId = process.env.SST_RESOURCE_POLLY_VOICE_ID_value;
const engine  = process.env.SST_RESOURCE_POLLY_ENGINE_value;
if (!voiceId) throw new Error("POLLY_VOICE_ID is not set");
if (!engine)  throw new Error("POLLY_ENGINE is not set");
```

### Polly client wrapper — `packages/core/src/tts/polly.ts`

Mirrors the shape of `packages/core/src/ocr/bedrock.ts`.

```ts
import { PollyClient, SynthesizeSpeechCommand } from "@aws-sdk/client-polly";
import { withPollyRetry } from "./retry.js";

export interface PollyResult {
  audioBytes: Uint8Array;
  charCount: number;
}

const client = new PollyClient({});

export async function synthesizeSpeech(
  text: string,
  voiceId: string,
  engine: string,
  ssmlRate?: string,          // e.g. "slow" | "medium" | "fast" — passed as SSML <prosody rate>
): Promise<PollyResult>
```

- `TextType`: `"ssml"` when `ssmlRate` is provided (wraps text in
  `<speak><prosody rate="${ssmlRate}">${text}</prosody></speak>`), `"text"` otherwise.
- `OutputFormat: "mp3"`, `Engine: engine`, `LanguageCode: "pt-BR"`, `VoiceId: voiceId`.
- Call wrapped in `withPollyRetry` (same transient-error detection as `withBedrockRetry`).
- Returns `{ audioBytes, charCount: text.length }`.

### Retry helper — `packages/core/src/tts/retry.ts`

Identical interface to `packages/core/src/ocr/retry.ts`. Detects
`ThrottlingException` and `$metadata.httpStatusCode >= 500`; exponential back-off
`200 * 2^attempt` ms; `maxAttempts: 3`. Unit-testable with `baseDelayMs: 0`.

### Content-hash helper — `packages/core/src/tts/hash.ts`

```ts
import { createHash } from "node:crypto";

/**
 * Canonical cache key for a TTS synthesis request.
 * hash = sha256(text + "|" + voiceId + "|" + engine + "|" + (ssmlRate ?? ""))
 * Returns lowercase hex.
 */
export function audioHash(
  text: string,
  voiceId: string,
  engine: string,
  ssmlRate?: string,
): string
```

The separator `|` prevents collisions between concatenated values.

### Audio pointer item — `UserData` table

Rather than a pure S3-head-object existence check (which requires an extra SDK round-trip and
can be racy), a lightweight DynamoDB pointer item is written once and consulted on every
subsequent request. This keeps cache lookups within the existing `ddb` client path and enables
future per-user audio analytics (char count totalling for cost tracking).

Item shape (stored in the `UserData` table alongside CARD items):

```
PK        = USER#<sub>
SK        = AUDIO#<hash>             # hash = audioHash(text, voiceId, engine, ssmlRate)
attrs:
  hash         string   # the content hash (redundant, but convenient for reads)
  s3Key        string   # audio/users/<sub>/<hash>.mp3
  voiceId      string   # e.g. "Camila"
  engine       string   # e.g. "neural"
  charCount    number   # text.length at synthesis time
  ssmlRate?    string   # present only if SSML prosody was applied
  createdAt    string   # ISO-8601 UTC
```

No GSI — audio pointers are always fetched by PK + full SK (`USER#<sub>` + `AUDIO#<hash>`),
which is a point-get, not a scan.

#### Key builders (add to `packages/core/src/db/keys.ts`)

```ts
/** Audio pointer item: cached TTS result for a user + content hash. */
export const audioKeys = {
  pointer: (sub: string, hash: string) => ({
    pk: `USER#${sub}`,
    sk: `AUDIO#${hash}`,
  }),
};
```

### Route handler — `POST /api/audio/synthesize`

File: `packages/application/app/api/audio/synthesize/route.ts`

Auth: `proxy.ts` middleware (JWT-verified). Extracts `sub` via `getAuthenticatedSub()`.

Request body:

```ts
{
  text:       string,     // required; max 1 000 chars after strip
  voiceId?:   string,     // optional override; must be one of the allowed set
  ssmlRate?:  string,     // optional; "slow" | "medium" | "fast"
}
```

Logic:

1. Validate: `text` present and `text.length <= 1000`; `voiceId` (if supplied) is one of
   `["Camila", "Vitória", "Thiago"]`; `ssmlRate` (if supplied) is one of
   `["slow", "medium", "fast"]`. Return 400 on validation failure.
2. Rate guard: query DynamoDB for the count of `AUDIO#` pointer items this user has created
   today (ISO date prefix on `createdAt`). If `charCount` sum for today exceeds
   **50 000 characters**, return 429 with `{ error: "daily_limit_reached" }`.
3. Compute `hash = audioHash(text, effectiveVoiceId, engine, ssmlRate)` where
   `effectiveVoiceId` = supplied `voiceId` ?? `POLLY_VOICE_ID` secret.
4. Point-get `audioKeys.pointer(sub, hash)` from `UserData`. If found, skip to step 6.
5. Call `synthesizeSpeech(text, effectiveVoiceId, engine, ssmlRate)`.
   PutObject the returned `audioBytes` to `storageKeys.audioMp3(sub, hash)`.
   Write a new `audioKeys.pointer` item to `UserData`.
6. Generate a presigned `GetObject` URL for `storageKeys.audioMp3(sub, hash)` (TTL 15 min).
7. Return `{ url, cached: boolean, charCount: number }`.

Response shape:

```json
{ "url": "https://...", "cached": true, "charCount": 42 }
```

### Play button UI

#### In the M8 `/review` card-flip session

The play button mounts **next to the card text** on both the front state and the back state
of the card-flip view described in M8's "Review session — card flip view" section:

- Front state: a circular `▶` icon button (`lucide-react` `Volume2` icon, 20 px) in the top-
  right corner of the card surface, vertically centred with the `card.front` text.
- Back state: a second `▶` button above `card.back`, mirroring the front placement.
- On tap: call `POST /api/audio/synthesize` with `{ text: card.front }` (or `card.back`).
  While the request is in flight, replace `▶` with a spinner (`Loader2`, animated). On
  success, create or reuse a hidden `<audio>` element and call `.play()`. On error, show a
  brief toast ("Audio unavailable").
- **Cache hit** (server returns `cached: true`): no visible loading state — the presigned URL
  is returned immediately; the `<audio>` element begins playing at once.
- **First synthesis**: spinner for the Polly round-trip (typically < 1 s for short card text).

The `<audio>` element is rendered once per session (`useRef`) and its `src` is swapped on
each play call. Autoplay is gated on a prior user gesture (the play button tap itself).

#### In study-material viewers (M13/M16)

A `<PlayButton>` component (`packages/application/components/tts/PlayButton.tsx`) accepts
`text: string` and `label?: string`. Renders the same `Volume2` icon button with identical
loading/error states. Placed at the top of each study-material card or paragraph block, so the
user can hear the entire front of a study card or a pt-BR example sentence.

### Voice selection

A small `<VoiceSelector>` component (a three-button radio group: Camila / Vitória / Thiago)
lives in the account settings page (or as a compact inline control in the review session
header). The selected voice is stored in `localStorage` under `tts.voiceId` (not in
DynamoDB — voice preference is a cosmetic device setting). The `POST /api/audio/synthesize`
call passes the locally stored `voiceId` in the request body.

### Cost guardrails

| Guard | Value | Enforcement |
|---|---|---|
| Max text length per request | 1 000 chars | Route handler: 400 if exceeded |
| Daily character cap per user | 50 000 chars | Route handler: 429 if exceeded |
| Max `ssmlRate` values | 3 allowed strings | Route handler: 400 otherwise |

The daily cap is approximated from the `AUDIO#` pointer items written today for the user
(summing `charCount`). This is eventually consistent — if two concurrent requests race through
before either pointer is written, the cap can be exceeded by at most one request. Accepted for
M18; an atomic counter (DynamoDB `ADD` on a daily aggregate item) can tighten this later.

## Risks / open questions

- **Polly IAM resource ARN**: Polly's `SynthesizeSpeech` action does not support per-voice
  or per-language ARN conditions in the `Resource` field — the minimal valid resource is `*`
  or a lexicon ARN. Add a condition key (`polly:LanguageCode: "pt-BR"`) as a compensating
  control and document why the resource is wider than the S3 and Bedrock grants.
- **Neural voice availability by region**: Polly neural voices for pt-BR (`Camila`, `Vitória`,
  `Thiago`) must be confirmed available in `us-east-1`. Verify with
  `aws polly describe-voices --engine neural --language-code pt-BR --region us-east-1` before
  seeding the secret; a wrong voice id returns a Polly 400 that surfaces as a hard error.
- **`OutputFormat: "mp3"` and browser compatibility**: `<audio>` MP3 playback is supported by
  all major browsers. Safari on iOS requires a user-gesture gate before `.play()` — the
  play-button tap is that gesture. Do not call `.play()` programmatically on page load.
- **Presigned URL TTL and S3 CORS**: the presigned `GetObject` URL (15 min TTL) is fetched
  client-side by the `<audio>` element. The `NotesBucket` CORS config (`infra/storage.ts`)
  currently allows only `PUT` and `GET` from the app origin. Confirm `GET` from the
  `<audio>` src is treated as a same-origin or CORS request by the browser and that the
  CORS `allowMethods: ["PUT", "GET"]` already covers it; if not, add `HEAD`.
- **Daily cap race condition**: two simultaneous synthesize calls for the same user can both
  pass the cap check before either pointer is written. The cap can be exceeded by one
  request. Accepted for M18 — the worst-case overage is a single extra call (~1 000 chars).
  A future hardening pass can use a DynamoDB atomic counter (`UpdateItem ADD`) on a daily
  aggregate item.
- **Cache pointer vs. S3 head-object**: the spec chooses a DynamoDB pointer item over a pure
  S3 `HeadObject` check. Rationale: avoids a cross-service round-trip for every cache miss
  check, enables `charCount` aggregation for the daily cap, and stays within the existing
  `ddb` client path. The trade-off is one extra DynamoDB write on first synthesis and one
  extra DynamoDB read on every request; at typical card-text lengths this is negligible.
- **SSML injection**: if `text` originates from user-created card content, a malicious user
  could embed SSML tags to manipulate synthesis. When `ssmlRate` is present and `TextType`
  is `"ssml"`, the `text` value must be XML-escaped (replace `<`, `>`, `&`, `"`, `'`)
  before interpolation into the `<prosody>` wrapper. Add this escaping to `polly.ts` and
  assert it in unit tests.
- **Card text length distribution**: M8 card fronts are typically 1–10 words (from
  `==highlight==` spans); card backs are up to 2 sentences. Both are well under the 1 000-char
  cap. Study-material viewers (M13/M16) may surface longer blocks — callers should truncate
  or split before passing to the play button.
