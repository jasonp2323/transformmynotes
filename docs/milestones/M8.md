# M8 · Review deck / spaced repetition

> Size: L · Depends on: M6

## Goal

Turn the `== highlighted ==` spans in a user's Markdown notes into a personal spaced-
repetition review deck. Every time a note is saved with highlights, the system extracts
them as `CARD` items and seeds them into the deck. An SM-2-style scheduler (ease
factor, interval, due-at timestamp) lives as pure TypeScript logic, fully unit-tested.
The "N cards ready to review" greeting count on the library home (stubbed at 0 in M6)
becomes live. A dedicated Review tab/deck UI lets the user step through due cards one
at a time, grade themselves, and watch the deck shrink.

## In scope

- `CARD` item data model in the Notes table (same single table, existing SST stage).
- SM-2-style scheduling algorithm as pure logic in
  `packages/core/src/srs/scheduler.ts` — no DynamoDB dependency, fully unit-tested.
- Card extraction from highlights on note save/update (parse `==…==` spans from the
  Markdown body).
- Due-count query: count cards where `dueAt <= now` for the calling user; feeds the
  greeting line and the Review tab badge.
- Review deck UI: a "Review" tab on the bottom nav that shows the card queue, a card-
  flip session (front → tap to reveal back → grade buttons), and a "deck empty" end
  state.
- "Add to review deck" button on the NoteView action bar (wired from M6's stub).
- Greeting line on the library home updated to show the live due-card count.
- Key builders + dynalite integration tests for all new card access patterns.
- Playwright E2E: save a note with highlights → cards appear in Review tab → grade a
  card → it disappears from the due queue.

## Out of scope

- Leitner-box or FSRS algorithm variants (SM-2 only in M8; algorithm is swappable
  later).
- Audio cards / image cards (text front/back only).
- Shared review decks (cards are always private to the card owner).
- Streak tracking, gamification, or progress charts.
- Offline review (cards require an API call to persist grades; offline support is
  future).
- Manual card creation outside of highlight extraction.
- Bulk-edit / reorder cards.
- Card export (Anki, CSV).

## Architecture & decisions

### Card data model

`CARD` items live in the Notes table alongside note metadata and token index items.
Using the same table keeps note-save and card-upsert in a single `TransactWrite`.

#### Item shape

```
PK            = USER#<sub>
SK            = CARD#<cardId>          # cardId = ULID generated at extraction time
GSI3-PK       = USER#<sub>
GSI3-SK       = DUE#<dueAt>           # ISO-8601 UTC, zero-padded to second precision
attrs:
  cardId           string   (ULID)
  sourceNoteId     string
  front            string   # the highlighted phrase (plain text, stripped of == marks)
  back             string   # the sentence context: up to 2 sentences surrounding the highlight
  ease             number   # SM-2 ease factor, default 2.5
  interval         number   # days until next review, default 1
  dueAt            string   # ISO-8601 UTC, next review datetime
  lastReviewedAt   string?  # ISO-8601 UTC
  createdAt        string   # ISO-8601 UTC
  updatedAt        string   # ISO-8601 UTC
```

#### GSI definition (`infra/db.ts`)

| GSI | PK | SK | Purpose |
|-----|----|----|---------|
| `ByDue` | `USER#<sub>` (GSI3-PK) | `DUE#<ISO-8601>` (GSI3-SK) | Query cards due for review; ranged scan for `dueAt <= now` |

The sort key `DUE#<ISO-8601>` is lexicographically sortable. A `ScanIndexForward:
true` scan up to the current timestamp returns all due cards in chronological order
(oldest-due first, so the most overdue cards are worked first).

Key builders to add to `packages/core/src/db/keys.ts`:

```typescript
cardItemKey(userSub: string, cardId: string): PrimaryKey
cardsByDueQuery(userSub: string, beforeOrAt: string): QueryInput
  // GSI3, SK from DUE#0000-... to DUE#<beforeOrAt>, ScanIndexForward true, limit 100
cardsByNoteQuery(userSub: string, noteId: string): QueryInput
  // base table PK=USER#<sub>, SK begins_with CARD# + FilterExpression sourceNoteId=noteId
  // (no GSI needed; per-note card count is small)
```

### SM-2 scheduler — pure logic

File: `packages/core/src/srs/scheduler.ts`

Implements the SM-2 algorithm. All inputs/outputs are plain objects — no I/O, no
DynamoDB dependency, fully unit-testable.

```typescript
type Grade = 0 | 1 | 2 | 3 | 4 | 5;   // 0–2 = failed, 3–5 = passed (SM-2 convention)

interface CardState {
  ease: number;        // EF, starts at 2.5
  interval: number;   // days, starts at 1
  dueAt: string;       // ISO-8601 UTC
}

interface ScheduleResult extends CardState {
  lastReviewedAt: string;
}

function schedule(current: CardState, grade: Grade, now?: Date): ScheduleResult
```

Algorithm (SM-2):
- If grade < 3 (failed): reset interval to 1, keep ease, due = now + 1 day.
- If grade >= 3 (passed):
  - New interval: if `interval === 1` → 6; if `interval === 6` → 21; else
    `Math.round(interval * ease)`.
  - New ease: `ease + (0.1 - (5 - grade) * (0.08 + (5 - grade) * 0.02))`.
  - Clamp ease to minimum 1.3.
  - `dueAt` = `now + newInterval days`.
- Returns `{ ease, interval, dueAt, lastReviewedAt: now.toISOString() }`.

The `now` parameter defaults to `new Date()` but is injectable for deterministic tests.

Unit test coverage targets:
- Grade 5 (perfect): ease increases, interval multiplies correctly.
- Grade 3 (barely passed): small ease increase, interval advances.
- Grade 0 (failed): interval resets to 1, ease unchanged (SM-2 preserves ease on
  failure — only grade affects ease when passing).
- Minimum ease clamp: repeated grade-3 responses eventually clamp at 1.3.
- Deterministic output for a seeded sequence of grades.

### Card extraction from highlights

Pure function: `packages/core/src/srs/extract.ts`

```typescript
function extractCards(noteId: string, markdownBody: string): RawCard[]
// RawCard = { front: string, back: string }
```

Algorithm:
1. Split `markdownBody` on newlines into paragraphs.
2. For each paragraph, find all `==…==` matches (regex: `/==(.+?)==/g`).
3. For each match:
   - `front` = the matched text (stripped of `==` markers).
   - `back` = the containing sentence context — up to 2 sentences surrounding the
     match (split on `. ` and `! ` and `? `), with `==…==` markers stripped.
4. Skip matches where `front.length < 2` or `front.length > 200` (noise guard).
5. Return `RawCard[]`.

This is a pure function — unit-tested independently of DynamoDB.

On note save/update (existing M5 route handler), call `extractCards`, diff against
existing cards for this note (`cardsByNoteQuery`), and:
- For new highlights: `PutItem` a new `CARD` with `dueAt = createdAt` (due immediately).
- For removed highlights: `DeleteItem` the card (only if `lastReviewedAt` is absent —
  an already-reviewed card is never auto-deleted; only newly unreviewed orphan cards are
  pruned).
- For existing unchanged highlights: no-op.

Diffing strategy: match by `front` string equality. If the same text exists, it is the
"same" card; if the front changed, it is treated as delete old + create new.

### Due-count query

`GET /api/cards/due-count` — returns `{ count: number }` for the calling user. Queries
`ByDue` GSI with `SK <= DUE#<now ISO>`, `Select: COUNT`. Used by:
- The library greeting line (client-side fetch on mount, 60 s cache).
- The Review tab badge.

For performance, the count query uses `Select: COUNT` (no item data transferred).

### Review session flow

`GET /api/cards/due` — queries `ByDue` GSI, returns up to 20 due cards (oldest-due
first). Client loads the session from this endpoint.

`PATCH /api/cards/[cardId]/grade` — accepts `{ grade: Grade }`. Calls `schedule()`,
writes the updated `ease`, `interval`, `dueAt`, `lastReviewedAt` back to DynamoDB.
Returns the updated `CardState`.

The session is client-managed: the React component holds the 20-card list in local
state, pops one card at a time, sends the grade, and moves to the next. After all 20
cards are graded, it re-fetches to check for more due cards. If none remain, shows the
"Deck empty" state.

### Review tab / deck UI

The Review tab (`/review`) is reached via the bottom nav (`layers` icon). Design is
derived from DS primitives (not a separate design screen file); matches the warm-paper
aesthetic.

#### Review tab — card list view (deck overview)

Shows the due-card count and a "Start review" button. Also lists notes with cards due
(grouped by `sourceNoteId`), each showing the note title and card count.

#### Review session — card flip view

Full-screen card view (fills the phone frame above the action bar):
- **Front state**: displays `card.front` in Newsreader serif, large (28px+). A "Tap to
  reveal" hint in muted mono at the bottom. A subtle gradient accent bar across the top
  (DS card motif).
- **Back state** (after tap): shows `card.back` below the front, separated by a
  hairline. Grade buttons appear: "Again" (grade 0), "Hard" (grade 2), "Good" (grade
  3), "Easy" (grade 5) — arranged as a 4-button row in pill shape, using DS Button
  variants (danger ghost, warning ghost, secondary, primary).
- Progress indicator: "Card N of M" in mono above the card.
- Exit button (chevron-left) in the nav bar returns to the deck overview.

#### Deck empty state

After all due cards are graded, show a success state with the check-circle icon and
copy: "All caught up — check back tomorrow." (DS `StateSuccess` motif adapted.)

### "Add to review deck" button

The NoteView action bar button (stubbed in M6) is now wired: tapping it extracts cards
from the current note's highlights and upserts them via a direct call to
`POST /api/notes/[noteId]/cards/refresh` (forces re-extraction + upsert for the note).
If no highlights exist, a toast explains: "Add == highlight == marks to your note to
create review cards."

### Infra changes

- `infra/db.ts`: add `ByDue` GSI to the Notes table definition.
- `infra/application.ts`: add `dynamodb:Query` IAM permission for the `ByDue` GSI ARN.
- No new `sst.Secret` entries required.

## Risks / open questions

- **Highlight diff false positives.** Diffing by `front` string equality means that if
  the user changes the wording of a highlight (e.g. "hable" → "hables"), the old card
  is deleted and a new one is created, losing any review history on the old card.
  Accepted for M8; a future "fuzzy match" diff strategy can preserve history.
- **TransactWrite size limit.** A note with many highlights (>25) will exceed the 25-
  item `TransactWrite` limit if combined with the note metadata write and token index
  writes. Mitigation: write cards in a separate batch (`BatchWriteItem`) after the
  main transaction commits. Document this two-phase write and test with a 30-highlight
  note.
- **`ByDue` scan cost.** A user with many overdue cards will have a large scan range.
  For M8, limit the `GET /api/cards/due` response to 20 cards per session; this keeps
  the query bounded. Document the 20-card session cap.
- **Card count per note.** A dense note with 50+ highlights creates 50+ cards. This is
  semantically correct but may overwhelm a user. Consider a soft cap (warn the user if
  > 30 highlights are detected); configurable later.
- **SM-2 vs. FSRS.** SM-2 is implemented as a pure function with a clean interface, so
  swapping in FSRS later requires only replacing `scheduler.ts`. The data model's
  `ease` and `interval` fields map naturally to FSRS parameters with a migration.
  Document this as the intended upgrade path.
- **`due-count` cache freshness.** A 60 s client-side cache means the greeting line
  can be slightly stale. This is acceptable UX; a real-time due count would require
  websockets or SSE, which are out of scope.
