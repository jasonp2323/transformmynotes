# M15 · Quizzes & tests (auto-graded)

> Size: XL · Depends on: M13

## Goal

Let the user generate a quiz from any note's Markdown body using M13's Converse tool-use
wrapper, take the quiz in-app, and receive an instant score report with per-question
feedback. Multiple-choice questions (MCQ) are graded by exact `correctIndex` match
server-side. Short-answer questions are graded by a second Bedrock judge call that returns
a structured `{ correct, score, feedback }` verdict. The answer key is stored server-side
and never exposed to the client before submission — enforced at the API boundary (anti-cheat).
Attempt history (all past attempts for a quiz, score, gradedAt) is stored in DynamoDB
and displayed alongside the results screen.

## In scope

- Quiz schema + Bedrock generation (MCQ + short-answer) via M13's `generate()` wrapper;
  generated body (questions + answer key) stored in S3.
- Server-side answer key withholding: `GET /api/study/[quizId]/questions` strips
  `correctIndex` and `modelAnswer`/`acceptableAnswers` from the client payload before
  sending.
- Quiz + attempts data model: `STUDYSET#<ulid>` of `type: "quiz"` in the Notes table;
  `ATTEMPT#<quizId>#<ulid>` sort-key items for per-user attempt history; GSI for
  list-attempts-per-quiz.
- Key builders for quiz and attempt access patterns in `packages/core/src/db/keys.ts`.
- `infra/db.ts` GSI addition (`ByQuizAttempt`) on the Notes table.
- Dynalite integration tests for attempt write→read and list-attempts-per-quiz.
- Quiz-taking UI: render questions one per page (wizard) or as a scrollable single page;
  collect answers client-side; submit once (no partial saves); prevent re-submission.
- Auto-grading route `POST /api/study/[quizId]/attempt`: grades MCQ exact-match
  server-side, calls Bedrock judge for short-answer, writes the attempt item.
- Bedrock short-answer judge: a second `ConverseCommand` with `withBedrockRetry`, tool-use
  returning `{ correct: boolean, score: number, feedback: string }` per short-answer
  question; reuses `BEDROCK_MODEL_ID` secret and `Resource.BEDROCK_MODEL_ID.value`
  pattern from `packages/core/src/ocr/bedrock.ts`.
- Score report screen: overall score %, per-question correct/incorrect with the correct
  answer revealed, explanations, and Bedrock feedback for short-answer items.
- Attempt history list: `GET /api/study/[quizId]/attempts` + a UI panel on the quiz detail
  page showing past attempts sorted by `gradedAt` descending.
- Unit tests for MCQ grading logic and mocked Bedrock judge.
- Dynalite integration tests for all new DynamoDB access patterns.
- Browser UI test covering the quiz-taking → submit → score-report flow (mocked Bedrock).

## Out of scope

- Timed quizzes / countdown timers.
- Partial-credit scoring beyond the `score: 0..1` from the judge.
- Sharing quizzes with other users.
- Retaking a quiz in the same session without navigating away (each attempt is a full
  new submission).
- True-or-false or fill-in-the-blank question types (MCQ + short-answer only in M15).
- Leaderboards or cross-user score comparison.
- Bulk quiz generation across multiple notes.
- Editing generated questions before taking the quiz (post-M15).
- Offline quiz-taking or local answer draft persistence.
- Push notifications for new quizzes.

## Architecture & decisions

### Quiz schema + generation

M13 provides `packages/core/src/study/generate.ts` with the following assumed interface
(locked in M13 as a formal TypeScript export):

```typescript
generate<T>(opts: {
  systemPrompt: string;
  userMessage: string;
  toolName: string;
  toolDescription: string;
  toolSchema: JSONSchema;
  modelId: string;
  maxTokens?: number;
}): Promise<T>
```

M15 adds `packages/core/src/study/generateQuiz.ts`:

```typescript
export interface MCQQuestion {
  type: "mcq";
  id: string;           // ULID assigned at generation time
  stem: string;         // the question text
  options: string[];    // 2–5 answer choices
  correctIndex: number; // 0-based index into options (ANSWER KEY — server-side only)
  explanation: string;  // shown post-submission
}

export interface ShortAnswerQuestion {
  type: "short-answer";
  id: string;                    // ULID assigned at generation time
  prompt: string;                // the question text
  modelAnswer: string;           // canonical answer (ANSWER KEY — server-side only)
  acceptableAnswers: string[];   // synonyms/abbreviations the judge also accepts
  explanation: string;           // shown post-submission
}

export type QuizQuestion = MCQQuestion | ShortAnswerQuestion;

export interface GeneratedQuiz {
  questions: QuizQuestion[];
}

export async function generateQuiz(
  markdownBody: string,
  noteId: string,
): Promise<GeneratedQuiz>
```

**Tool-use JSON schema** passed to `generate()`:

```json
{
  "type": "object",
  "required": ["questions"],
  "properties": {
    "questions": {
      "type": "array",
      "minItems": 3,
      "maxItems": 15,
      "items": {
        "oneOf": [
          {
            "type": "object",
            "required": ["type", "stem", "options", "correctIndex", "explanation"],
            "properties": {
              "type":         { "type": "string", "enum": ["mcq"] },
              "stem":         { "type": "string", "maxLength": 400 },
              "options":      { "type": "array", "items": { "type": "string", "maxLength": 200 }, "minItems": 2, "maxItems": 5 },
              "correctIndex": { "type": "integer", "minimum": 0 },
              "explanation":  { "type": "string", "maxLength": 600 }
            }
          },
          {
            "type": "object",
            "required": ["type", "prompt", "modelAnswer", "acceptableAnswers", "explanation"],
            "properties": {
              "type":              { "type": "string", "enum": ["short-answer"] },
              "prompt":            { "type": "string", "maxLength": 400 },
              "modelAnswer":       { "type": "string", "maxLength": 300 },
              "acceptableAnswers": { "type": "array", "items": { "type": "string", "maxLength": 200 }, "maxItems": 10 },
              "explanation":       { "type": "string", "maxLength": 600 }
            }
          }
        ]
      }
    }
  }
}
```

**System prompt** (stored as `QUIZ_SYSTEM_PROMPT` exported constant in `generateQuiz.ts`):

> You are an expert quiz author for study notes. Given a Markdown note, produce 3–15 mixed
> questions testing key facts and concepts. Use multiple-choice (MCQ) for factual recall and
> short-answer for deeper comprehension. Rules: (1) MCQ `options` must include exactly one
> correct answer at `correctIndex`; distractors must be plausible, not trivially wrong.
> (2) Short-answer `modelAnswer` is the concise ideal answer (≤ 300 chars); list synonyms in
> `acceptableAnswers`. (3) `explanation` clarifies why the correct answer is right — always
> present, ≤ 600 chars. (4) If the note contains `==highlighted==` terms, each must appear in
> at least one question. (5) Output ONLY via the tool call — no prose.

`inferenceConfig.maxTokens`: 3072. Model id from `Resource.BEDROCK_MODEL_ID.value`; throws
loudly if unset (same guard as `packages/core/src/ocr/bedrock.ts` line 24–29). Bedrock call
wrapped in `withBedrockRetry` from `packages/core/src/ocr/retry.ts` (reused as-is).

After generation, `generateQuiz.ts` assigns a ULID `id` to each question (so the client can
reference questions by stable id in its submission payload).

**Answer key isolation**: `generateQuiz.ts` returns the full `GeneratedQuiz` including
`correctIndex`/`modelAnswer`/`acceptableAnswers`. The generation route writes the full object
to S3 (answer key included). The quiz-questions route strips answer-key fields before sending
to the client (see "Route handlers" below).

### Data model

#### Quiz item (`STUDYSET#<quizId>` in the Notes table)

Quizzes are a `STUDYSET` of `type: "quiz"`, following M13's existing `STUDYSET#` pattern:

```
PK        = USER#<sub>
SK        = STUDYSET#<quizId>          # quizId = ULID
attrs:
  quizId        string (ULID)
  sourceNoteId  string
  type          "quiz"
  status        "generating" | "ready" | "failed"
  bodyS3Key     string                 # quiz body (questions + answer key) in S3
                                       # e.g. quizzes/users/<sub>/<quizId>.json
  questionCount number
  createdAt     string (ISO-8601)
  updatedAt     string (ISO-8601)
  errorMsg?     string
```

No new GSI for the quiz item itself — quizzes are fetched by `USER#<sub>` + `STUDYSET#<quizId>`.

#### Attempt item

```
PK        = USER#<sub>
SK        = ATTEMPT#<quizId>#<attemptId>   # attemptId = ULID
GSI6-PK   = QUIZ#<quizId>                 # "ByQuizAttempt" GSI — list all attempts for a quiz
GSI6-SK   = GRADEDAT#<gradedAt ISO-8601>  # lexicographic descending scan
attrs:
  attemptId       string (ULID)
  quizId          string
  answers         Record<questionId, string>
                  # MCQ: "0" | "1" | "2" | … (string representation of chosen index)
                  # Short-answer: free-text string
  results         Record<questionId, {
                    correct: boolean
                    score:   number     # 0 or 1 for MCQ; 0..1 from judge for short-answer
                    feedback?: string   # judge feedback for short-answer; absent for MCQ
                  }>
  score           number  # 0..1 overall (mean of per-question scores)
  gradedAt        string  # ISO-8601 UTC
  durationMs?     number  # client-measured ms from first render to submit
```

#### GSI definition (`infra/db.ts`)

Add `ByQuizAttempt` GSI to the **Notes table** (the same table that holds `CARD#`,
`STUDYSET#`, etc. from M8/M13/M14):

| GSI | Hash key | Range key | Purpose |
|-----|----------|-----------|---------|
| `ByQuizAttempt` | `gsi6pk = QUIZ#<quizId>` | `gsi6sk = GRADEDAT#<ISO-8601>` | List all attempts for a quiz, newest first |

Fields to add to the Notes table definition in `infra/db.ts`:

```typescript
fields: { ..., gsi6pk: "string", gsi6sk: "string" }
globalIndexes: {
  ...,
  ByQuizAttempt: { hashKey: "gsi6pk", rangeKey: "gsi6sk" },
}
```

`GRADEDAT#<ISO-8601>` is lexicographically sortable; a `ScanIndexForward: false` scan
returns newest-first (most recent attempt at the top of the history list).

### Route handlers

#### `POST /api/study/generate` (extend M13's route — add `"quiz"` branch)

Auth: `proxy.ts` middleware. Body: `{ noteId: string; type: "quiz" }`.

Logic:
1. Validate `noteId` ownership (read Note item; assert `PK === USER#<sub>`).
2. Fetch note's Markdown body from S3 via `bodyS3Key`.
3. Call `generateQuiz(markdownBody, noteId)` — returns `GeneratedQuiz` with answer key.
4. Write the full quiz body (including answer key) to S3 at
   `quizzes/users/<sub>/<quizId>.json`.
5. Write a `STUDYSET#<quizId>` item with `status: "ready"`, `bodyS3Key`, `questionCount`.
6. Return `{ quizId, questionCount }` — **do NOT return the quiz body or any questions** from
   this route (answers not yet exposed).

Returns 403 for non-owner `noteId`; 404 if note not found; 500 + `status: "failed"` item on
Bedrock error.

#### `GET /api/study/[quizId]/questions`

Auth: `proxy.ts`. Returns the quiz questions stripped of answer-key fields.

Logic:
1. Read `STUDYSET#<quizId>` item; assert sub ownership; assert `status === "ready"`.
2. Fetch quiz body JSON from S3.
3. Strip answer-key fields from each question before serialising:
   - MCQ: omit `correctIndex` and `explanation`.
   - Short-answer: omit `modelAnswer`, `acceptableAnswers`, and `explanation`.
4. Return `{ quizId, questions: ClientQuestion[] }`.

`ClientQuestion` union type:

```typescript
type ClientMCQ = { type: "mcq"; id: string; stem: string; options: string[] }
type ClientShortAnswer = { type: "short-answer"; id: string; prompt: string }
type ClientQuestion = ClientMCQ | ClientShortAnswer
```

The answer key **never** leaves this route before submission. This is the sole anti-cheat
enforcement point — document with a `// ANTI-CHEAT: do not include correctIndex / modelAnswer`
comment in the route handler.

#### `POST /api/study/[quizId]/attempt`

Auth: `proxy.ts`. Body:

```typescript
{
  answers: Record<string, string>;  // questionId → answer (index string for MCQ, free text for SA)
  durationMs?: number;
}
```

Logic:
1. Validate ownership of `quizId`.
2. Fetch full quiz body from S3 (with answer key).
3. Grade each question:
   - **MCQ**: `correct = parseInt(answers[q.id]) === q.correctIndex`; `score = correct ? 1 : 0`.
   - **Short-answer**: call `judgeShortAnswer(q, answers[q.id])` — see below. `correct` and
     `score` from judge response.
4. Compute `score = mean(perQuestionScores)`.
5. Write attempt item with `attemptItemKey` + `attemptGsiKey` (includes all `results`, `score`,
   `gradedAt: now`, `durationMs`).
6. Return `{ attemptId, score, results: GradedResult[] }` where each `GradedResult` includes
   `questionId`, `correct`, `score`, `feedback`, and the answer-key fields now revealed:
   `correctIndex` (MCQ), `modelAnswer` (short-answer), `explanation`.

Returns 400 if `answers` is missing any question id; 401/403 as usual.

#### `GET /api/study/[quizId]/attempts`

Auth: `proxy.ts`.

Queries `listAttemptsByQuizQuery(quizId)` via `ByQuizAttempt` GSI; filters to items whose
`PK === USER#<sub>` (ownership) — the GSI query returns all users' attempts for a quiz, so
the route must filter server-side. Returns `{ attempts: AttemptSummary[] }` sorted newest
first, limit 20:

```typescript
interface AttemptSummary {
  attemptId: string;
  score: number;
  gradedAt: string;
  questionCount: number;
  durationMs?: number;
}
```

### Bedrock short-answer judge

File: `packages/core/src/study/judgeShortAnswer.ts`

```typescript
export interface JudgeResult {
  correct: boolean;
  score: number;    // 0..1 (0 = wrong, 0.5 = partial, 1 = correct)
  feedback: string; // ≤ 200 chars, shown to the user in the score report
}

export async function judgeShortAnswer(
  question: ShortAnswerQuestion,
  userAnswer: string,
): Promise<JudgeResult>
```

Implementation:
- Uses `BedrockRuntimeClient` → `ConverseCommand` (same client pattern as `bedrock.ts`).
- Reads `Resource.BEDROCK_MODEL_ID.value`; throws if unset.
- Wrapped in `withBedrockRetry` from `retry.ts`.
- `inferenceConfig.maxTokens`: 256 (judge output is tiny).
- Tool-use schema:

```json
{
  "type": "object",
  "required": ["correct", "score", "feedback"],
  "properties": {
    "correct":  { "type": "boolean" },
    "score":    { "type": "number", "minimum": 0, "maximum": 1 },
    "feedback": { "type": "string", "maxLength": 200 }
  }
}
```

- **System prompt** (exported as `JUDGE_SYSTEM_PROMPT`):

  > You are a strict but fair answer evaluator. Given a question, the model answer, a list of
  > acceptable synonyms, and a student's answer, decide whether the student answered correctly.
  > Rules: (1) Minor spelling errors and valid paraphrases count as correct. (2) Semantically
  > wrong answers are incorrect even if they mention related terms. (3) Set `score` to 1.0 for
  > fully correct, 0.5 for partially correct (key idea present but incomplete), 0.0 for wrong.
  > (4) `feedback` is a single concise sentence explaining the verdict. (5) Output only via the
  > tool call.

- User turn (text content block, constructed in `judgeShortAnswer`):

  ```
  Question: <q.prompt>
  Model answer: <q.modelAnswer>
  Also acceptable: <q.acceptableAnswers.join(", ")>
  Student answer: <userAnswer>
  ```

- `correct` is derived from the tool response: `result.score >= 0.5`.

## Risks / open questions

- **M13 interface stability.** M15 calls `generate()` directly. If M13's function signature
  changes, `generateQuiz.ts` breaks at compile time (mitigated by locking the `generate()`
  export as a formal TypeScript type in M13 — same mitigation as M14).
- **ByQuizAttempt GSI ownership filter cost.** The GSI is keyed by `QUIZ#<quizId>`, so the
  query returns all users' attempts for a quiz. The route must filter `PK === USER#<sub>`
  server-side. For M15 this is acceptable (quizzes are per-user; the only users who attempt a
  quiz are the quiz owner, so the filter never discards real rows). If quizzes are ever shared
  (post-M15), revisit the GSI design to add a user-scoped SK prefix.
- **Judge call latency.** A quiz with 5 short-answer questions requires 5 parallel Bedrock
  calls. At ~1–2 s per call (with `withBedrockRetry`), the `POST /api/study/[quizId]/attempt`
  route may take 2–3 s with `Promise.all`. This is acceptable UX (user sees "Grading…"
  overlay); document the expected latency in the route handler and set a generous Lambda/API
  timeout (≥ 30 s).
- **`ByQuizAttempt` GSI addition to the Notes table.** M8 added `ByDue` (GSI3); M13 added
  `StudySetsByUser`/`StudySetsByNote` (GSI4/GSI5); M14 did not add a GSI; M15 adds
  `ByQuizAttempt` (GSI6, the next free index). Adding a GSI to an existing Notes table that
  already has data requires DynamoDB to back-fill the index — typically fast for small tables
  but can take minutes in production. Verify the deploy succeeds on the `pr-<N>` stage before
  landing on `master`.
- **Answer key in S3 vs. DynamoDB.** Storing the full quiz body (including answer key) in S3
  rather than DynamoDB avoids the 400 KB item size limit for large quizzes and keeps the DB
  item small. The trade-off is an extra S3 `GetObject` on every grade request. For M15 (≤ 15
  questions, small JSON) this is negligible; document as a known latency contributor.
- **Judge score threshold.** `correct = score >= 0.5` is an opinionated threshold. The judge
  prompt defines `score: 0.5` as "key idea present but incomplete". If user feedback reveals
  this is too lenient, it can be raised to `0.7` by changing one constant in
  `judgeShortAnswer.ts` without a schema migration.
- **Re-grading on model-version bump.** If `BEDROCK_MODEL_ID` is bumped to a new model
  version, previously graded short-answer attempts will have been judged by the old model.
  This is cosmetic (historical records stand as-is); document in the architecture note that
  past attempts reflect the model that was active at submission time.
