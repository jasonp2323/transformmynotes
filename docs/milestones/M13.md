# M13 · AI study material — generation engine & foundation

> Size: XL · Depends on: M4, M5, M6

## Goal

Deliver the shared infrastructure and data model that M14–M17 build on, plus the
minimal UI entry point that makes study-material generation usable end-to-end in this
milestone. A user selects a note, picks a study-material type (flashcards, quiz,
assignment, or summary), and triggers generation — the system writes a `STUDYSET` item
to DynamoDB with `status: queued`, a DynamoDB Streams consumer in `infra/jobs.ts` picks
it up asynchronously, calls Bedrock using a tool-use (`toolConfig`) schema to get typed
JSON back, and writes the result to S3 + flips the status to `ready`. The UI polls for
status, then presents a result list and a generic JSON preview. Material-type-specific
renderers (flashcard decks, quiz sessions, assignments, summaries) arrive in M14–M16;
M13 ships the generation plumbing, data model, secrets, guardrails, language policy, and
the entry-point UI that lets a real user trigger and view a study set today.

The app's primary audience is Brazilian-Portuguese learners. Generated study material is
produced in **Brazilian Portuguese (pt-BR) by default**. When a note's `langPair`
indicates a pt-BR ↔ en language-learning context, the system produces **bilingual
artifacts** (e.g. flashcard front in pt-BR / back in English) to reinforce acquisition.
M13 establishes the **base system prompt** that defines the assistant's role and language
policy; all material-type prompts in M14–M17 inherit from this shared foundation.

## In scope

- **Structured-generation wrapper** `packages/core/src/study/generate.ts`: wraps
  `ConverseCommand` with `toolConfig` (Bedrock tool-use) and a per-type JSON
  `inputSchema` so the model returns validated typed JSON — not free text. Reuses
  `withBedrockRetry` and reads the model id from the existing `BEDROCK_MODEL_ID` secret
  via `process.env.SST_RESOURCE_BEDROCK_MODEL_ID_value`.
- **`STUDYSET` data model** in the Notes table (`infra/db.ts`): new SK prefix
  `STUDYSET#<ulid>`, two new GSIs (recency + by-source-note), S3 prefix for generated
  bodies (`study/users/<sub>/<id>.json`).
- Key builders for study sets in `packages/core/src/db/keys.ts`.
- Dynalite integration tests for all new write→read access patterns.
- **Async generation job**: `POST /api/study/generate` writes a `queued` STUDYSET item
  and returns immediately; a DynamoDB Streams Lambda consumer in `infra/jobs.ts`
  processes it (`queued → running → ready | failed`).
- **System-prompt design & Brazilian-Portuguese language policy**: a shared base system
  prompt (`STUDY_SYSTEM_PROMPT`) that defines the assistant's role, pt-BR default output
  language, and bilingual artifact policy for language-learning notes; a layered prompt
  model (base + per-type + per-request tool-use schema); prompt stored as `sst.Secret`
  with `promptVersion` tracked on each STUDYSET; a fixture-based eval plan. All
  material-type prompts in M14–M17 inherit the base. See "System-prompt design &
  language policy" subsection below.
- **Generation guardrails**: explicit `maxTokens` cap per type; per-user rate limit
  (max N in-flight or N per day) enforced server-side; fail loud on missing config.
- **"Generate study material" UI** on the note view (`packages/application`): type
  picker, async progress / polling state, result list showing the user's study sets for
  that note.
- **Study-set list page** (`/study`): lists all study sets for the user, newest first,
  with type badge + status indicator.
- **Generic viewer page** (`/study/[studySetId]`): renders the raw generated JSON in a
  readable preview. Type-specific renderers (M14–M16) will replace this view when
  they land.
- **Delete**: `DELETE /api/study/[studySetId]` + UI affordance to remove a study set
  (soft-deletes by removing the DynamoDB item and the S3 object).
- All new DynamoDB access patterns have dynalite integration tests.
- Ownership checks on every API route (caller `sub` === item `PK`).

## Architecture & decisions

### Structured-generation wrapper

File: `packages/core/src/study/generate.ts`

Uses Bedrock **tool-use** (`toolConfig`) so the model is forced to return structured
JSON matching a supplied `inputSchema`, rather than free text we have to parse. This is
more reliable than prompt-only JSON extraction and gives TypeScript-level typing.

```typescript
import { BedrockRuntimeClient, ConverseCommand } from '@aws-sdk/client-bedrock-runtime';
import { withBedrockRetry } from '../ocr/retry.js';

export type StudyMaterialType = 'flashcards' | 'quiz' | 'assignment' | 'summary';

export interface GenerateStudyMaterialInput {
  type: StudyMaterialType;
  noteMarkdown: string;         // full Markdown body fetched from S3
  noteTitle: string;
  language?: 'pt-BR' | 'bilingual';  // default: 'pt-BR'
}

export interface GenerateStudyMaterialResult {
  payload: unknown;             // typed by the per-type toolUse schema
  promptVersion: string;        // sha256(combinedPrompt).slice(0, 8) — stored on STUDYSET
  usage?: { inputTokens?: number; outputTokens?: number };
}

export async function generateStudyMaterial(
  input: GenerateStudyMaterialInput,
): Promise<GenerateStudyMaterialResult>
```

**Implementation notes:**

- `modelId` = `process.env.SST_RESOURCE_BEDROCK_MODEL_ID_value`; throw on missing.
- `maxTokens` per type:
  - `flashcards`: 4096
  - `quiz`: 4096
  - `assignment`: 2048
  - `summary`: 1024
- Combined system prompt = `STUDY_SYSTEM_PROMPT` (base) + `"\n\n"` + type-specific
  `sst.Secret` (see Secrets section) + language-policy directive derived from
  `input.language` (`'pt-BR'` default; `'bilingual'` appends the bilingual instruction);
  passed as `system: [{ text: combinedPrompt }]`. Compute `promptVersion` (sha256 of
  combined prompt, first 8 chars) and return it alongside `payload`.
- `toolConfig`: one tool named `submit_study_material` with a JSON Schema `inputSchema`
  specific to the type (see schemas below). Set `toolChoice: { tool: { name:
  "submit_study_material" } }` to force the model to call that tool.
- Extract result from `response.output.message.content` — find the `toolUse` block
  with name `submit_study_material` and return its `input` as `payload`.
- Wrap the `client.send(command)` in `withBedrockRetry(() => …)`.

**Tool input schemas (JSON Schema, abbreviated):**

```
flashcards → { cards: [{ front: string, back: string }] }
quiz       → { questions: [{ stem: string, choices: string[4], answerIndex: 0-3, explanation: string }] }
assignment → { title: string, instructions: string, rubric: [{ criterion: string, points: number }] }
summary    → { title: string, tldr: string, keyPoints: string[], terms: [{ term: string, definition: string }] }
```

Unit-test with a mocked `BedrockRuntimeClient` using `vi.mock`; assert `toolConfig` is
present, `toolChoice` forces the correct tool name, and `maxTokens` matches the type.

### STUDYSET data model

`STUDYSET` items live in the Notes table alongside `NOTE#` and `CARD#` items, under the
same `PK = USER#<sub>` partition.

#### Item shape

```
PK              = USER#<sub>
SK              = STUDYSET#<ulid>          # ulid = time-ordered, generated at POST time
GSI4PK          = USER#<sub>
GSI4SK          = STUDYSET#<ulid>          # recency — newest first (desc scan)
GSI5PK          = NOTE#<sourceNoteId>      # by-source-note lookup
GSI5SK          = USER#<sub>#STUDYSET#<ulid>

attrs:
  studySetId      string  (ULID — same as the one in SK)
  sourceNoteIds   string[]  # single-element array in M13; multi-note in M17
  type            'flashcards' | 'quiz' | 'assignment' | 'summary'
  title           string    # e.g. "Flashcards – Subjuntivo (2025-06-10)"
  status          'queued' | 'running' | 'ready' | 'failed'
  language        'pt-BR' | 'bilingual'   # resolved language mode; stored at queue time
  error?          string    # present only when status = 'failed'
  bodyS3Key?      string    # study/users/<sub>/<ulid>.json — set when status = 'ready'
  model           string    # the BEDROCK_MODEL_ID value used; snapshot at generation time
  promptVersion   string    # sha256(basePrompt + typePrompt).slice(0, 8) — set on ready
  createdAt       string    # ISO-8601 UTC
  updatedAt       string    # ISO-8601 UTC
```

The `bodyS3Key` is set only after generation completes. Large generated payloads
(flashcard decks, quizzes) live in S3; the DynamoDB item holds only metadata + status.
Items smaller than ~30 KB could be stored inline, but storing all types in S3
consistently simplifies the consumer code and avoids DDB item-size limits.

#### GSI definitions (`infra/db.ts`)

Add two new fields to the Notes table definition (`gsi4pk`, `gsi4sk`, `gsi5pk`,
`gsi5sk`, all string type) and declare:

| GSI | Hash key | Range key | Purpose |
|-----|----------|-----------|---------|
| `StudySetsByUser` (GSI4) | `GSI4PK` = `USER#<sub>` | `GSI4SK` = `STUDYSET#<ulid>` | List all study sets for a user, newest first (ULID lexicographic desc scan) |
| `StudySetsByNote` (GSI5) | `GSI5PK` = `NOTE#<sourceNoteId>` | `GSI5SK` = `USER#<sub>#STUDYSET#<ulid>` | List all study sets derived from a given note |

GSI4 uses a `ScanIndexForward: false` query to return newest-first. GSI5 uses a
`begins_with(gsi5sk, "USER#<sub>#")` condition to isolate the requesting user's sets
when listing by note (avoiding cross-user data leaks through the GSI).

#### Key builders (`packages/core/src/db/keys.ts`)

```typescript
export const studySetKeys = {
  /** Primary key for a study set item. */
  item: (sub: string, studySetId: string) => ({
    pk: `USER#${sub}`,
    sk: `STUDYSET#${studySetId}`,
  }),

  /** GSI4 key attributes (recency index). Attach on write. */
  recencyIndex: (sub: string, studySetId: string) => ({
    gsi4pk: `USER#${sub}`,
    gsi4sk: `STUDYSET#${studySetId}`,
  }),

  /** GSI5 key attributes (by-source-note index). Attach on write. */
  byNoteIndex: (sourceNoteId: string, sub: string, studySetId: string) => ({
    gsi5pk: `NOTE#${sourceNoteId}`,
    gsi5sk: `USER#${sub}#STUDYSET#${studySetId}`,
  }),

  /** Query: list all study sets for a user via GSI4, newest first. */
  listByUser: (sub: string, limit = 50) => ({
    IndexName: 'StudySetsByUser',
    KeyConditionExpression: 'gsi4pk = :gsi4pk AND begins_with(gsi4sk, :prefix)',
    ExpressionAttributeValues: { ':gsi4pk': `USER#${sub}`, ':prefix': 'STUDYSET#' },
    ScanIndexForward: false,
    Limit: limit,
  }),

  /** Query: list all study sets derived from a specific note for a specific user. */
  listByNote: (sourceNoteId: string, sub: string) => ({
    IndexName: 'StudySetsByNote',
    KeyConditionExpression: 'gsi5pk = :gsi5pk AND begins_with(gsi5sk, :prefix)',
    ExpressionAttributeValues: {
      ':gsi5pk': `NOTE#${sourceNoteId}`,
      ':prefix': `USER#${sub}#STUDYSET#`,
    },
  }),
};
```

#### S3 key (`packages/core/src/db/keys.ts` — `storageKeys`)

Add to the existing `storageKeys` object:

```typescript
studySetBody: (sub: string, studySetId: string) => `study/users/${sub}/${studySetId}.json`,
```

### Async generation job

**Why async:** Bedrock generation for a full flashcard deck or quiz takes 5–30 seconds.
Holding an HTTP connection open that long is fragile (Lambda timeout, client timeout,
bad UX). The right pattern is:

1. `POST /api/study/generate` — writes `STUDYSET` item with `status: queued`, returns
   `{ studySetId }` immediately (HTTP 202).
2. DynamoDB Streams consumer in `infra/jobs.ts` — triggered by the `INSERT` event on
   the Notes table (stream already set to `new-and-old-images`). Filters for
   `SK begins_with "STUDYSET#"` and `status = "queued"`. Processes the item.
3. Consumer flow: `queued → running` (conditional update to guard idempotency),
   fetch note Markdown from S3 (`bodyS3Key` on the note item), call
   `generateStudyMaterial`, write result to S3 (`studySetBody`), update item
   `status → ready` + set `bodyS3Key`. On any unrecoverable error: update
   `status → failed` + set `error` message.

**Idempotency guard:** Before calling Bedrock, the consumer does a conditional
`UpdateItem` that atomically flips `status` from `queued` to `running` with a
`ConditionExpression: #status = :queued`. If the condition fails (another Lambda
invocation already took it), the handler exits cleanly without a duplicate Bedrock call.

**Consumer implementation (`infra/jobs.ts`):**

```typescript
import { userData } from './db';
import { notesBucket } from './storage';
import { bedrockInferenceProfileId, studySystemPrompt, studyFlashcardsPrompt,
         studyQuizPrompt, studyAssignmentPrompt, studySummaryPrompt } from './secrets';

export const studyGenerationConsumer = new sst.aws.Function('StudyGenerationConsumer', {
  handler: 'packages/application/jobs/study-generation.handler',
  link: [userData, notesBucket, bedrockInferenceProfileId,
         studySystemPrompt, studyFlashcardsPrompt, studyQuizPrompt,
         studyAssignmentPrompt, studySummaryPrompt],
  permissions: [
    { actions: ['dynamodb:GetItem', 'dynamodb:UpdateItem'], resources: [userData.arn] },
    { actions: ['s3:GetObject', 's3:PutObject'],
      resources: [$interpolate`arn:aws:s3:::${notesBucket.name}/study/*`,
                  $interpolate`arn:aws:s3:::${notesBucket.name}/markdown/*`] },
    { actions: ['bedrock:InvokeModel', 'bedrock:InvokeModelWithResponseStream'],
      resources: [$interpolate`arn:aws:bedrock:us-east-1::foundation-model/${bedrockInferenceProfileId.value}`] },
  ],
});

userData.subscribe(studyGenerationConsumer.arn, {
  filters: [{ eventName: ['INSERT'], dynamodb: { NewImage: { sk: { S: [{ prefix: 'STUDYSET#' }] } } } }],
});
```

The handler file lives at
`packages/application/jobs/study-generation.ts` (under the application package so it
has access to the `@transformmynotes/core` workspace dependency).

**Status polling:** The client polls `GET /api/study/[studySetId]` every 2 seconds
while `status === 'queued' | 'running'`. Max 60 polls (120 s); after timeout, show
a "still processing" message with a manual refresh option.

### System-prompt design & language policy

#### Role framing

The assistant is a **study-material generator for a Brazilian-Portuguese note-taking and
language-learning app**. Its job is to transform a user's handwritten (OCR-transcribed)
study notes into structured, pedagogically sound artifacts. Notes are predominantly in
Brazilian Portuguese; some carry a `langPair` that signals active pt-BR ↔ en language
learning, in which case the assistant produces bilingual output to reinforce acquisition.

#### Layered prompt model

Every generation call assembles three layers:

| Layer | What it contains | Where it lives |
|-------|-----------------|----------------|
| **Base system prompt** | Role framing, language policy, output-quality rules common to all material types | `STUDY_SYSTEM_PROMPT` (`sst.Secret`) |
| **Per-material-type instruction layer** | Type-specific instructions (flashcard count/style, quiz difficulty, etc.) | `STUDY_FLASHCARDS_PROMPT`, `STUDY_QUIZ_PROMPT`, `STUDY_ASSIGNMENT_PROMPT`, `STUDY_SUMMARY_PROMPT` (`sst.Secret`s) |
| **Per-request tool-use JSON schema** | The `toolConfig` `inputSchema` that forces typed JSON output for this specific type/request | Inline in `generate.ts` per `StudyMaterialType` |

`generateStudyMaterial` concatenates `baseSystemPrompt + "\n\n" + typePrompt` and
passes the combined string as `system: [{ text: combinedPrompt }]`. The per-request
schema (layer 3) is always the same for a given type; it is not stored as a secret
because schema changes require a code deploy (they are part of the TypeScript contract).

#### Language policy

- **Default output language: Brazilian Portuguese (pt-BR).** The base system prompt
  instructs the model to write all generated content (card text, question stems, rubric
  criteria, summaries) in pt-BR unless the note's language context indicates otherwise.
- **Bilingual mode (pt-BR ↔ en).** When `POST /api/study/generate` receives a
  `language` param of `"bilingual"` (or the source note's `langPair` is `"pt-BR → en"`
  or `"en → pt-BR"`), the generation wrapper instructs the model to produce bilingual
  artifacts: flashcard front in pt-BR / back in English (or vice-versa per
  `langPair` direction), quiz answer explanations in both languages, etc.
- **Configurable per request.** The `POST /api/study/generate` request body accepts an
  optional `language` field:

  ```typescript
  {
    sourceNoteId: string;
    type: StudyMaterialType;
    language?: 'pt-BR' | 'bilingual';   // default: 'pt-BR'
  }
  ```

  The resolved `language` value is stored on the STUDYSET item and threaded into the
  prompt so the model's instruction is unambiguous. The `generate.ts` wrapper accepts
  `language` as part of `GenerateStudyMaterialInput` and injects the appropriate
  language directive into the combined system prompt before invoking Bedrock.

#### Prompt storage & versioning

- `STUDY_SYSTEM_PROMPT` — the shared base system prompt, stored as an `sst.Secret`
  (declared in `infra/secrets.ts`, SCREAMING_SNAKE_CASE, fail loud if unset). Seeded in
  both Console environments (production + fallback). Prompt iteration is a secret update,
  not a code deploy — mirrors how `BEDROCK_MODEL_ID` is handled today.
- Each material-type secret (`STUDY_FLASHCARDS_PROMPT`, etc.) supplements the base;
  neither replaces it.
- **`promptVersion` field on STUDYSET items.** At generation time, compute a short
  stable tag from the combined prompt (e.g. first 8 chars of `sha256(basePrompt +
  typePrompt)`). Store it as `promptVersion: string` on the STUDYSET DynamoDB item. This
  enables tracing which prompt version produced a given study set, which is essential for
  evaluating prompt iterations and deciding whether to regenerate stale sets after a
  prompt update. Add `promptVersion` to the STUDYSET item shape in `infra/db.ts` and
  key builders.

#### Eval / iteration loop

Before shipping to production, validate the base prompt on a representative fixture set:

1. **Fixture corpus**: assemble 5–10 real pt-BR note snippets (a mix of topics —
   grammar rules, vocabulary lists, subject-matter notes in Portuguese) stored in
   `packages/core/test/fixtures/study-prompt/`. These are static `.md` files checked
   into the repo; they are safe to commit because they are study-content samples, not
   credentials.
2. **Expected-shape rubric** (manual, not automated): for each fixture, describe the
   expected output shape (e.g. "≥ 8 flashcards; fronts are concise Portuguese questions;
   backs are precise answers"). Record the rubric in a `rubric.md` alongside the
   fixtures.
3. **Eval script** (`packages/scripts/src/eval-study-prompt.ts`): runs
   `generateStudyMaterial` against each fixture (requires a live SST stage with secrets
   seeded), writes outputs to `tmp/eval-output/`, and prints a checklist so the
   prompt author can score each output against the rubric. Not a CI gate — run manually
   before each prompt update.
4. **Acceptance bar**: all 5–10 fixtures produce structurally valid JSON (schema
   validated), output is in pt-BR (or bilingual where the fixture's `langPair` requests
   it), and at least 80 % of outputs pass the manual rubric on first review.

The eval loop must be exercised at least once on the initial `STUDY_SYSTEM_PROMPT` seed
value before the milestone is considered Done.

### Route handlers

#### `POST /api/study/generate`

Auth: `proxy.ts` middleware (`getAuthenticatedSub()`).

Request body:
```typescript
{
  sourceNoteId: string;   // must be a NOTE owned by the caller
  type: StudyMaterialType;
}
```

Logic:
1. Verify `sourceNoteId` ownership: `GetItem` the note by `noteKeys.item(sub, noteId)`;
   return 404 if not found or sub mismatch.
2. Check per-user rate limit: query `StudySetsByUser` GSI with a `FilterExpression`
   for `status IN ('queued', 'running')` and count; reject with 429 if ≥ 3
   in-flight. (Hard limit; the constant is configurable via `MAX_CONCURRENT_STUDY_JOBS`
   read from env, defaulting to 3, failing loud if set to a non-integer.)
3. Generate a ULID (`studySetId`).
4. Build the note title: derive from the source note's `title` field.
5. Write the `STUDYSET` item with `status: queued`; include all GSI4 + GSI5 key attrs.
6. Return HTTP 202: `{ studySetId }`.

#### `GET /api/study/[studySetId]`

Auth: `proxy.ts` middleware.

Returns the study set metadata (`studySetId`, `type`, `title`, `status`, `error?`,
`createdAt`, `updatedAt`). Does NOT inline the body JSON from S3 — the viewer page
fetches the body separately. Returns 404 if not found or sub mismatch; 401 if
unauthenticated.

#### `GET /api/study/[studySetId]/body`

Auth: `proxy.ts` middleware.

Returns the parsed JSON body from S3 (`bodyS3Key`). Returns 404 if `status !== 'ready'`
or `bodyS3Key` is unset. Caller (the viewer page) uses this to render the content.

#### `GET /api/study?noteId=<id>` (optional `noteId` filter)

Auth: `proxy.ts` middleware.

Without `noteId`: lists all study sets for the user via `StudySetsByUser` GSI (newest
first, limit 50). With `noteId`: lists via `StudySetsByNote` GSI filtered to the
caller's sub. Returns `{ studySets: StudySetMeta[] }`.

#### `DELETE /api/study/[studySetId]`

Auth: `proxy.ts` middleware.

1. Verify ownership.
2. Delete the S3 object at `bodyS3Key` (if present, best-effort — do not error on
   missing object).
3. `DeleteItem` from DynamoDB.
4. Return HTTP 204.

**Token caps** (enforced in `generateStudyMaterial`, not in the prompt):

| Type | maxTokens |
|------|-----------|
| flashcards | 4096 |
| quiz | 4096 |
| assignment | 2048 |
| summary | 1024 |

per user. Enforced in `POST /api/study/generate` before writing the item.

non-integer, default 3) so the limit can be tightened per stage without a code deploy.

### "Generate study material" UI entry point

Location: `packages/application/app/(authed)/notes/[noteId]/page.tsx` (the NoteView)
and/or the note action bar.

- **Type picker**: a bottom-sheet or inline panel with four options — Flashcards, Quiz,
  Assignment, Summary — each with an icon and one-line description. Selecting a type
  and tapping "Generate" calls `POST /api/study/generate`.
- **Progress state**: after the POST returns 202, the component transitions to a
  progress view (spinner + "Generating your flashcards…") and begins polling
  `GET /api/study/[studySetId]` every 2 s. Poll at most 60 times (120 s total);
  show a "still processing — check back later" fallback after timeout.
- **Result list**: when status reaches `ready`, navigate to `/study/[studySetId]` (the
  generic viewer). Also refresh the "Study sets for this note" section of the note view
  which lists existing sets (via `GET /api/study?noteId=<id>`).
- **Error state**: when status is `failed`, show the error message with a "Try again"
  button (re-calls `POST /api/study/generate` with the same params).

### Study-set list page (`/study`)

Route: `packages/application/app/(authed)/study/page.tsx`

Fetches `GET /api/study` (all sets, newest first). Renders a list with:
- Type badge (Flashcards / Quiz / Assignment / Summary), coloured by type.
- Status indicator: a pulsing dot for `queued/running`, a check for `ready`, an X for
  `failed`.
- Note title (derived from the `title` field on the study set).
- `createdAt` relative timestamp.
- Tapping a `ready` item navigates to `/study/[studySetId]`.

### Generic viewer page (`/study/[studySetId]`)

Route: `packages/application/app/(authed)/study/[studySetId]/page.tsx`

Fetches the item metadata (`GET /api/study/[studySetId]`) and the body
(`GET /api/study/[studySetId]/body`). Renders the JSON body in a legible way:

- For `flashcards`: numbered card list, front/back stacked.
- For `quiz`: question + choices list (answer revealed on tap).
- For `assignment`: title, instructions, rubric table.
- For `summary`: tldr card, key-points list, terms table.

These are intentionally basic renderings — they are replaced by the full type-specific
renderers in M14–M16. The important thing is the JSON is human-readable today.

Includes a "Delete" button (calls `DELETE /api/study/[studySetId]`; navigates back to
`/study` on success) and a disabled "Open in deck" / "Start quiz" stub button

## Risks / open questions

- **pt-BR output quality & dialect.** Brazilian Portuguese has regional vocabulary and
  orthographic conventions that differ from European Portuguese. A prompt that only says
  "write in Portuguese" may produce EP-flavoured output or mix dialects. The base system
  prompt must be explicit ("Brazilian Portuguese (pt-BR)") and the fixture-based eval
  must include notes covering colloquial pt-BR vocabulary and grammar structures. If
  model outputs drift toward EP or produce code-switched text, iterate the prompt before
  launch — do not ship until the eval passes on real pt-BR note content.
- **GSI provisioning time.** Adding GSI4 and GSI5 to the Notes table with
  `sst deploy` involves CloudFormation + DynamoDB GSI creation, which can take
  several minutes. If the table already has data (e.g. on an older `pr-<N>` stage),
  DynamoDB must back-fill the GSI — plan for a few minutes of reduced availability.
  Run `sst deploy` and wait for the stack to stabilise before testing.
- **Stream consumer cold-start latency.** The Lambda consumer cold-start on a new `pr-<N>`
  stage can add 2–5 s to the first generation. Subsequent invocations are warm. This
  is acceptable; document it so testers know not to expect sub-second transitions from
  `queued` to `running`.
- **Bedrock tool-use model compatibility.** `toolConfig` with `toolChoice: { tool: … }`
  requires a model that supports tool-use (e.g. Claude 3+ Sonnet). The existing
  `BEDROCK_MODEL_ID` value must be a tool-use-capable model. Verify on the Bedrock
  console before seeding; document the minimum model requirement in `infra/secrets.ts`.
- **Large note bodies.** A note with a very long Markdown body (e.g. a 10-page OCR
  transcription) may approach or exceed the model's context window. Mitigation: in
  the consumer, truncate `noteMarkdown` to a configurable character limit (e.g. 40 000
  chars ≈ ~10 000 tokens) and log a warning if truncation occurs. The truncation limit
  should be a server-side constant, not silently ignored.
- **S3 delete partial failure.** `DELETE /api/study/[studySetId]` deletes the S3
  object then the DynamoDB item. If the S3 delete succeeds but the DynamoDB delete
  fails, the item is orphaned. Mitigation: delete DynamoDB first (the source of truth),
  then S3 best-effort; if S3 delete fails, log but return 204 to the client (the item
  is already gone from the user's perspective).
- **Concurrent generation at scale.** The per-user rate limit (3 in-flight) is a
  simple count-based check, not a proper distributed lock. Under rapid concurrent
  requests it is theoretically possible to exceed the limit by a small margin. For an
  MVP this is acceptable; a DynamoDB condition-expression-based atomic counter can
  replace it if rate-limiting becomes a product requirement.
- **M14–M16 schema compatibility.** The `payload` stored in S3 as JSON must match the
  schema that M14 (flashcards) and M15 (quiz) renderers expect. The JSON Schema in
  `generateStudyMaterial`'s `toolConfig` is the contract; document it as stable once
  M13 merges. Any breaking schema change requires a migration of existing S3 objects.
