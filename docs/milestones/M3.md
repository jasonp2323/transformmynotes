# M3 · Invites, groups & admin panel

> Size: L · Depends on: M2 (auth & onboarding)

## Goal

Deliver the complete invite system, groups/courses data model, and the full admin panel
(ported from `screens-admin.jsx`). Admins can issue single-use email invites (sent via Resend)
or reusable capped shareable codes; both code types expire in 30 days by default and are
revocable immediately. Admins can approve or reject pending registrations, manage the member
roster, and manage invite lifecycle — all from the desktop-optimised `DesktopShell` layout.
Every admin route is gated server-side on the Cognito `admin` group (set in M2's `proxy.ts`).

The M2 Post-Confirmation Lambda already reads the `Invites` table for invite-based
registrations; M3 writes the records that Lambda consumes, completing the loop.

## In scope

- `Invites` DynamoDB table: full schema, GSI, key builders, and dynalite integration tests.
- `Groups` DynamoDB table (for course/group metadata + membership records): full schema, GSI,
  key builders, and dynalite integration tests.
- Invite creation API (`POST /api/admin/invites`): email-invite (sends via Resend) and
  reusable shareable code, with expiry and group assignment.
- Invite redemption flow completions: the `/api/auth/invite/validate` endpoint (introduced
  as a stub in M2) is fully implemented against the real `Invites` table.
- Admin panel pages (all under `/admin/**`, gated by `proxy.ts` `admin` group check):
  - `AdminPending` → `/admin/pending` — approve/reject queue.
  - `AdminUsers` → `/admin/users` — member roster, role change, enable/disable, remove.
  - `AdminInvites` → `/admin/invites` — create, list, filter, revoke.
- `DesktopShell` sidebar component shared across all admin pages.
- Approve action: adds user to Cognito `member` group + sets DynamoDB `status=active`;
  sends a welcome email via Resend.
- Reject action: sets DynamoDB `status=disabled`, records an audit note; sends a rejection
  email via Resend (calm tone, per DS content guidelines).
- Rate limiting on invite redemption (`POST /api/auth/register` with a code, and
  `/api/auth/invite/validate`) — already stubbed in M2; ensure the real Invites table lookups
  are within the same rate-limit window.
- Unit tests for: invite code hashing (`sha256`), expiry logic, single-use vs. capped-use
  guard, rate-limit sliding window.
- Dynalite integration tests for every new DynamoDB access pattern.
- Browser UI tests for all three admin panel views.

## Out of scope

- Note capture, OCR, and the main notebook library (separate milestones).
- Group membership management beyond what invite assignment covers (full group admin UI is a
  later milestone).
- Bulk invite import (CSV).
- Audit log UI (records are written; surfacing them is future work).
- Per-group permission scoping (all members currently see all their group's notes).
- Public invite landing page on the marketing site (marketing has no DB access; the invite
  accept page lives in `packages/application`).

## Architecture & decisions

### Data model — `Invites` table

Defined in `infra/db.ts`. Each invite is one item. Raw invite codes are **never stored**;
only `sha256(rawCode)` appears in the PK.

| Key | Value | Purpose |
|---|---|---|
| `PK` | `INVITE#<sha256(code)>` | O(1) lookup on redemption (hash incoming code, query by PK) |
| `SK` | `INVITE` | Static discriminator |
| `GSI1PK` | `INVITES` | Partition all invites into one list |
| `GSI1SK` | `<status>#<ISO-8601 createdAt>` | Filter by status + time-order within status; e.g. `pending#2026-06-01T12:00:00Z` |

Attributes:

| Attribute | Type | Notes |
|---|---|---|
| `codeHash` | string | `sha256(rawCode)` — mirrors the PK suffix |
| `type` | `email \| code` | Email invite = single-use for one address; code = reusable up to `maxUses` |
| `targetEmail` | string? | Only for `type=email`; the locked email address this invite is for |
| `label` | string? | Human-readable label for `type=code` invites (e.g. "SPAN-201-FALL") |
| `groupId` | string? | If set, redeemer is added to this group on activation |
| `expiresAt` | string | ISO-8601; default = `now + 30d`; `null` = never expires |
| `maxUses` | number | For `type=code`; ≥1; email invites always 1 |
| `usedCount` | number | Atomic-incremented on each redemption |
| `status` | `pending \| used \| expired \| revoked` | `used` when `usedCount >= maxUses` for a code, or on first use for email |
| `createdBy` | string | Admin `sub` |
| `createdAt` | string | ISO-8601 |
| `updatedAt` | string | ISO-8601; set on status change |
| `auditNotes` | string? | Free-text set on revoke/reject |

GSI name: `GSI1` — `GSI1PK` (HASH) + `GSI1SK` (RANGE). Supports listing all invites with
optional status filtering by key-condition prefix on `GSI1SK`.

Key builders in `packages/core/src/db/keys.ts`:

- `inviteKey(codeHash)` → `{ PK: 'INVITE#<codeHash>', SK: 'INVITE' }`
- `inviteIndexKey(status, createdAt)` → `{ GSI1PK: 'INVITES', GSI1SK: '<status>#<createdAt>' }`
- `hashInviteCode(rawCode)` → `string` (sha256 hex; pure function, unit-testable)
- `listInvitesByStatus(status)` → KeyConditionExpression with `begins_with(GSI1SK, '<status>#')`
- `listAllInvites()` → query on `GSI1PK = 'INVITES'` with no SK condition

### Data model — `Groups` table

Groups (courses) are stored in the same DynamoDB single-table design or a dedicated table
(prefer single-table if the table limit allows). Two item shapes: the group metadata record
and per-member membership records.

**Group metadata item:**

| Key | Value |
|---|---|
| `PK` | `GROUP#<groupId>` |
| `SK` | `META` |

Attributes: `groupId`, `name`, `description?`, `createdBy`, `createdAt`, `memberCount`
(maintained by conditional increments on membership writes).

**Group membership item:**

| Key | Value |
|---|---|
| `PK` | `GROUP#<groupId>` |
| `SK` | `MEMBER#<userSub>` |
| `GSI1PK` | `USER#<userSub>` |
| `GSI1SK` | `GROUP#<groupId>` |

Attributes: `groupId`, `userSub`, `joinedAt`, `role` (`member | admin`).

GSI1 (same index as `UserData` table if using single-table, or a new GSI on the Groups table)
inverted index: given a `userSub`, list all groups that user belongs to. GSI1PK =
`USER#<sub>`, GSI1SK = `GROUP#<groupId>`.

Key builders:

- `groupMetaKey(groupId)` → `{ PK: 'GROUP#<groupId>', SK: 'META' }`
- `groupMemberKey(groupId, userSub)` → `{ PK: 'GROUP#<groupId>', SK: 'MEMBER#<userSub>' }`
- `userGroupsIndexKey(userSub, groupId)` → `{ GSI1PK: 'USER#<userSub>', GSI1SK: 'GROUP#<groupId>' }`
- `listGroupMembers(groupId)` → query `PK = 'GROUP#<groupId>'` with `begins_with(SK, 'MEMBER#')`
- `listUserGroups(userSub)` → query GSI1 `GSI1PK = 'USER#<userSub>'` with `begins_with(GSI1SK, 'GROUP#')`

### Invite creation flow

**Email invite** (`type=email`, `maxUses=1`):

1. Admin POSTs `{ type: 'email', email, groupId?, expiresAt? }` to
   `POST /api/admin/invites`.
2. Server generates a cryptographically random code (e.g. 8-char alphanumeric via
   `crypto.randomBytes`). Formats it as `XXXX-XXXX` for display (separator stored in the
   label, not in the hash input — hash the raw alphanumeric string before formatting).
3. Computes `codeHash = sha256(rawCode)`.
4. Writes the `Invites` item (PK=`INVITE#<codeHash>`).
5. Sends an invite email via Resend: from `INVITE_FROM_ADDRESS` (a new `sst.Secret`),
   body includes the formatted code, the group name, and an expiry date. The deep link
   `/invite?code=<rawCode>&email=<email>` is also included for convenience.
6. Returns `{ codeDisplay: 'XXXX-XXXX', expiresAt }` to the admin UI (raw code only
   returned once, at creation time — never retrievable again).

**Shareable code** (`type=code`, `maxUses=N`):

1. Admin POSTs `{ type: 'code', label, groupId?, maxUses, expiresAt? }`.
2. Same code generation + hashing.
3. No email sent. Returns `{ codeDisplay, expiresAt }` for the admin to share manually.

### Invite redemption flow (completing the M2 stub)

`POST /api/auth/invite/validate` (used by the register and invite-accept pages):

1. Hash the user-supplied code: `codeHash = sha256(rawCode)`.
2. `GetItem` from `Invites` by `PK = 'INVITE#<codeHash>'`.
3. Validate: item exists; `status = 'pending'`; `expiresAt` is in the future (or null);
   if `type = 'email'`, `targetEmail` matches the provided email (case-insensitive).
4. Return `{ valid, groupName, inviterName?, expiresAt }` (never return whether the email
   matches a registered user).
5. Do NOT increment `usedCount` here — that happens atomically in the Post-Confirmation
   Lambda to avoid partial states.

The Post-Confirmation Lambda (M2) performs the atomic increment:
`UpdateItem` with `ConditionExpression: usedCount < maxUses AND #status = :pending`,
`UpdateExpression: SET usedCount = usedCount + :one, #status = if(usedCount + 1 >= maxUses, :used, :pending)`.
On `ConditionalCheckFailedException`, treat as "already used / expired" and fall back to
`status=pending` for the user profile.

### Rate limiting

A shared utility `packages/application/lib/ratelimit.ts` implements a sliding-window counter
stored in a DynamoDB item (or in-memory for non-Lambda/edge targets). Limits:

- `POST /api/auth/invite/validate`: 10 requests per 15 minutes per IP.
- `POST /api/auth/register` (with invite code): 10 requests per 15 minutes per IP.
- `POST /api/admin/invites`: 20 requests per minute per admin `sub` (prevent spam).

On limit exceeded, return HTTP 429 with `Retry-After` header.

### Approve / reject actions

`POST /api/admin/users/:sub/approve`:

1. Verify caller is in the `admin` Cognito group (from JWT in server action context).
2. Read the `UserData` profile. Assert `status = 'pending'`.
3. `AdminAddUserToGroup(sub, 'member')` via `@aws-sdk/client-cognito-identity-provider`.
4. Update DynamoDB: `status = 'active'`, `updatedAt = now`.
5. Send welcome email via Resend: from `INVITE_FROM_ADDRESS`, calm tone ("Your access to
   TransformMyNotes is ready...").
6. Return `{ ok: true }`. The admin UI removes the row with an optimistic update + toast.

`POST /api/admin/users/:sub/reject`:

1. Verify caller is admin.
2. Assert `status = 'pending'`.
3. Update DynamoDB: `status = 'disabled'`, `auditNotes = 'Rejected by admin'`, `updatedAt`.
4. Do NOT remove from Cognito — the account remains in Cognito as `CONFIRMED` but is
   permanently blocked from notebook access by the `proxy.ts` status check.
5. Send rejection email via Resend (optional, calm tone: "We weren't able to approve your
   request at this time.").
6. Return `{ ok: true }`.

### User management actions

`PATCH /api/admin/users/:sub/role` — change role between `admin` and `member`:
Calls `AdminAddUserToGroup` / `AdminRemoveUserFromGroup`; updates `role` in DynamoDB.

`PATCH /api/admin/users/:sub/status` — enable/disable:
Updates `status` in DynamoDB to `active` or `disabled`. Does not change Cognito group.
`proxy.ts` status check enforces the block.

`DELETE /api/admin/users/:sub` — remove member:
`AdminDeleteUser` in Cognito; delete `UserData` item; write an audit record
(`USER#<sub>#DELETED` item with minimal attrs for audit trail). Soft-delete only — do not
delete notes (note ownership by `sub` is preserved for potential restore). Confirm dialog
required client-side (matches the `ADialog` in `AdminUsers`).

### API routes summary

All under `packages/application/app/api/admin/`:

| Method | Route | Description |
|---|---|---|
| `GET` | `/api/admin/users/pending` | List `STATUS#pending` users from GSI1 |
| `GET` | `/api/admin/users` | List all active + disabled users (GSI scan or table scan with filter) |
| `POST` | `/api/admin/users/:sub/approve` | Approve pending user |
| `POST` | `/api/admin/users/:sub/reject` | Reject pending user |
| `PATCH` | `/api/admin/users/:sub/role` | Change role admin ↔ member |
| `PATCH` | `/api/admin/users/:sub/status` | Enable / disable user |
| `DELETE` | `/api/admin/users/:sub` | Remove user (with audit record) |
| `GET` | `/api/admin/invites` | List invites (optional `?status=` filter) |
| `POST` | `/api/admin/invites` | Create email invite or shareable code |
| `DELETE` | `/api/admin/invites/:codeHash` | Revoke invite |

All admin routes verify the `admin` group claim from the server-side JWT on every request —
never trust client-supplied headers.

### Security notes

- **Invite codes hashed at rest**: `sha256(rawCode)` in PK; raw code is only ever in memory
  during generation and in the HTTP response (returned once). If the `Invites` table is
  compromised, codes cannot be reversed.
- **Single-use atomicity**: the Post-Confirmation Lambda uses a DynamoDB conditional write
  (`usedCount < maxUses`) so two simultaneous redemptions of the same single-use code cannot
  both succeed.
- **Admin gate on every route**: all `/api/admin/**` route handlers call a shared
  `requireAdminGroup(request)` helper that verifies the `cognito:groups` JWT claim.
  `proxy.ts` also blocks at the edge — two layers.
- **No email enumeration on invite validation**: `POST /api/auth/invite/validate` returns
  `{ valid: false }` for any failure (expired, revoked, wrong email) without distinguishing
  the failure reason.
- **Resend "from" address**: `INVITE_FROM_ADDRESS` must be a verified domain sender in
  Resend. Fail loudly at deploy if unset.
- **Rate limiting**: covered above (10/15 min per IP on redemption, 20/min per admin on
  invite creation).
- **Admin actions require confirmation**: remove-member and approve-all require UI
  confirmation (`ADialog`) to prevent accidental destructive actions.
- **Audit trail**: rejected users and removed members leave an audit record in DynamoDB;
  revoking an invite sets `auditNotes`. Not surfaced in the UI yet but queryable.

## Risks / open questions

- **Resend sender verification**: `INVITE_FROM_ADDRESS` must be a verified sender in Resend.
  For `pr-<N>` stages the fallback Console environment can point to a verified test address
  (e.g. a no-reply alias on the domain). Confirm before M3 starts.
- **Cognito `AdminAddUserToGroup` latency**: calling this from both the Lambda (at
  registration) and the server-side approve route means group membership changes must be
  eventually consistent with the JWT. The JWT is issued at sign-in and has a fixed lifetime
  (default 1 hour). An approved user must sign out and back in to pick up the `member`
  group in their token. Decide whether to show an in-app prompt ("Please sign in again to
  activate your access") or to rely on a short token lifetime.
- **DynamoDB table count**: adding `Invites` and `Groups` increases the table count per
  stage. AWS default per-account limit is 2 500 tables but there is a soft limit on active
  tables in some regions. Confirm the account limit before deploying many ephemeral PR stages
  in parallel.
- **`AdminAddUserToGroup` IAM for the application Lambda**: the application Next.js function
  (not just the Post-Confirmation Lambda) now also needs `cognito-idp:AdminAddUserToGroup`
  and `cognito-idp:AdminRemoveUserFromGroup` for the approve/role-change routes. Confirm
  these are granted in `infra/application.ts`.
- **Resend email in E2E**: the E2E suite cannot actually receive emails. Options: (a) mock
  the Resend SDK at the test layer; (b) use Resend's test mode / sandbox; (c) intercept the
  HTTP call with a Playwright route handler. Decide before sub-issue 10.
- **Group names for invite hints**: the M2 `/api/auth/invite/validate` endpoint returns
  `groupName`. With M3 in place, derive the name from the `Groups` table via `groupId` on
  the invite. Ensure the `Groups` table has at least one seeded group in the E2E `globalSetup`
  so the hint resolves correctly.
- **"Approve all" atomicity**: the "Approve all" button in `AdminPending` calls the approve
  route for each pending user sequentially. If one call fails mid-batch, the remaining users
  are not approved. Consider a `POST /api/admin/users/approve-all` batch endpoint, or
  document that "Approve all" is best-effort and the admin should retry on partial failure.
