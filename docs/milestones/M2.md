# M2 · Auth & onboarding

> Size: L · Depends on: M0 (monorepo skeleton), M1 (marketing site)

## Goal

Deliver the authentication and onboarding layer for `app.transformmynotes.com`. This covers:
wiring the Cognito user pool (provisioned per-stage by `infra/auth.ts`) to the Next.js
application via Amplify Auth and `proxy.ts`; the login, forgot/reset-password, request-access,
and request-received screens (ported from the design files); the DynamoDB `UserData` table that
stores each user's profile and approval status; and an `AccessRequests` capture so prospective
users can ask for access.

### Account model (locked decision)

**There is NO public self-service signup anywhere in the product.** The Cognito user pool stays
`allowAdminCreateUserOnly: true` — the public Cognito `SignUp` API is disabled. Accounts come
into existence in exactly these ways:

- **Admin accounts** — created manually by an operator in the AWS Cognito console (see the
  bootstrap-admin runbook), then added to the `admin` group.
- **User (member) accounts** — created in any of three admin-driven ways: (a) manually by an
  admin in the Cognito console; (b) from the application's **Admin Panel** (an admin creates the
  user in-app via server-side Cognito admin APIs — `AdminCreateUser` etc.); or (c) via an
  **invite** redemption flow. Both the Admin Panel and the invite flow are **M3** work (they need
  the admin UI and the `Invites` table), so M2 does not ship a working in-app account-creation or
  invite-redemption path.

Because nobody can self-register, the public-facing onboarding surface is a **Request Access**
page: a prospective user submits their name + email; the submission is captured as an
`AccessRequest` record (it does **not** create any Cognito account). An admin later reviews the
request in the **Admin Panel** (M3) and provisions the person — approving a request there creates
the user account (Cognito console, in-app Admin Panel create, or invite). M2 only *captures* the
request and shows a "request received" confirmation; the review/approve queue is M3.

## Out of scope

- **Any public self-service signup / account creation** (locked out by the account model above).
- Invite **creation** and the full invite data model (M3). Invite **redemption** (turning a
  valid invite into a Cognito account) also lands with / after M3, since it needs the `Invites`
  table.
- The application **Admin Panel** — both creating users in-app (server-side `AdminCreateUser`)
  and the queue that reviews/approves `AccessRequests` (M3).

- Email address change after registration; account deletion self-service.
- Group / course assignment (M3).

## Architecture & decisions

### Data model — `UserData` table (existing)

Defined in `infra/db.ts`. Generic single-table (`pk`/`sk` + `GSI1` on `gsi1pk`/`gsi1sk`).
Holds two item kinds: **user profiles** and **access requests**.

**User profile item** (one per Cognito sub):

| Key | Value | Purpose |
|---|---|---|
| `pk` | `USER#<cognitoSub>` | Primary lookup by Cognito sub |
| `sk` | `PROFILE` | Static discriminator |
| `gsi1pk` | `STATUS#<status>` | List users by status (`STATUS#pending`, `STATUS#active`, `STATUS#disabled`) |
| `gsi1sk` | `<ISO-8601 createdAt>` | Time-ordered within status |

Attributes: `sub`, `email`, `name`, `status` (`pending|active|disabled`), `role`
(`admin|member`), `groupIds` (string[]), `noteCount` (number), `createdAt`, `updatedAt`.
Builders: `userDataKeys.profile`, `userDataKeys.statusIndex`, `userDataKeys.listByStatus`
(already present).

**Access request item** (one per submitted request):

| Key | Value | Purpose |
|---|---|---|
| `pk` | `ACCESSREQ#<id>` | Primary lookup by request id (uuid) |
| `sk` | `REQUEST` | Static discriminator |
| `gsi1pk` | `ACCESSREQ_STATUS#<status>` | List requests by status (`new`, `approved`, `dismissed`) |
| `gsi1sk` | `<ISO-8601 createdAt>` | Time-ordered within status, for the admin queue |

Attributes: `id`, `email`, `name`, `note` (optional string), `status` (`new|approved|dismissed`),
`createdAt`, `updatedAt`. New builders to add in `keys.ts`:
- `accessRequestKeys.request(id)` → `{ pk: 'ACCESSREQ#<id>', sk: 'REQUEST' }`
- `accessRequestKeys.statusIndex(status, createdAt)` → `{ gsi1pk, gsi1sk }`
- `accessRequestKeys.listByStatus(status)` → GSI1 KeyConditionExpression (admin queue, M3)

> An access request is **not** a user. It carries no Cognito sub and grants nothing — it is a
> lead for an admin to act on. Storing it in the same table is purely to avoid a second table;
> the `ACCESSREQ#` namespace keeps it isolated from `USER#` profiles.

### Cognito pool & the (dormant) Post-Confirmation Lambda

`infra/auth.ts` provisions the pool with `allowAdminCreateUserOnly: true`. The
Post-Confirmation Lambda (`packages/core/src/handlers/post-confirmation.ts`) is **retained** but
**effectively dormant in M2**: it only fires on `PostConfirmation_ConfirmSignUp`, which the
public `SignUp` flow would trigger — and that flow is disabled. It is kept in place for the M3
invite-redemption flow (if redemption ends up using a signUp-style confirmation) and does no
harm while dormant.

**Consequence to resolve in the proxy/gating work:** a user created directly in the Cognito
console does **not** go through `SignUp`, so no Lambda writes their `UserData` profile. Their
profile must therefore be created another way — e.g. lazily on first authenticated request in
`proxy.ts` / a server action, or by a Post-Authentication / Pre-Token-Generation trigger.
This is called out as an open question under the `proxy.ts` gating sub-issue.

### Amplify Auth client config

`packages/application` reads `Resource.Auth.userPoolId` / `Resource.Auth.clientId` and exposes
them as `NEXT_PUBLIC_COGNITO_USER_POOL_ID` / `NEXT_PUBLIC_COGNITO_CLIENT_ID`. Amplify Auth is
configured once at the app root. (Shipped M2.3.) No `sst.Secret` is needed — these are public
identifiers. There is no client `signUp` call anywhere in the app.

### `proxy.ts` route gating

`packages/application/proxy.ts` (the existing auth middleware) is extended:

- **JWT verification**: already done via `aws-jwt-verify`. No change.
- **Notebook routes** (`/dashboard`, `/notes/**`, `/review/**`, `/account`): after verifying the
  JWT, read the `UserData` profile by the `sub` claim. If the profile is missing, create it (see
  the open question above) or treat as not-yet-active. If `status !== 'active'` redirect to a
  "not active yet" view. Cache the profile per request to avoid a DB read per asset.
- **Admin routes** (`/admin/**`): check `cognito:groups` from the verified JWT contains `admin`.
  If not, redirect to `/dashboard`. Never trust a client-supplied role.
- **Auth/public pages** (`/login`, `/forgot-password`, `/reset-password`, `/request-access`,
  `/pending`): if a valid `active` session is present, redirect to `/dashboard`. `/request-access`
  and `/pending` are reachable while unauthenticated.

### Request Access flow

- **`/request-access`** (client page): name + email (+ optional short note) → `POST
  /api/auth/request-access`.
- **`POST /api/auth/request-access`** (server route): rate-limited; validates input; writes an
  `AccessRequest` item (`status: 'new'`) via the `accessRequestKeys` builders. Returns a generic
  `{ ok: true }` regardless of whether the email already has an account/request (no enumeration).
- On success the page routes to **`/pending`** (request-received confirmation), passing the email
  for display. `/pending` shows the `PendingApproval` three-step timeline reframed as "request
  received → admin review → access granted" and a "Back to sign in" link.

### API routes

- `POST /api/auth/request-access` — captures an access request (writes `AccessRequest`).
  Rate-limited. Always returns a generic success (no email enumeration).
- No `signUp` / `register` / `invite/validate` routes in M2 (invite validation is M3).
- No server-side route for login / forgot-password — those are pure Amplify client calls.

### Security notes

- **No enumeration**: `POST /api/auth/request-access` returns the same generic success whether or
  not the email already has an account or a prior request. Login errors stay generic too.
- **Rate limiting**: `POST /api/auth/request-access` is rate-limited server-side (e.g. 10 req /
  15 min per IP) via a shared `packages/application/lib/ratelimit.ts` utility, so the public
  endpoint can't be used to flood the requests table.
- **Admin group gate is JWT-claim-based**: always read `cognito:groups` from the verified
  server-side JWT in `proxy.ts`; never trust a client header.
- **CSRF**: Amplify Auth + App Router server actions use `SameSite` cookies; no extra token
  needed. The request-access endpoint is unauthenticated and idempotent-ish (capture only).
- **Password policy** (login / reset): Cognito's built-in min-8-characters rule, surfaced via the
  DS `PasswordField` hint.

### Bootstrap-admin manual runbook (no code — documented task only)

One-time, per-stage step in the AWS Cognito console (NOT automated):

1. Cognito console → User Pools → select the pool for the target stage.
2. "Users" tab → **Create user**. Username (email), email marked verified, temporary password.
3. Sign in to the app with the temporary password; complete the forced password change.
4. Cognito console → Users → the user → "Group memberships" → **Add user to group** → `admin`.
5. In the `UserData` table for the stage, create/seed the admin's profile item
   (`pk=USER#<sub>`, `sk=PROFILE`) with `status=active`, `role=admin`. (Console-created users
   have no profile written automatically — see the proxy/gating open question for the longer-term
   automatic-creation approach.)
6. Sign in again — full admin access.

Member accounts are created the same way (steps 1–3, skip the `admin` group, `role=member`) or
via the M3 invite flow. For ephemeral `pr-<N>` stages used only for automated testing, the E2E
harness seeds the test user via `cognito-local` and skips this runbook.

## Risks / open questions

- **Profile creation for console-created users**: no `SignUp` ⇒ no Post-Confirmation ⇒ no
  auto-written `UserData` profile. Resolve in the proxy/gating sub-issue (lazy create vs. an
  auth-time Lambda). Until then, the bootstrap runbook seeds the profile by hand.
- **Server-side account creation under an admin-only pool**: with public `signUp` disabled, every
  user account is minted server-side via Cognito admin APIs (`AdminCreateUser` +
  `AdminSetUserPassword`). Both the M3 **Admin Panel** "create user" action and the M3 invite
  redemption route share this mechanism. M3 work (Admin Panel + `Invites` table); flagged here so
  M3 plans for it.
- **Access requests go nowhere visible until M3**: M2 only captures requests; the Admin Panel queue
  that reviews/approves them (and creates the account) + optional email notification land in M3.
  Acceptable because the data is captured durably.
- **`cognito-local` fidelity**: triggers don't emulate identically; the (dormant) Lambda and the
  M3 invite flow should be validated on a real `pr-<N>` pool, not only `cognito-local`.

## Manual test plan

Perform on the deployed `pr-<N>` stage (URL in the CI run summary). Flows start at
`https://app.<pr-N-domain>/`.

1. **Login — happy path.** `/login` with bootstrap-admin credentials → `/dashboard`.
2. **Login — wrong password.** Valid email + wrong password → generic inline error (no "user not
   found" / "email not registered").
3. **Forgot password.** `/login` → "Forgot password?" → enter admin email → reset code sent
   (check `cognito-local` logs / inbox) → complete on `/reset-password` → sign in with new password.
4. **Request access.** `/request-access` → fill name + email → "Request access" → lands on
   `/pending` with the "request received" timeline and the submitted email shown. Confirm an
   `AccessRequest` item exists in the `UserData` table (DynamoDB console / CLI) with `status:'new'`.
5. **No signup exists.** Confirm there is no path in the app that calls Cognito `signUp`; visiting
   any old `/register` URL does not present an account-creating form.
6. **Admin route gate — non-admin.** Sign in as a `member` → attempt `/admin/pending` → redirected
   to `/dashboard`.
7. **Admin route gate — admin.** Sign in as bootstrap admin → `/admin/pending` renders (may be
   empty until M3).
8. **Request-received "Back to sign in".** On `/pending`, click "Back to sign in" → `/login`.
9. **Mobile layout.** Login + request-access at 390 px wide → no horizontal scroll; touch targets
   ≥ 44 px; typography/spacing match the mobile-first design.
