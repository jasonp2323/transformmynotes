# M2 · Auth & onboarding

> Size: L · Depends on: M0 (monorepo skeleton), M1 (marketing site)

## Goal

Deliver the complete authentication and onboarding layer for `app.transformmynotes.com`. This
covers: wiring the Cognito user pool (provisioned per-stage by `infra/auth.ts`) to the Next.js
application via Amplify Auth and `proxy.ts`; the login, registration, pending-approval, and
invite-accept screens (ported from the design files); and the DynamoDB `UserData` table that
stores each user's profile and approval status.

Registration has two tracks that share a single page: (1) **self-registration** — user submits
name/email/password with an optional invite-code field left blank, Cognito creates the account,
a Post-Confirmation Lambda writes a profile with `status=pending`, and the user lands on the
pending-approval screen; (2) **invite-based registration** — a valid invite code is provided
inline (or the user arrives via a deep-link `/invite?code=…&email=…`), the invite is validated
server-side on submit, and on success the user is immediately added to the Cognito `member`
group and their profile is set to `status=active`, bypassing the admin queue.

## In scope

- `infra/auth.ts` additions: Post-Confirmation Lambda trigger wired to the user pool; IAM grant
  so the Lambda can write to the `UserData` table.
- `infra/db.ts`: `UserData` table definition (PK + GSI1) and its links in `infra/application.ts`.
- `packages/core/src/db/keys.ts`: key builders for UserData (profile lookup by sub, GSI query
  for pending queue).
- `packages/core/test/`: dynalite integration tests for all new UserData access patterns.
- `proxy.ts` route gating: notebook routes (`/dashboard`, `/notes/**`, `/review/**`, `/account`)
  require `status=active` (checked against DynamoDB, not Cognito attributes); admin routes
  (`/admin/**`) require membership in the Cognito `admin` group (checked from the JWT
  `cognito:groups` claim).
- Login page (`/login`) — both `LoginCalm` and `LoginBranded` variants, settling on one for
  production (recommend `LoginBranded`).
- Registration page (`/register`) — ported from `RegisterInline`; inline optional invite-code
  field with live validation feedback.
- Invite-accept page (`/invite`) — ported from `InviteAccept`; email and code locked, set name
  + password.
- Pending-approval screen (`/pending`) — ported from `PendingApproval`; shown after
  self-registration completes.
- Forgot-password flow: initiate (`/forgot-password`) and confirm-reset (`/reset-password`)
  pages using Cognito's built-in `forgotPassword` + `confirmResetPassword` Amplify calls.
- Bootstrap-admin manual runbook (documented in this spec, no code).
- E2E Playwright tests (authed suite, `e2e/application/`) covering login, self-registration
  (pending path), and invite-accept (active path).

## Out of scope

- Admin panel UI (M3).
- Invite creation and full invite data model (M3); M2 only *validates* existing invites on
  redemption (reading from the `Invites` table that M3 will write).
- Social / OAuth sign-in providers.
- Email address change after registration.
- Account deletion self-service.
- Group / course assignment beyond what an invite carries (M3).

## Architecture & decisions

### Data model — `UserData` table

Defined in `infra/db.ts`. Single-table; one item per user.

| Key | Value | Purpose |
|---|---|---|
| `PK` | `USER#<cognitoSub>` | Primary lookup by Cognito sub |
| `SK` | `PROFILE` | Static discriminator |
| `GSI1PK` | `STATUS#<status>` | List users by status (`STATUS#pending`, `STATUS#active`, `STATUS#disabled`) |
| `GSI1SK` | `<ISO-8601 createdAt>` | Time-ordered within status (newest last; flip for newest-first scan) |

Attributes: `sub` (string), `email` (string), `name` (string), `status` (enum:
`pending|active|disabled`), `role` (enum: `admin|member`; mirrors the Cognito group, kept in
sync on role changes in M3), `groupIds` (string[], groups/courses the user belongs to),
`noteCount` (number, maintained by note write events), `createdAt` (ISO-8601), `updatedAt`
(ISO-8601).

GSI name: `GSI1` — `GSI1PK` (HASH) + `GSI1SK` (RANGE). Used by the admin pending queue to
list `STATUS#pending` items in chronological order.

Key builders in `packages/core/src/db/keys.ts`:
- `userProfileKey(sub)` → `{ PK: 'USER#<sub>', SK: 'PROFILE' }`
- `statusIndexKey(status, createdAt)` → `{ GSI1PK: 'STATUS#<status>', GSI1SK: '<createdAt>' }`
- `listByStatus(status)` → KeyConditionExpression for GSI1 scan

### Post-Confirmation Lambda

Deployed as a Lambda function (defined in `infra/auth.ts` or a new `infra/post-confirm.ts`)
and wired as the user pool's Post-Confirmation trigger. On every `ConfirmSignUp` event it:

1. Reads the invite code from the Cognito `custom:inviteCode` user attribute (set by the client
   at sign-up if the user supplied one).
2. If an invite code is present: validates it against the `Invites` table (M3 writes these; the
   Lambda must handle the case where the table doesn't exist yet — treat missing table as
   "no valid invite"). If the invite is valid and not expired/used/revoked: marks the invite
   used (atomic conditional write), sets user `status=active`, calls
   `AdminAddUserToGroup('member')`.
3. If no valid invite: sets user `status=pending`, does NOT add to any Cognito group.
4. In both cases writes the `UserData` profile item (PK=`USER#<sub>`, SK=`PROFILE`) with all
   attributes.

The Lambda is given IAM permissions to `dynamodb:PutItem` on `UserData`, `dynamodb:GetItem` +
`dynamodb:UpdateItem` on `Invites` (read-ahead for M3), and
`cognito-idp:AdminAddUserToGroup` on the user pool.

**Important:** the Lambda must not throw on any error that would block Cognito confirmation —
wrap the entire body in try/catch and log failures; the user is confirmed regardless.

### Amplify Auth client config

`packages/application` reads `Resource.Auth.userPoolId` and `Resource.Auth.clientId` (from
the `sst.Resource` binding set in `infra/application.ts`) and exposes them as
`NEXT_PUBLIC_COGNITO_USER_POOL_ID` and `NEXT_PUBLIC_COGNITO_CLIENT_ID`. Amplify Auth is
configured once at the app root (`app/layout.tsx`) with `Amplify.configure({ Auth: { ... } })`.
No `sst.Secret` is needed for these values — they are public identifiers.

### `proxy.ts` route gating

`packages/application/proxy.ts` (the existing auth middleware) is extended:

- **JWT verification**: already done via `aws-jwt-verify`; pool id + client id from
  `sst.Resource`. No change needed.
- **Notebook routes** (`/dashboard`, `/notes/**`, `/review/**`, `/account`): after verifying
  the JWT, read the `UserData` profile from DynamoDB by the `sub` claim. If `status !== 'active'`
  redirect to `/pending`. Cache the profile in the request context (edge-compatible: use
  `Next.js` middleware headers or a short-lived server-side cache) to avoid a DB read per
  request.
- **Admin routes** (`/admin/**`): check `event.idToken.payload['cognito:groups']` contains
  `'admin'`. If not, return 403 (or redirect to `/dashboard`). Do NOT rely on the DynamoDB
  `role` field for the gate — always use the Cognito group claim from the verified JWT.
- **Auth pages** (`/login`, `/register`, `/invite`, `/forgot-password`, `/reset-password`,
  `/pending`): if a valid JWT is present and `status=active`, redirect to `/dashboard`.
- `/pending`: accessible to any authenticated user regardless of status (needed to show the
  waiting screen).

### Infra changes

- `infra/auth.ts`: add `postConfirmation` trigger pointing to the Lambda.

- `infra/application.ts`: link `UserData` table to the application; grant Lambda IAM as above.
- No new `sst.Secret` entries for auth (Cognito identifiers come from `sst.Resource`).

### API routes

- `POST /api/auth/register` — validates invite code existence (not full redemption; that happens
  in the Lambda). Returns `{ valid: boolean, groupName?: string }` for inline feedback without
  leaking whether the email is registered. Rate-limited (see security notes).
- `POST /api/auth/invite/validate` — given `{ code, email }` returns `{ valid, groupName,
  inviterName, expiresAt }` for pre-populating the `/invite` accept page.
- No server-side route for login/forgot-password — those are pure Amplify client calls.

### Security notes

- **No email enumeration**: registration errors never distinguish "email already registered"
  from any other error. The endpoint always returns a generic message on failure.
- **Invite codes hashed at rest**: the M3 `Invites` table stores `sha256(code)` as the PK.
  The Lambda and `/api/auth/invite/validate` hash the user-supplied code before lookup —
  the raw code never touches DynamoDB.
- **Rate limiting**: `POST /api/auth/register` and `POST /api/auth/invite/validate` are
  rate-limited server-side (e.g. 10 req / 15 min per IP) using an in-memory sliding window
  or a DynamoDB counter item. Implement in a shared `packages/application/lib/ratelimit.ts`
  utility.
- **Admin group gate is JWT-claim-based**: never trust a client-supplied role header; always
  read `cognito:groups` from the verified server-side JWT in `proxy.ts`.
- **CSRF**: Amplify Auth and Next.js App Router server actions both use `SameSite=Strict`
  cookies; no additional CSRF token needed for the auth flows.
- **Password policy**: enforce Cognito's built-in minimum-8-characters rule; surface the error
  message ("At least 8 characters.") from the DS `PasswordField` hint.

### Bootstrap-admin manual runbook (no code — documented task only)

This is a **one-time, per-stage manual step** performed in the AWS Cognito console (or via the
AWS CLI) immediately after the first deploy of a stage. It is NOT automated:

1. Open the AWS Cognito console → User Pools → select the pool for the target stage.
2. In the "Users" tab click **Create user**. Fill in: username (email), email (mark as
   verified), temporary password. Click Create.
3. Sign in to the app with the temporary password; Cognito will prompt a password change —
   complete it.
4. Back in the Cognito console → Users → click the user → "Group memberships" →
   **Add user to group** → select `admin`. Click Save.
5. In the DynamoDB console (or via the AWS CLI) find the `UserData` table for the stage. The
   Post-Confirmation Lambda will have written a profile with `status=pending`. Update that
   item: set `status` to `active` and `role` to `admin`.
6. Sign in again — the user now has full admin access.

Repeat for each stage (`production`, and any long-lived `pr-<N>` that needs an admin). For
ephemeral `pr-<N>` stages used only for automated testing, the E2E harness seeds the test user
via `cognito-local` and skips this runbook.

## Risks / open questions

- **Lambda cold starts in middleware**: the `proxy.ts` DynamoDB read for `status` adds latency
  on every notebook request. Mitigate: consider storing `status` as a Cognito custom attribute
  (set by the Lambda) so `proxy.ts` can read it from the JWT claim without a DB round-trip —
  evaluate during implementation.
- **Email verification UX**: Cognito's built-in email verification sends a 6-digit code. The
  design doesn't include a verify-email screen; a simple numeric-code input screen needs to be
  designed inline with the DS.
- **`cognito-local` fidelity**: `cognito-local` doesn't emulate all Cognito Lambda trigger
  behaviours identically. The Post-Confirmation Lambda should be tested against a real
  `pr-<N>` pool, not only `cognito-local`, before M2 is marked Done.
- **Invite table dependency**: the Post-Confirmation Lambda reads the `Invites` table (defined
  in M3). For M2, the Lambda must gracefully handle the table not yet existing — treat as
  "no valid invite" and set `status=pending`.
- **Group/course name in hints**: the inline registration code-field shows "you'll join
  <group>". This requires the `/api/auth/invite/validate` endpoint to return `groupName`.
  For M2, `groupName` can be a stub ("your group") if the Groups table is not yet populated
  by M3.

## Manual test plan

Perform the following on the deployed `pr-<N>` stage (URL surfaced in the CI run summary).
All flows start at `https://app.<pr-N-domain>/`.

1. **Login — happy path**
   Navigate to `/login`. Enter the bootstrap-admin credentials. Click "Sign in".
   _Expected_: redirected to `/dashboard` with the admin navigation visible.

2. **Login — wrong password**
   Navigate to `/login`. Enter a valid email and a wrong password. Click "Sign in".
   _Expected_: inline error message appears; message does not say "user not found" or
   "email not registered" (no enumeration).

3. **Forgot password**
   Navigate to `/login`, click "Forgot password?". Enter the admin email. Click "Send reset link".
   _Expected_: success message; Cognito sends a reset code (check `cognito-local` logs or
   real email inbox). Complete reset on `/reset-password`. Sign in with new password.

4. **Self-registration (no invite code) — pending path**
   Navigate to `/register`. Fill name, email (a fresh address), password. Leave invite code
   blank. Click "Request access".
   _Expected_: verify-email code screen appears. Enter the 6-digit code. Redirected to
   `/pending` — three-step timeline visible with "Admin review" active. Attempting to navigate
   to `/dashboard` redirects back to `/pending`.

5. **Registration with valid invite code — active path**
   (Requires a test invite code — create one via DynamoDB directly for M2, or use the M3
   admin panel once available.) Navigate to `/register`. Fill name, email, password. Enter a
   valid invite code. Inline hint updates to "Valid — you'll join <group> right away." Click
   "Join <group>". Complete email verification.
   _Expected_: redirected directly to `/dashboard` (not `/pending`); user's Cognito group
   membership includes `member`.

6. **Invite-accept deep link**
   Navigate to `/invite?code=<VALID_CODE>&email=<email>`. Observe locked email + code fields.
   Fill name + password. Click "Accept & create account".
   _Expected_: account created, immediately `active`, redirected to `/dashboard`.

7. **Admin route gate — non-admin**
   Sign in as a regular `member` user. Attempt to navigate to `/admin/pending`.
   _Expected_: redirected to `/dashboard` (or 403 page); no admin content visible.

8. **Admin route gate — admin**
   Sign in as the bootstrap admin. Navigate to `/admin/pending`.
   _Expected_: pending queue renders (may be empty at this stage).

9. **Pending screen sign-out**
   While on `/pending`, click "Back to sign in".
   _Expected_: session cleared, redirected to `/login`.

10. **Mobile layout**
    Open the login and registration pages on a 390 px wide viewport (iPhone 14 equivalent).
    _Expected_: no horizontal scroll; touch targets ≥ 44 px; typography and spacing match
    the mobile-first design screens.
