# M22.4 · Decision gate — static export / SPA decouple (architecture fork)

> **Status:** DECIDED — **NO-GO** (do not pursue the static-export / SPA fork now) · 2026-06-19
> **Phase:** M22.4 of `docs/milestones/M22.md` (Offline support) · Issue #496
> **Scope of this doc:** M22.4.1 (spike + go/no-go). M22.4.2 / M22.4.3 were the
> *conditional* follow-ons "(if go)"; the decision below means they are **not
> scheduled** (see "Consequences").

---

## 1. The question

Phase 4 asked whether to move the authed app (`packages/application`) from its
current **SSR-on-Lambda** model to a **static export (`output: 'export'`) /
client-rendered SPA**, so the Capacitor Android app could be shipped as a
**bundled `webDir`** and launch with **zero network**. That is the *only* path to
a true cold-start-offline launch (today the WebView loads
`https://app.transformmynotes.com` via `server.url`).

The phase was deliberately decision-gated because this is a **product-wide
architecture fork**, not a mobile-only tweak.

## 2. Decision (TL;DR)

**NO-GO.** Do not convert the application to a static export / SPA at this time.

The static-export fork is an **XL, multi-milestone, product-wide rewrite** of the
app's auth, rendering, API hosting, and security-header model, and it **directly
sacrifices the #1 design constraint of M22** — "every web deploy is instantly
live in the app" (`server.url`). The marginal benefit it buys (instant
*cold-start* with zero network) is small relative to the offline capability we
**already shipped** in M22.1–M22.3, which covers the realistic field scenario
(an already-installed, previously-opened app losing connectivity).

We will **keep the SSR + service-worker architecture**. Revisit only if the
specific trigger conditions in §8 materialise.

## 3. What we already have (and why it changes the calculus)

M22.1–M22.3 layered offline capability **on top of SSR**, with no architecture
change, and it is live today:

| Capability | Where | Shipped |
|---|---|---|
| PWA app shell + precache (Serwist) | `app/sw.ts`, `next.config.mjs:92–101` | M22.1 |
| Branded offline fallback page | `app/offline/page.tsx`, Capacitor `errorPath: 'offline.html'` | M22.1 |
| Versioned SW + enforced update prompt | `src/components/pwa/pwa-updater.tsx`, `docs/runbooks/pwa-service-worker.md` | M22.1 |
| Offline read cache (notes + library) | `src/lib/offline/readStore.ts`, SW `StaleWhileRevalidate` for `/api/notes*` | M22.2 |
| Auth-aware caches (namespaced per `sub`, purge on sign-out) | `src/lib/offline/purge.ts` | M22.2 |
| Offline mutation queue + Background Sync replay | `src/lib/offline/mutationQueue.ts`, SW `tmn-sync` | M22.3 |
| Version-guarded LWW conflict handling | mutation queue (409 → `conflict`) | M22.3 |
| Offline capture queue (defer photo→OCR) | `src/lib/offline/captureQueue.ts` | M22.3 |

**Crucially, none of this depends on the static-export choice** — the SW +
IndexedDB stack is orthogonal to SSR vs SPA. So the *incremental* value the fork
would add is narrow: a true **first-launch-with-no-network-ever** experience. For
an app that is installed once and then used repeatedly, the realistic offline
case (open it, lose signal, keep working) is **already covered**.

## 4. Option A — keep SSR + SW (status quo)

- **Architecture:** unchanged. SSR pages + 57 API routes on Lambda; Serwist SW +
  IndexedDB for offline.
- **`server.url` benefit preserved:** every `master` deploy is instantly live in
  the WebView — no app-store release, no stale bundle.
- **Auth unchanged:** server-side JWT gate in `middleware.ts` / `proxy.ts`
  (httpOnly `CognitoIdToken` cookie verified with `aws-jwt-verify`).
- **Security headers intact:** CSP-Report-Only / HSTS / X-Frame-Options etc. set
  server-side in `next.config.mjs:55–89`.
- **Offline:** everything in §3 — short of cold-start-with-zero-network.
- **Cost:** $0 incremental. Already built.

## 5. Option B — static export / SPA (the fork) — what breaks

The inventory below is the factual basis for the NO-GO. Each row is a
**load-bearing** server dependency that a static export removes.

| # | Component | Today (SSR) | Under `output: 'export'` | Severity |
|---|---|---|---|---|
| 1 | **Auth middleware gate** | `middleware.ts` + `proxy.ts` verify the Cognito JWT at the edge for `/dashboard,/notes,/review,/account,/admin,/search` (`middleware.ts:5–25`) | **Gone.** Static export has no middleware/edge runtime. Route protection must move entirely client-side. | Breaking |
| 2 | **API routes (57)** | `app/api/**/route.ts`, all `runtime='nodejs'` + `dynamic='force-dynamic'`; hit DynamoDB (`@transformmynotes/core`), S3, Bedrock, Polly, Cognito admin | Static export **emits no API routes**. All 57 must be re-hosted as a **separate backend** (API Gateway + Lambda or a standalone server). | Breaking |
| 3 | **SSR pages (~6+ async server components)** | `dashboard`, `account`, `search`, `notes/[noteId]` (+ `generateMetadata`), `login`, 5× `admin/*` read `cookies()`, call `verifyIdToken()`, query DynamoDB/S3 server-side | Must be rewritten as **client components** fetching a remote API; per-request server data fetch + `generateMetadata` from DynamoDB/S3 are not exportable. | Breaking |
| 4 | **Security headers** | `async headers()` sets HSTS, CSP-Report-Only, X-Frame-Options, Permissions-Policy (`next.config.mjs:55–89`) | `headers()` **does not run** in static export. CSP/HSTS must move to a reverse proxy/CDN config — and the planned CSP-nonce hardening (M11) assumes a server render. | Breaking (security regression risk) |
| 5 | **Server-only parser libs** | `unpdf`, `mammoth`, `epub2` declared `serverComponentsExternalPackages` (`next.config.mjs:45–47`), required at Node runtime for PDF/DOCX/EPUB ingest | Would have to be **bundled into the client** (large) or moved behind the separate API. | Major |
| 6 | **Cognito token model** | Server sets an **httpOnly** `CognitoIdToken` cookie via `/api/auth/login`; JS cannot read it; middleware verifies it | SPA must hold tokens in **JS-readable storage** (Amplify localStorage) and the separate API must do **stateless JWT validation** on every call. New XSS-exposure surface; new CSRF/refresh design. | Breaking (auth rewrite) |
| 7 | **Capacitor `webDir`** | `webDir: 'www'` + `server.url → app.transformmynotes.com` (`capacitor.config.ts:8–14`) — WebView loads the live SSR app | Switch `webDir` to the static `out/` bundle and drop `server.url`. **This is the only "easy" change — but it forces #1–#6 first.** | Config (gated by the rest) |
| 8 | **`server.url` instant-deploy** | Every `master` deploy is live in the app immediately | **Lost.** A bundled SPA ships in the app binary → app-store release cadence returns for UI changes. Directly violates M22's #1 constraint. | Breaking (product) |

### Auth-model change in detail (the real cost)

The fork is not "add `output: 'export'`". It is a **re-architecture of authn/z**:

- The current model is **server-trust**: the only thing that proves identity is an
  httpOnly cookie the client can't forge or read, verified at the edge before any
  protected page or API route runs. Remove SSR and that entire gate disappears.
- A SPA needs: (a) client-held tokens (Amplify already *can* manage these, but is
  currently **not** the source of truth — the httpOnly cookie is); (b) a separate
  always-on API that performs **stateless JWT verification per request** (so the
  57 routes' implicit "the middleware already checked you" assumption is gone and
  each must verify independently); (c) a refresh-token strategy that works inside
  a Capacitor WebView; (d) re-doing the admin flows (`AdminInitiateAuth`,
  `AdminSetUserPassword`, group management) against that API.
- Net: this is essentially **M22.4.2 ("client-token auth model")** — correctly
  sized **L** on its own — plus a security review, before any offline benefit is
  realised.

## 6. Effort estimate

| Workstream | Rough size |
|---|---|
| Client-token auth model (replace middleware gate) | **L** |
| Re-host 57 API routes as a standalone backend (or keep Next API on Lambda and point SPA at it) | **L–XL** |
| Convert ~6+ SSR pages → client + remote data fetching | **M–L** |
| Re-home security headers (CSP/HSTS) to CDN/proxy + redo CSP-nonce plan | **M** |
| Bundle/relocate PDF/DOCX/EPUB parsing | **M** |
| Static bundle + Capacitor `webDir` switch + CI (`mobile-v*`) | **L** |
| Regression + security review of the new auth surface | **M** |

**Total: XL — a milestone of its own (the spec itself flags "likely promoted to
M23").** This is not completable within M22.

## 7. Recommendation

**NO-GO.** Keep SSR + service worker. Rationale, in priority order:

1. **It breaks M22's #1 constraint.** Bundling the SPA sacrifices `server.url`
   "instant-deploy", the explicit guiding principle of the whole milestone.
2. **Low marginal benefit.** M22.1–M22.3 already deliver the realistic offline
   experience. The only thing the fork adds is *cold-start with zero network*,
   which an installed-and-used app rarely needs.
3. **High blast radius.** It rewrites auth, re-hosts 57 routes, converts SSR
   pages, and relocates security headers — XL effort with a real security
   regression risk (httpOnly → JS-readable tokens, lost server-side CSP).
4. **Not reversible cheaply.** Once auth and API hosting are decoupled, walking it
   back is itself a project.

The cost/benefit is lopsided against the fork **today**.

## 8. When to revisit (trigger conditions)

Re-open this decision (as a fresh **M23-scale** milestone) only if one of these
becomes true:

- A product requirement emerges for **true cold-start, never-been-online** use
  (e.g. shipping to users who install offline and must use it before first
  connect).
- We independently decide to **split the backend into a standalone API** for
  other reasons (then the API-hosting cost of the fork is already paid).
- Capacitor `server.url` becomes untenable (store-policy change, or the
  instant-deploy model is abandoned for another reason).

If revisited, the follow-on is the two **conditional** tasks from this phase,
promoted to their own milestone: client-token auth model (was M22.4.2) and static
bundle + `webDir` switch + CI (was M22.4.3).

## 9. Consequences / next steps

- **M22 is functionally complete** at Phase 3. Phase 4's deliverable was *this
  decision*, and it is **NO-GO**, so M22.4.2 / M22.4.3 are **not scheduled**.
- Close issue **#496** (M22.4) as resolved-by-decision; reference this doc.
- Mark the M22 epic (#497) Phase 4 done with the NO-GO outcome noted.
- No code change ships from M22.4 — the existing SSR + SW architecture stands.
