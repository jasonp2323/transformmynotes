# M23 · Admin Cost Breakdown — per-user AI & storage metering

> Size: L · Depends on: M3 (admin panel + Groups), M4 (Bedrock OCR — the first metered call site)

## Goal

Give admins a **Cost Breakdown** tab in the admin panel that shows, per user, how much
each user is costing in **AI tokens** (AWS Bedrock) and **S3 storage**, expressed both as
raw usage (tokens, bytes) and as **estimated USD**. The tab is data-forward: an admin can
slice spend by **user, group, AI model, feature, and date range**, with daily trend
charts.

The numbers are **self-metered estimates**, not AWS's actual bill. AWS billing cannot be
attributed to an individual end-user (AWS has no concept of our Cognito users), so
per-user cost must come from usage *we* record at each call site, multiplied by a
configurable **price book**. The app already extracts Bedrock `usage.inputTokens` /
`usage.outputTokens` on every OCR call (`packages/core/src/ocr/bedrock.ts`) and then
**discards them** (`packages/application/lib/transcribe/process-job.ts`); M23 captures
that data instead of throwing it away, and builds the metering + aggregation + UI around
it.

**Core principle — store quantities, derive dollars.** We persist only physical
quantities (tokens, bytes), never pre-computed USD. Dollar figures are computed at
read-time from an admin-editable price book. A price correction therefore re-prices all
history instantly with no data migration, and the same records yield both "cost in
tokens" and "cost in USD".

**Capture model — immutable event log + DynamoDB Streams aggregator.** Each metered
action writes one cheap, immutable **raw event** on the hot path. A **Streams aggregator
Lambda** rolls raw events into **daily aggregate items**. This keeps the request path to a
single `PutItem`, preserves raw events for re-aggregation, and matches the repo's existing
"jobs consume a DynamoDB stream" pattern. The aggregator is **idempotent by recompute**
(it re-sums the affected `user/day/feature/model` bucket from raw events and PUTs the
total) so at-least-once stream delivery and replays converge to the correct value rather
than double-counting.

## In scope

- A new dedicated **`Usage` DynamoDB table** (see Architecture) with a stream
  (`new-and-old-images`), linked to both `application` and `jobs`.
- Key builders in `packages/core/src/db/keys.ts` for raw events, daily aggregates, the
  storage gauge, and the price-book config item — plus parse helpers for KEYS_ONLY/GSI
  recovery. No inline key strings.
- **Price book** as an admin-editable config item (`$/1K input tokens`, `$/1K output
  tokens` per model; `$/GB-month` for S3), mirroring M19's `CONFIG#AI` pattern. Pure
  USD-calculation functions with unit tests.
- **Hot-path event capture**:
  - Thread the already-extracted Bedrock `usage` through the OCR/transcription path and
    write an AI usage event (feature, model, input/output tokens) per call. Built so any
    future Bedrock call site (M13 study generation, etc.) writes the same event with one
    helper call.
  - Record S3 object byte sizes on write (original images, note markdown) and emit a
    **storage delta** so the per-user storage gauge stays current; decrement on delete.
- **Streams aggregator job** in `infra/jobs.ts`: consumes the `Usage` stream and maintains
  daily aggregate items idempotently.
- **Daily storage-snapshot cron** in `infra/jobs.ts`: samples each user's current storage
  gauge once per day into a daily storage aggregate (so GB-month can be derived as an
  average of daily byte snapshots).
- **Admin aggregation API** under `/api/admin/cost/*` (admin-gated via
  `getAdminApiUser()`): per-user list, breakdown by model / feature / group, account-wide
  totals, all over a date range; plus a price-book read/update endpoint.
- **Cost Breakdown tab**: new sidebar nav item + `/admin/cost-breakdown` page, a charting
  library (`recharts`), filters (user / group / model / feature / date range), daily trend
  + breakdown charts, a price-book editor, responsive layout, and empty/loading/error
  states. Real browser UI test.
- Dynalite integration tests for every new access pattern (event write → aggregate
  read-back, by-day GSI cross-user query, storage gauge round-trip, idempotent
  re-aggregation).
- Unit tests for all pure logic (USD calc, GB-month derivation, aggregation/rollup
  reducers, key builders/parsers).

## Out of scope

- **AWS actual-bill reconciliation** (Cost Explorer / CUR import). The tab is
  self-metered estimates only; an account-wide "estimated vs actually billed" panel is a
  possible future follow-up, not M23.
- **Polly TTS character metering** and any non-AI/non-S3 AWS cost (DynamoDB, Lambda,
  CloudFront, data-transfer). The schema is designed generically (a new `feature` / event
  shape drops in with no migration), but only **Bedrock tokens** and **S3 storage** are
  metered in M23.
- **S3 request-count / data-transfer-out** metering (negligible vs storage + AI).
- **Per-user billing / invoicing / quota enforcement.** M23 is observability for admins,
  not a billing system and not a hard spend cap.
- **Back-filling historical cost** for data created before M23 ships (no usage events
  exist for it). Storage gauge is seeded from current object sizes going forward; an
  optional one-off back-fill script is noted as a risk, not a deliverable.
- **Exact-cent accuracy.** Figures are estimates from a configurable price book; they
  will not match the AWS invoice to the cent.

## Architecture & decisions

### New table — `Usage` (single-table, dedicated domain)

Metering is its own domain with its own access patterns and a cross-user date-partitioned
index, so it gets its own table rather than overloading `UserData`.

Defined in `infra/db.ts`; linked from `infra/application.ts` (writes events, reads
aggregates) and `infra/jobs.ts` (aggregator + snapshot cron). Stream set to
`new-and-old-images`.

Item shapes (all in one table):

- **Raw AI event** (immutable, hot-path write, TTL'd):
  - `PK = USER#<sub>`, `SK = EVT#<YYYY-MM-DD>#<ulid>`
  - attrs: `feature` (`'ocr' | 'study' | …`), `model` (model id), `inputTokens`,
    `outputTokens`, `ts` (ISO-8601), `expiresAt` (TTL, e.g. 90 days — aggregates are
    permanent, raw events are not).
  - Sparse on GSI1 (carries no `gsi1*` keys) so raw events never appear in the by-day
    aggregate index.
- **Raw storage-delta event** (immutable, hot-path write, TTL'd): same `EVT#` shape with
  `feature='storage'` and a signed `bytesDelta` (+ on write, − on delete). Drives the
  gauge update in the aggregator.
- **Storage gauge** (mutable running counter): `PK = USER#<sub>`, `SK = STORAGE#CURRENT`,
  attr `bytes` maintained via atomic `ADD`. The current bytes-stored for a user.
- **Daily aggregate** (written by the aggregator, permanent):
  - `PK = USER#<sub>`, `SK = DAY#<YYYY-MM-DD>#<feature>#<model>`
  - attrs: `inputTokens`, `outputTokens`, `calls` (AI) **or** `byteDayBytes` (storage
    snapshot for that day).
  - **GSI1 `UsageByDay`** (projection ALL): `gsi1pk = DAY#<YYYY-MM-DD>`,
    `gsi1sk = USER#<sub>#<feature>#<model>` — cross-user aggregation for a day. The admin
    API queries each day in the requested range (≤ ~31 partitions) and reduces in-app:
    by-model, by-feature, by-group (group membership resolved via the existing `Groups`
    table), and account totals all fall out of this one index. The per-user view uses the
    base table directly (`PK = USER#<sub>`, `begins_with(SK,'DAY#')` over the range).
- **Price book config** (admin-editable): `PK = CONFIG`, `SK = PRICING`, attrs: a map of
  `modelId → { inputPer1k, outputPer1k }` plus `s3PerGbMonth`. Read at query time to
  derive USD; never embedded in stored events.

### Capture & aggregation flow

1. **Hot path** (request/job): after a Bedrock call, a single `putUsageEvent()` helper
   writes one immutable `EVT#` item (fire-and-forget; a metering failure must never break
   the user-facing OCR/generation). S3 writes/deletes emit a `storage` delta event the
   same way.
2. **Stream → aggregator Lambda** (`infra/jobs.ts`): on each new `EVT#` record, the
   aggregator recomputes the affected bucket. For AI events it re-sums that
   `(user, day, feature, model)` bucket and PUTs the daily aggregate (idempotent — replays
   converge). For `storage` deltas it applies the signed delta to the `STORAGE#CURRENT`
   gauge via atomic `ADD` (delta events are processed at-least-once; dedupe by recording
   the processed event ulid on the gauge, or by making the gauge itself reconcilable from
   the snapshot cron — see Risks).
3. **Daily storage-snapshot cron** (`infra/jobs.ts`): once per day, for each active user
   (enumerated via `UserData` GSI1 `STATUS#active`), read `STORAGE#CURRENT.bytes` and
   write a `DAY#<date>#storage` aggregate. GB-month for a period = average of the daily
   byte snapshots ÷ 1e9 × `s3PerGbMonth`.
4. **Read path** (admin API): query aggregates over the date range, join the price book,
   compute USD in pure functions, return shaped data for the tab.

admin, exactly like the existing admin routes. The tab route `/admin/cost-breakdown` is
covered by the existing `(admin)` route-group gate + `proxy.ts` admin matcher.

## Risks / open questions

- **Aggregator idempotency.** Streams deliver at-least-once. AI aggregates are safe via
  recompute-and-PUT. The **storage gauge** uses atomic `ADD` on signed deltas, which is
  *not* naturally idempotent — a redelivered delta double-applies. Mitigation: dedupe by
  recording processed event ulids, or treat the daily snapshot as the source of truth and
  let the gauge self-heal. Decide in M23.3.1.
- **Storage GB-month is an approximation.** Daily snapshots averaged over the month is
  standard but not identical to AWS's continuous integration of bytes-hours; close enough
  for an estimate.
- **Hot-path safety.** Metering must be strictly fire-and-forget — a `Usage` write failure
  can never surface to the user or fail an OCR/generation job. Enforced in
  `putUsageEvent()`.
- **No historical back-fill.** Cost starts accumulating at ship time; pre-M23 data has no
  events. An optional one-off script could seed the storage gauge from current S3 object
  sizes — out of scope unless requested.
- **Model id churn.** The price book is keyed by model id; M19's runtime-configurable
  model selection means new model ids can appear. Unknown-model events should fall back to
  a default rate and surface an "unpriced model" warning in the tab rather than silently
  costing $0.
- **Future categories.** Polly (M18) and other AWS costs are deliberately deferred; the
  generic `feature` dimension means they slot in later without a schema change.
