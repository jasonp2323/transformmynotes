# M28 · AI Activity UI

> Size: XL · Depends on: M13 (study-gen job pipeline), M4 (transcription/OCR job), M18 (TTS synthesis), M19 (admin AI-settings panel — Collapsible reuse)

## Goal

Make the app **show what the AI is actually doing in the background**. Today the only
feedback during AI work is a single-line "Generating your flashcards…" banner inside the note
view (`GenerateStudyMaterial.tsx`), driven by one `status` field (`queued → running →
ready/failed`) polled every 2s — and it vanishes the moment you navigate away.

M28 replaces that with a **global, collapsible AI-activity indicator** anchored in the authed
app shell. It is **collapsed by default**, showing a one-line subject of what the AI is
currently doing ("Writing your flashcards"). Expanding it reveals a **truthful, per-job phase
breakdown**: the current phase, a timestamped step-history log, progress (e.g. "section 3 of
5"), and — for LLM generations — the **live streamed model output**. It tracks **all** of the
user's in-flight AI work (study generation, transcription/OCR, and TTS), survives navigation,
and disappears when nothing is running.

To make the expanded detail real rather than cosmetic, the backend records granular phase +
step-history data as each job progresses, and LLM jobs stream their tokens to a buffer the
client can tail over SSE.

## In scope

- A **unified `ACTIVITY` DynamoDB item** (new access pattern) that every AI pipeline writes to:
  one record per job, carrying `kind`, `status`, `phase`, `phaseDetail`, `progress`, a
  timestamped `steps[]` history, and a TTL. One discovery query, one UI shape for all kinds.
- **Phase + step-history tracking on all three AI pipelines**: study generation
  (`jobs/study-generation.ts`), transcription/OCR (`lib/transcribe` job), and TTS synthesis
  (`/api/audio/synthesize`).
- **Activity API**: `GET /api/activity` (the user's in-flight + recent activities) and
  `GET /api/activity/[id]` (one activity's detail + full step history).
- **Live token streaming (approach A — SSE relay over a buffer)**: LLM jobs (study-gen,
  transcription/OCR) switch to a streaming Bedrock call and flush token batches to a per-activity
  S3 buffer; a new `GET /api/activity/[id]/stream` SSE route tails that buffer and relays deltas
  to the client's `EventSource`. The durable async-job model is unchanged — streaming is a live
  "peek" layered on top, not a replacement.
- **Frontend**: a reusable `Collapsible` design-system primitive; an `AiActivityProvider` +
  global `AiActivityIndicator` (collapsed chip → expanded per-activity panels with phase,
  step-history, progress, and live output); generate/transcribe/TTS triggers register their job
  with the provider so the indicator appears immediately.
- **Wire the new `Collapsible` into the M19 admin AI-settings version-history panel** (replacing
  its current placeholder).
- Tests: unit tests for the ACTIVITY key builders + phase/step helpers; a dynalite integration
  test for the activity write→discover→detail round-trip; browser UI tests for the indicator
  (collapsed/expanded, multi-job, live output) and the M19 panel.

## Out of scope

- **AI work other than the three named pipelines.** Only study-gen, transcription/OCR, and TTS
  report activity in M28; any future AI surface opts in by writing an `ACTIVITY` item.
- **Approach B (true in-request streaming).** We explicitly keep the background-job architecture
  and relay from a buffer (approach A). Moving the model call into a long-held SSE request is a
  separate future decision.
- **Token-by-token fidelity.** The streamed view updates at the buffer-flush cadence
  (~0.5–1 s batches), not strictly one token at a time.
- **A persistent activity history page / audit view.** `ACTIVITY` items are short-lived (TTL ~24h)
  and surfaced only through the live indicator; a durable "past activity" page is out of scope.
- **Cancelling a running job from the indicator.** The panel observes; it does not control. A
  cancel affordance is a follow-up.
- **WebSocket / AppSync push infrastructure.** Discovery stays on the existing poll model; only
  the live-output channel uses SSE (HTTP, no new transport infra).
- Changing the generation algorithms, prompts, SM-2 scheduling, or the study/transcription/TTS
  output formats themselves.

## Architecture & decisions

### Unified `ACTIVITY` item (new access pattern)

One record per AI job, written by whichever pipeline owns the work. Shared shape =
single discovery query + single UI contract.

```
PK  = USER#<sub>
SK  = ACTIVITY#<ulid>          (ULID ⇒ lexicographic sort == chronological)
Attributes:
  activityId    string                                   — the ULID
  kind          'study' | 'transcription' | 'tts'
  refId         string                                   — studySetId / transcriptionJobId / audio id
  status        'queued' | 'running' | 'ready' | 'failed'
  phase         string                                   — machine phase id (kind-specific enum)
  phaseDetail   string                                   — server-authored human subject line
  progress?     { current: number; total: number }       — e.g. map-reduce chunk 3 of 5
  steps         Array<{ phase: string; detail: string; at: string }>   — timestamped history
  title         string                                   — what's being produced ("Flashcards from 3 notes")
  error?        string                                   — only when status = 'failed'
  stream?       { s3Key: string; done: boolean }          — present for LLM kinds once streaming starts
  ttl           number                                    — epoch seconds, ~24h out (DynamoDB TTL)
  createdAt     string                                    — ISO-8601
  updatedAt     string                                    — ISO-8601
```

**Discovery — no new GSI.** The global indicator lists the user's activities with a base-table
query `PK = USER#<sub>` + `begins_with(SK, 'ACTIVITY#')`, `ScanIndexForward: false` (newest
first). In-flight = same query with a `FilterExpression` on `status IN (queued, running)` —
exactly mirroring the existing `inFlightByUser()` pattern. Recency cap small (e.g. 25). The
current GSI max is GSI8; **M28 adds none.**

**Key builders** live in `packages/core/src/db/keys.ts` as `activityKeys`:
`activityItemKey(sub, activityId)`, `activityListQuery(sub)`, `activityInFlightQuery(sub)`,
`buildActivityItem(...)`, and `appendStepUpdate(...)` (the `UpdateItem` expression that pushes a
`{phase, detail, at}` onto `steps`, sets `phase`/`phaseDetail`/`progress`/`updatedAt`, and is
the single place phase transitions are encoded). No inline `pk`/`sk` strings anywhere else.

**TTL.** `ttl` auto-expires finished records ~24h after creation so the table doesn't accumulate
activity history (enable TTL on the `ttl` attribute in `infra/db.ts`).

### Producers — phase + step history per pipeline

Each pipeline creates its `ACTIVITY` record when work is enqueued and calls `appendStepUpdate`
at each transition. The `phaseDetail` strings are authored server-side so they cannot
misrepresent what is happening.

- **Study generation** (`jobs/study-generation.ts`) — phases:
  `queued → reading_notes → analyzing → generating → finalizing → ready|failed`.
  - `reading_notes` — loading the N source note bodies from S3 (`detail`: "Reading 3 notes").
  - `analyzing` — for map-reduce inputs, one step per map chunk with
    `progress {current,total}` from the existing `chunkCount` ("Analyzing section 3 of 5").
    Single-note inputs skip straight through.
  - `generating` — the Bedrock generation (now the **streaming** call, see below).
  - `finalizing` — writing the body to S3 and flipping the STUDYSET status.
  The STUDYSET item keeps its own `status` (unchanged source of truth for the viewer); the
  ACTIVITY record mirrors it for the indicator. The activity's `refId` = `studySetId`.
- **Transcription / OCR** (`lib/transcribe` job, `processTranscriptionJob`) — phases:
  `queued → uploading → transcribing → finalizing → ready|failed`. The `transcribing` phase is
  the streaming Bedrock vision call. `refId` = transcription job id.
- **TTS synthesis** (`/api/audio/synthesize`) — synchronous Polly, short-lived but still
  surfaced: `queued → synthesizing → ready|failed`. Written inline in the route (no background
  job); no token stream (audio, not text), so no `stream` field. `refId` = audio id.

### Activity API

```
GET /api/activity            → { inFlight: ActivitySummary[]; recent: ActivitySummary[] }
GET /api/activity/[id]       → { activity: ActivityDetail }   (includes full steps[] + stream meta)
```

- Auth via `proxy.ts` (401 without a token). Ownership is implicit in the `USER#<sub>` PK — an
  activity not under the caller's partition is simply 404.
- `GET /api/activity` is what the indicator polls (every ~2 s while anything is in flight; it
  stops polling when `inFlight` is empty and resumes when a trigger registers a new job).
- `ActivitySummary` = the collapsed-view fields (`activityId, kind, status, phase, phaseDetail,
  progress, title, updatedAt`); `ActivityDetail` adds `steps[]` + `stream`.

### Live token streaming — approach A (SSE relay over a buffer)

The LLM work runs in a fire-and-forget background Lambda, not in the request the browser holds,
so tokens are relayed via a buffer rather than streamed directly from the model call:

1. **Producer side.** Study-gen / transcription jobs switch from the non-streaming
   `ConverseCommand` to the streaming `ConverseStreamCommand` (Bedrock
   `InvokeModelWithResponseStream` — IAM already bound on the study consumer per M13/infra). As
   tokens arrive, the job accumulates them and **flushes the running buffer to S3** every
   ~0.5–1 s (or every N tokens) at `activity/<sub>/<activityId>.stream.txt`, overwriting the
   object each flush (whole-buffer write — fine at these sizes). On completion it sets
   `stream.done = true` on the ACTIVITY item. The activity's `stream.s3Key` points at the object.
2. **Relay side.** New `GET /api/activity/[id]/stream` SSE route (authed, ownership-checked).
   It tails the S3 buffer: reads the object, emits the new suffix as an SSE `data:` event,
   sleeps briefly, repeats, and **closes the stream when `stream.done` flips true** (or after a
   safety timeout). One HTTP connection per open panel; no new transport infra.
3. **Client side.** When a panel is expanded for an LLM-kind activity that is `running`, the
   indicator opens an `EventSource` to the stream route and appends deltas into the live-output
   view; it closes the source on `done`, on collapse, or on unmount.

**IAM/infra deltas.** Study-gen + transcription Lambdas need S3 **write** on `activity/*`
(plus `bedrock:InvokeModelWithResponseStream`, already present for study-gen; add it for the
transcription function if absent). The application function needs S3 **read** on `activity/*`
for the relay route. The `activity/*` prefix lives in the existing notes/data bucket.

### Frontend

- **`Collapsible` primitive** (`packages/application/src/components/ui/Collapsible.tsx`) — a
  presentational disclosure widget: a header (subject + chevron, `aria-expanded`,
  `aria-controls`) and a region (`role="region"`), collapsed by default, keyboard-operable.
  No app/data coupling — reusable by the indicator **and** the M19 admin panel.
- **`AiActivityProvider`** — a client context mounted in the authed layout. Holds the current
  activity list, owns the poll loop against `GET /api/activity`, and exposes
  `registerActivity()` so a trigger (Generate / Transcribe / Synthesize) can optimistically
  register its new job and kick polling immediately rather than waiting for the next interval.
- **`AiActivityIndicator`** — the global widget (anchored app-wide, e.g. bottom corner / navbar).
  Collapsed: a chip with a spinner + count + the most-recent subject ("AI is working · 2").
  Expanded: a `Collapsible` per activity showing phase, the canonical step checklist driven by
  `steps[]` (current step highlighted), `progress`, and — for `running` LLM kinds — the live
  `EventSource` output. Finished activities show a brief done/failed state then drop off (TTL +
  client filtering). Hidden entirely when there is nothing in flight or recent.
- **Trigger wiring.** The existing `GenerateStudyMaterial` flow (and the transcribe/TTS triggers)
  call `registerActivity()` on enqueue. The old inline single-line banner is **removed** in
  favour of the global indicator (the note view can still deep-link to the produced study set on
  completion).
- **M19 admin panel.** Replace the version-history panel's placeholder disclosure in the
  admin AI-settings page with the new `Collapsible`.

### Infra / secrets

- `infra/db.ts` — enable **TTL** on the Notes table `ttl` attribute (ACTIVITY items set it).
- S3 — new logical `activity/*` prefix in the existing data bucket; grant study-gen +
  transcription Lambdas **write** and the application function **read** on it.
- IAM — ensure `bedrock:InvokeModelWithResponseStream` is granted to the transcription function
  (already present on study-gen).
- **No new `sst.Secret`, no new table, no new GSI.**

## Risks / open questions

- **Stream buffer in S3, overwritten each flush.** Whole-object writes are simplest but cost a
  PUT per flush; keep the flush cadence modest (~0.5–1 s) and cap buffer size. If volumes grow,
  revisit (append-friendly store / chunked objects). Acceptable for M28.
- **SSE route holds a Lambda open.** The relay route stays open while a panel is expanded; bound
  it with a safety timeout and close promptly on `stream.done`/disconnect so it doesn't pin a
  function indefinitely. Only LLM `running` activities open it, and only while expanded.
- **Polling churn.** The indicator must stop polling when nothing is in flight (and only resume
  on a registered trigger or a periodic light check) so it doesn't hammer `GET /api/activity`
  on every page forever.
- **STUDYSET status vs ACTIVITY duplication.** The STUDYSET `status` remains the viewer's source
  of truth; the ACTIVITY record mirrors phase for the indicator. Keep the job writing both
  consistently (or have the activity derive from the same transition points) to avoid drift.
- **TTS is synchronous.** Its activity may flash by quickly; ensure the indicator still shows a
  brief "done" state rather than never appearing.
- **Trigger registration vs server truth.** `registerActivity()` is an optimistic client hint;
  the next poll reconciles it against the server list (avoid duplicate panels for the same job —
  key panels by `activityId`/`refId`).
- **Ownership on the stream route.** The SSE route must verify the activity is under the caller's
  partition before relaying any buffer bytes (404 otherwise) — the S3 key embeds `sub`.

## Manual test plan

Test on the deployed `pr-<N>` stage:

1. **Indicator appears on generate.** From a note, generate flashcards. Expect the collapsed
   "AI is working" chip to appear immediately (before completion).
2. **Expand shows real phases.** Expand the chip. Expect a per-activity panel showing the live
   phase subject changing over time (Reading → Analyzing → Writing → Finishing) with a
   timestamped step list; for a multi-note input, expect "section N of M" progress.
3. **Live streaming.** While an LLM activity is `running` and expanded, expect the model's output
   to stream into the live-output area, and stop cleanly when it finishes.
4. **Survives navigation.** Start a generation, navigate to another page. Expect the chip to
   persist and keep updating; return and confirm it completed.
5. **Multiple kinds at once.** Kick off a transcription and a study generation (and a TTS play).
   Expect all three tracked as separate panels with their own phases; TTS shows a brief
   synthesize→done.
6. **Completion + cleanup.** When all jobs finish, expect a brief done state then the indicator
   hides itself; no console errors; the SSE connection closed.
7. **Failure path.** Force/observe a failed generation. Expect the panel shows the failed status
   + error detail rather than spinning forever.
8. **M19 admin panel.** On the admin AI-settings page, expand/collapse the version-history panel.
   Expect it uses the new Collapsible and behaves identically to before.
