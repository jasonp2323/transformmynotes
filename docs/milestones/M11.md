# M11 · Security hardening

> Size: L · Depends on: M2, M3, M10

## Goal

Harden TransformMyNotes against real-world attack patterns now that the service is live and accepting users. This milestone tightens the existing auth and registration flows with Cloudflare Turnstile bot protection (stopping credential-stuffing and automated abuse), applies an OWASP ASVS Level 1 + OWASP Top 10 baseline across both packages (security response headers, CSP, DynamoDB-backed rate limiting, input validation, cookie hardening, no-enumeration guarantees), and enables all three GitHub-native code-scanning pillars (CodeQL SAST, Dependabot, secret scanning + push protection) at zero additional cost.

This milestone is intentionally not a feature milestone. No new user-facing capabilities are built. Every sub-issue tightens, verifies, or protects what already exists. It is the natural post-launch complement to M10's operational hardening.

## In scope

**Pillar 1 — Cloudflare Turnstile bot protection**
- Add a Turnstile client-side widget to the login page (`packages/application/app/(auth)/login/page.tsx`), forgot-password page (`app/(auth)/forgot-password/page.tsx`), reset-password page (`app/(auth)/reset-password/page.tsx`), and the signup / invite-accept / registration pages (once built in M3)
- Add a shared server-side `verifyTurnstile(token: string)` helper in `packages/application/lib/` that calls `https://challenges.cloudflare.com/turnstile/v0/siteverify` with the secret key; the route handler calls this helper **before** invoking any Cognito operation (Amplify `signIn`, `resetPassword`, `confirmResetPassword`, or the admin `AdminCreateUser` / invite-redemption path)
- Two new `sst.Secret` entries in `infra/secrets.ts`: `TURNSTILE_SITE_KEY` (exposed as `NEXT_PUBLIC_TURNSTILE_SITE_KEY` — the widget sitekey is a public value like the Cognito pool id) and `TURNSTILE_SECRET_KEY` (server-only, read only in the `verifyTurnstile` helper); both declared with no empty fallback and seeded in both SST Console environments (production + fallback). Cloudflare provides documented test keys for non-production stages
- The route handler returns a generic `400 Bad Request` (not a Cognito error) if the Turnstile token is absent or the siteverify call returns `success: false` — no Cognito call is made

**Pillar 2 — OWASP ASVS Level 1 + OWASP Top 10 baseline**
- **Security response headers**: add a strict but app-compatible set of HTTP response headers to every response from `packages/application` and `packages/marketing` via `next.config` `headers()` (and the existing `proxy.ts` middleware where appropriate): `Content-Security-Policy` (see "Architecture & decisions"), `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), geolocation=(), microphone=()` (with camera relaxed to `camera=(self)` on routes that use the capture flow, once that route exists in M4)
- **Rate limiting on sensitive routes**: a DynamoDB-backed fixed-window counter (new access pattern in `packages/core/src/db/keys.ts` + dynalite integration test) keyed by a composite of `CF-Connecting-IP` (or `x-forwarded-for` fallback) + route slug; returns `429 Too Many Requests` with a `Retry-After` header past the threshold. Applied to: `POST /api/auth/login`, `POST /api/auth/forgot-password`, `POST /api/auth/reset-password`, `POST /api/invites/redeem`, and any registration endpoint. Complements Turnstile as a defense-in-depth layer
- **Cookie / session hardening**: the `CognitoIdToken` cookie set in `packages/application/app/(auth)/login/page.tsx` must carry `HttpOnly`, `Secure`, and `SameSite=Lax` attributes; currently the client sets it via `document.cookie` without these flags — move cookie setting to a minimal server-side `POST /api/auth/set-session` route handler so `HttpOnly` can be enforced
- **Input validation**: every existing and new route handler (`app/api/**`) validates its request body with a `zod` schema and rejects malformed input with `400`; no raw Zod error detail in the response body (return a generic message, log detail server-side to CloudWatch)
- **No email enumeration**: confirm that `POST /api/auth/login` and `POST /api/auth/forgot-password` return identical response shapes and timing regardless of whether the email exists (the existing `forgot-password` page already swallows the Cognito error — confirm the pattern holds end-to-end through the new server-side route)
- **No raw error leakage**: all route handlers catch unexpected errors and return `{ error: "Something went wrong. Please try again." }` to the client; full error detail (message + stack) goes to `console.error` (CloudWatch only)
- **ASVS L1 + OWASP Top 10 self-audit checklist**: committed to `docs/security/asvs-l1-checklist.md`, mapping each relevant ASVS L1 control and OWASP Top 10 category to the codebase location where it is satisfied

**Pillar 3 — GitHub-native code scanning**
- **CodeQL SAST**: new workflow `.github/workflows/codeql.yml` targeting JavaScript/TypeScript, triggered on every PR and on a weekly schedule (`cron: '0 2 * * 1'`); uses the `actions/codeql-action` suite (`init` → `autobuild` → `analyze`); results surface in the repo's Security tab → Code scanning alerts
- **Dependabot**: new config `.github/dependabot.yml` covering the `npm` ecosystem at the monorepo root (and optionally each workspace) plus the `github-actions` ecosystem; minor and patch version bumps grouped into a single weekly PR per ecosystem to reduce noise; major bumps as individual PRs
- **Secret scanning + push protection**: enabled in GitHub repo Settings → Security → Secret scanning (toggle "Secret scanning" and "Push protection"); a documented settings-level step in this doc since it is a UI toggle, not a file. Requires the repo admin (jasonp2323) to enable it once; no workflow change needed

## Architecture & decisions

### Turnstile integration

**Client widget**
Import the Turnstile React component (`@marsidev/react-turnstile` — a thin, well-maintained wrapper around Cloudflare's widget script) in the four auth pages. Render it just above the submit button. On `onSuccess(token)`, store the token in component state. Pass `siteKey={process.env.NEXT_PUBLIC_TURNSTILE_SITE_KEY}` — this is a `NEXT_PUBLIC_` value exactly like `NEXT_PUBLIC_COGNITO_USER_POOL_ID` and requires no SST binding to expose it (set it in `environment` in `infra/application.ts` pointing at `turnstileSiteKey.value`). On form submit, include the token in the POST body sent to the server-side route.

**Server `verifyTurnstile` helper** (`packages/application/lib/turnstile.ts`)
```ts
export async function verifyTurnstile(token: string): Promise<void> {
  const secret = process.env.TURNSTILE_SECRET_KEY;
  if (!secret) throw new Error("TURNSTILE_SECRET_KEY is not set");
  const res = await fetch("https://challenges.cloudflare.com/turnstile/v0/siteverify", {
    method: "POST",
    headers: { "Content-Type": "application/x-www-form-urlencoded" },
    body: new URLSearchParams({ secret, response: token }),
  });
  const data = await res.json() as { success: boolean };
  if (!data.success) throw new TurnstileError("Turnstile verification failed");
}
```
The route handler catches `TurnstileError` and returns `{ error: "Bot check failed. Please try again." }` with status `400`. All Cognito calls are downstream of this check — if `verifyTurnstile` throws, Cognito is never invoked.

**The two new secrets** (`infra/secrets.ts`)
```ts
export const turnstileSiteKey = new sst.Secret("TURNSTILE_SITE_KEY");
export const turnstileSecretKey = new sst.Secret("TURNSTILE_SECRET_KEY");
```
No empty fallback. Both seeded in both Console environments (production values + fallback/staging values). For non-production stages (`pr-<N>`), use Cloudflare's documented test keys: sitekey `1x00000000000000000000AA` (always passes) or `2x00000000000000000000AB` (always blocks) for test purposes. `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is added to the `environment` map in `infra/application.ts` (alongside `NEXT_PUBLIC_COGNITO_USER_POOL_ID`).

### Security headers / CSP

Applied via `next.config` `headers()` in both `packages/application` and `packages/marketing`. The `headers()` config applies to all routes matching `"/(.*)"`.

**Content-Security-Policy directive sketch** (application):
```
default-src 'self';
script-src 'self' https://challenges.cloudflare.com 'nonce-{nonce}';
style-src 'self' 'unsafe-inline';
img-src 'self' data: https://*.cloudfront.net https://*.amazonaws.com;
frame-src https://challenges.cloudflare.com;
connect-src 'self' https://cognito-idp.us-east-1.amazonaws.com https://*.auth.us-east-1.amazoncognito.com https://challenges.cloudflare.com;
font-src 'self';
object-src 'none';
base-uri 'self';
form-action 'self';
frame-ancestors 'none';
upgrade-insecure-requests;
```
Key callouts:
- `script-src` includes `https://challenges.cloudflare.com` for the Turnstile widget script and a per-request `nonce` for Next.js inline scripts. The nonce approach (`next/headers` + `generateNonce()` in a Server Component layout) is preferred over `'unsafe-inline'` to satisfy ASVS V1.6.
- `frame-src` must include `https://challenges.cloudflare.com` because the Turnstile challenge renders in a sandboxed iframe.
- `img-src` includes the CloudFront and S3 origins where user-uploaded note images are served from.
- `connect-src` includes the Cognito service endpoint (used by Amplify Auth's `signIn` / `fetchAuthSession` calls) and the Cognito Hosted UI domain.
- Marketing CSP is simpler (no Cognito, no Turnstile) but must still cover any Google Fonts or other CDN references.
- **Start in report-only mode** (`Content-Security-Policy-Report-Only`) on the first deploy and monitor the browser console for violations before switching to enforcing. See Risks.

**Other headers** (both packages):
```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), geolocation=(), microphone=()
```
`X-Frame-Options: DENY` and `frame-ancestors 'none'` in CSP are redundant but belt-and-suspenders — some older browsers only honour the header.

### Rate limiting (DynamoDB-backed)

**Access pattern** — new key builder in `packages/core/src/db/keys.ts`:
```ts
export const rateLimitKeys = {
  /** Fixed-window counter record. windowId = "<route>#<ip>#<windowStart>". */
  counter: (route: string, ip: string, windowStart: string) => ({
    pk: `RATELIMIT#${route}`,
    sk: `IP#${ip}#WIN#${windowStart}`,
  }),
};
```
The route handler computes `windowStart` by flooring `Date.now()` to the nearest window (e.g. 60 seconds for login). It calls `UpdateItem` with `ADD #count :one` and `ConditionExpression` none (unconditional increment); if the returned `count` exceeds the threshold (e.g. 10 attempts / 60s for login, 5 / 60s for forgot-password), return `429` with `Retry-After: <seconds until window end>`. Counter items carry a DynamoDB TTL (`expiresAt = windowStart + 2 * windowSizeSeconds`) so exhausted-window records are cleaned up automatically without a `DeleteItem` call.

The `UserData` table (already linked to `application` in `infra/application.ts`) is reused for rate-limit counters — no new table required. The GSI is not needed for this access pattern (it's a direct PK+SK lookup). The key builder and the `UpdateItem` + threshold logic live in `packages/core/src/db/` and are exercised by a dynalite integration test (`ratelimit.integration.test.ts`) that writes a sequence of increments and asserts the counter value and TTL.

**IP extraction**: read `CF-Connecting-IP` (set by Cloudflare for all production traffic) with `x-forwarded-for` as the fallback for `pr-<N>` stages and local dev. Never trust a client-supplied `X-Real-IP` header.

**Thresholds** (seeded as defaults, adjustable via future config):
- Login: 10 requests / 60 seconds per IP
- Forgot-password: 5 requests / 60 seconds per IP
- Invite redemption: 5 requests / 60 seconds per IP

### Input validation and error handling

Every route handler in `packages/application/app/api/**` must:
1. Parse and validate the request body with a `zod` schema at the top of the handler before any business logic. Return `{ error: "Invalid request." }` with status `400` on parse failure — no raw Zod error paths in the response.
2. Wrap the main logic in a `try/catch`; catch unexpected errors, `console.error` the full detail (message, stack, request path), and return `{ error: "Something went wrong. Please try again." }` with status `500`.
3. Never include a Cognito error message verbatim in the response body (e.g. `UserNotFoundException` or `NotAuthorizedException` must not reach the client as-is).

The no-enumeration requirement for login and forgot-password: the response shape and HTTP status for "email not found" must be identical to "wrong password" (login) and "email not found" must silently proceed to the reset-password step without error (forgot-password already does this in `app/(auth)/forgot-password/page.tsx` — confirm the server-side route maintains this invariant when Turnstile + rate limiting are added as a wrapper).

### Cookie / session hardening

Currently `packages/application/app/(auth)/login/page.tsx` sets `document.cookie = \`CognitoIdToken=...; path=/; samesite=lax\`` client-side. This means the cookie cannot carry `HttpOnly` (JavaScript cannot set `HttpOnly` on itself) and `Secure` is not enforced.

Introduce a minimal `POST /api/auth/set-session` route handler: the client POSTs the raw ID token to this endpoint (over HTTPS), and the route handler sets the cookie server-side via `response.cookies.set("CognitoIdToken", token, { httpOnly: true, secure: true, sameSite: "lax", path: "/" })`. The client no longer touches `document.cookie`. `proxy.ts` already reads the cookie by name (`req.cookies.get("CognitoIdToken")`) — no proxy change needed. A `POST /api/auth/sign-out` route handler clears the cookie.

### Code scanning

**CodeQL (`.github/workflows/codeql.yml`)**
Standard two-job pattern from the `actions/codeql-action` v3 suite:
```yaml
name: CodeQL
on:
  push:
    branches: ["master"]
  pull_request:
  schedule:
    - cron: '0 2 * * 1'   # weekly Monday 02:00 UTC
permissions:
  security-events: write
  contents: read
  actions: read
jobs:
  analyze:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        language: [javascript-typescript]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/codeql-action/init@v3
        with:
          languages: ${{ matrix.language }}
      - uses: actions/codeql-action/autobuild@v3
      - uses: actions/codeql-action/analyze@v3
```
Results appear under Security → Code scanning alerts. Alert suppression (`.github/codeql-config.yml`) can be added later for known false-positive patterns once the initial scan baseline is understood.

**Dependabot (`.github/dependabot.yml`)**
```yaml
version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule: { interval: weekly }
    groups:
      minor-patch: { update-types: ["minor", "patch"] }
    open-pull-requests-limit: 10
  - package-ecosystem: github-actions
    directory: "/"
    schedule: { interval: weekly }
    groups:
      actions-minor-patch: { update-types: ["minor", "patch"] }
```
Grouping minor/patch into one weekly PR per ecosystem keeps the PR noise low. Major version bumps are individual PRs (Dependabot default). The `npm` entry at `"/"` covers the monorepo root `package-lock.json`, which includes all workspace dependencies.

## Risks / open questions

- **CSP breaking Next.js inline scripts or Amplify**: Next.js injects inline `<script>` tags for hydration data; Amplify Auth makes `fetch` calls to Cognito endpoints. A too-strict CSP will break the app on first deploy. Mitigation: start with `Content-Security-Policy-Report-Only`, deploy to a `pr-<N>` stage, and inspect the browser console for violation reports before switching to enforcing mode. The nonce approach (generated per request in the Server Component layout) handles Next.js inline scripts without `'unsafe-inline'`. Allow extra time for the CSP tuning phase.
- **Turnstile test keys vs production keys**: the Cloudflare test sitekey `1x00000000000000000000AA` always passes, which means `pr-<N>` E2E tests do not exercise real challenge solving. Acceptable for CI, but the production keys must be seeded correctly in the production Console environment and manually verified on the first production deploy.
- **Rate limiting false positives behind shared NAT or Cloudflare IP ranges**: users behind a corporate NAT or a Cloudflare WARP VPN may share a single egress IP, causing a single heavy user to exhaust the limit for their entire office. Mitigation: key on `CF-Connecting-IP` (the true client IP that Cloudflare passes through, not the Cloudflare proxy IP); set the threshold conservatively but not aggressively (10 login attempts / 60 s is unlikely to affect a legitimate user). Monitor CloudWatch for `429` spikes after launch and tune if needed.
- **MFA deferral**: TOTP or SMS MFA is the single highest-impact security control not in this milestone. Without MFA, a stolen password is sufficient to authenticate. Turnstile + rate limiting reduce automated credential-stuffing but do not protect against a targeted attack with a known password. Plan a dedicated future MFA milestone (e.g. `M13`): enable TOTP on the Cognito user pool, update the Amplify `signIn` flow to handle the `TOTP_SOFTWARE_TOKEN_MFA` challenge step, update the proxy.ts session flow, and update the E2E `InitiateAuth` headless sign-in recipe.
- **CodeQL noise on a Next.js monorepo**: CodeQL's JavaScript/TypeScript analyser can produce false-positive alerts on React patterns (e.g. flagging JSX string concatenation as potential XSS). Plan to triage the initial scan baseline and suppress known false positives with inline comments or a `codeql-config.yml` exclusion list. Do not bulk-dismiss all alerts without review.
- **`@marsidev/react-turnstile` version pinning**: pin the package to a specific minor version in `packages/application/package.json` to avoid an upstream breaking change silently disabling the widget. The Turnstile JavaScript API is stable (Cloudflare maintains backward compatibility), but the React wrapper is community-maintained.
- **`document.cookie` race condition during the session-cookie migration**: during the period between the client setting the cookie (old path) and the server endpoint being deployed, a user who signs in mid-rollout may end up with a non-`HttpOnly` cookie. Since this is a PR-stage deploy, not a rolling update, the race window is negligible — but a clear-cookies sign-out on first load after the deploy can be added as a safety net.
- **Open question**: should the CSP `upgrade-insecure-requests` directive be included? It is generally safe but can cause issues with mixed-content resources served from HTTP (e.g. if any third-party embed uses plain HTTP). Given the stack is entirely HTTPS-first, include it and monitor for breakage.
