# M7 · Sharing & collaboration

> Size: L · Depends on: M6

## Goal

Enable members of a group to share individual notes with each other. A note owner can
share a note to their entire group or to specific members; recipients see shared notes
in the "Shared" tab of the library (the placeholder wired in M6 is now populated).
Permission is strictly read-only for recipients — only the note's original owner can
edit or delete it. Group admins can revoke any share within their group. Every read of
a shared note is authorised server-side; the client is never trusted to assert
ownership or recipient status.

## In scope

- Share data model: `SHARE` items in the Notes table keyed so a recipient can list all
  notes shared with them (GSI by recipient).
- Share a note to a group or to one or more specific members (share action on the
  note action bar / NoteView).
- "List shared-with-me" access pattern that populates the Shared tab.
- Server-side authorisation on every shared-note read: note owner check OR valid share
  record check; neither path trusts the client.
- Manage shares UI: a share sheet (bottom sheet on mobile, dialog on desktop) showing
  who a note is currently shared with, with revoke controls.
- Shared tab in the library: lists notes shared with the calling user by others (not
  their own notes). Shows the sharer's name, group name, and `sharedAt`.
- Group admin super-power: an admin can revoke any share that belongs to their group.
- Key builders + dynalite integration tests for all new access patterns.
- Playwright E2E covering: owner shares note → recipient sees it in Shared tab →
  owner revokes → it disappears from recipient's Shared tab.

## Out of scope

- Real-time collaboration / simultaneous editing (future).
- Sharing notes outside of an existing group (public links, external email invites).
- Recipient editing shared notes (read-only; editing is always owner-only).
- Push / email notification when a note is shared with you (future).
- Sharing to the whole app / across groups.
- Fine-grained per-field permissions (comment-only, highlight-only, etc.).
- Shared note search (shared notes do not contribute to the recipient's token index).

## Architecture & decisions

### Share data model

A `SHARE` item lives in the Notes table alongside note metadata and token index items.
Using the same table keeps transactional consistency (a note delete can remove its
shares in the same `TransactWrite`).

#### Item shape

```
PK           = USER#<ownerSub>                       # owner's partition
SK           = SHARE#<noteId>#RECIPIENT#<recipientSub>
GSI2-PK      = USER#<recipientSub>                   # recipient-facing index
GSI2-SK      = SHARED_AT#<ISO-8601>                  # newest-first scan in Shared tab
attrs:
  ownerSub         string
  ownerName        string    # denormalised for display (updated on profile change)
  noteId           string
  noteTitle        string    # denormalised for display in Shared tab
  groupId          string    # which group this share is scoped to
  permission       "read"    # only "read" in M7; extensible later
  sharedAt         string    # ISO-8601
  revokedAt?       string    # set on soft-delete; items are TTL-expired after 30 days
```

Soft-delete on revoke (set `revokedAt`, add a TTL attribute) so the Shared tab query
can filter with a `FilterExpression: attribute_not_exists(revokedAt)`. Hard-delete is
applied by a daily DynamoDB TTL cleanup (no Lambda needed).

#### Sharing to a whole group vs. specific members

- **Group share**: write one `SHARE` item per active group member (fan-out on write at
  share time). Groups rarely exceed a few dozen members, so fan-out is safe. If a new
  member joins after the share, the admin can re-share (or a future "group share"
  record type is added); for M7, fan-out on write is the chosen trade-off.
- **Specific-member share**: write exactly one `SHARE` item for that member.

#### GSI definitions (`infra/db.ts`)

| GSI | PK | SK | Purpose |
|-----|----|----|---------|
| `ByRecipient` | `USER#<recipientSub>` (GSI2-PK) | `SHARED_AT#<ISO-8601>` (GSI2-SK) | List all notes shared with a recipient, newest first |

The sort key `SHARED_AT#<ISO-8601>` is lexicographically sortable (ISO-8601 UTC
strings sort chronologically). `ScanIndexForward: false` gives newest-first.

Key builders to add to `packages/core/src/db/keys.ts`:

```typescript
shareItemKey(ownerSub: string, noteId: string, recipientSub: string): PrimaryKey
sharesByRecipientQuery(recipientSub: string): QueryInput   // GSI2, desc, limit 50
sharesByNoteQuery(ownerSub: string, noteId: string): QueryInput   // base table, SK begins_with SHARE#<noteId>
```

### Authorisation model

Every route that returns note content (Markdown body, metadata) runs this check:

```
isOwner = note.PK === userKey(callerSub)
isRecipient = SHARE item exists where PK=userKey(ownerSub), SK=shareKey(noteId, callerSub), revokedAt absent
authorized = isOwner OR isRecipient
```

The check is implemented in a shared helper `packages/core/src/db/shares.ts` —
`authoriseNoteRead(callerSub, ownerSub, noteId): Promise<boolean>` — so it is
reusable by multiple route handlers and testable in isolation.

Group admin revoke: an admin may revoke a share if `admin.groupIds` contains the share's
`groupId`. Checked server-side via the UserData table's `groupIds` field.

### API routes / route handlers

| Route | Method | Description |
|-------|--------|-------------|
| `POST /api/notes/[noteId]/shares` | POST | Create share(s). Body: `{ recipientSubs?: string[], groupId?: string }`. Owner-only. If `groupId` provided, resolves members and fan-out writes. |
| `GET /api/notes/[noteId]/shares` | GET | List current shares for a note. Returns sharer info + recipient list. Owner-only. |
| `DELETE /api/notes/[noteId]/shares/[recipientSub]` | DELETE | Revoke a specific share. Owner or group admin. Sets `revokedAt`. |
| `GET /api/shared` | GET | List notes shared with the calling user (Shared tab). Queries GSI2. Returns `{ notes: SharedNoteSummary[] }`. |
| `GET /api/notes/[noteId]` | GET (update) | Already exists from M6. Extend to run `authoriseNoteRead`; now authorises both owners and valid recipients. |

### Shared tab population

`GET /api/shared` queries `ByRecipient` GSI with `PK=USER#<callerSub>`, limit 50,
newest first, filtering out soft-deleted shares. Returns the denormalised
`{ noteId, noteTitle, ownerName, groupId, sharedAt }` — no extra fetch needed for
list display.

When the user taps a shared NoteCard, the app navigates to `/notes/[noteId]` (same
route as owned notes). The route handler's extended authorisation now allows the
recipient to read it.

### Share UI — design components

The `screens-notebook.jsx` `NoteView` action bar already has an icon button slot.
For M7, add a `share-2` Lucide icon button to that bar. Tapping it opens the Share
Sheet.

**Share Sheet** (new component, not in the design files — implement from DS primitives):
- Bottom sheet on mobile (slides up from bottom, `22px` top radius, blurred backdrop).
- Dialog on desktop (centred, `22px` radius).
- Contents:
  - Eyebrow: `SHARING "Note title"`.
  - Group selector: segmented or dropdown — "Whole group" vs "Specific members".
  - For specific members: a multi-select list of group members (Avatar + name + checkbox).
  - Current shares list: who it is already shared with, each with a Revoke button.
  - Primary action: "Share" button (disabled if no new recipients selected).
- Revoke: inline — tapping Revoke on an existing share asks for confirmation in a
  small inline confirmation row, then calls `DELETE /api/notes/[noteId]/shares/[sub]`.

**Shared tab NoteCard** — same `NoteCard` component, with an additional `sharedBy`
eyebrow line ("Shared by Ana Ruiz · Spanish 201") in the card subtitle position.

### Security notes

- `POST /api/notes/[noteId]/shares`: verifies that the caller is the note owner before
  creating any share. Does not trust a `ownerSub` field sent by the client.
- Recipient resolution for group shares: fetches member list from DynamoDB (UserData
  table) server-side; never trusts a client-supplied member list.
- Admin revoke: checks the caller's `groupIds` (from UserData) against the share's
  `groupId`. An admin of group A cannot revoke shares in group B.
- Shared note read: `authoriseNoteRead` is called in `GET /api/notes/[noteId]` before
  any S3 fetch. A user who is not the owner and has no valid (non-revoked) share record
  gets a 403.
- Soft-deleted shares (with `revokedAt`) are excluded by the `ByRecipient` GSI query
  using `FilterExpression`. This is a belt-and-suspenders measure; the route handler
  also double-checks `revokedAt` on any direct item lookup.
- Token index: shared notes do NOT add tokens to the recipient's personal token index.
  The Shared tab search is out of scope; recipients can only browse shared notes, not
  search across them.

### M7.2 · Wave 2 — Server routes (shares API + auth extension)

1. **(M) M7.2.1 — `POST /api/notes/[noteId]/shares` — create shares**
   Owner-authenticated endpoint. Accepts `{ recipientSubs?, groupId? }`. If `groupId`,
   resolves current active members from UserData, fans out to write one share item per
   member (excluding the owner). Uses `TransactWrite` up to 25 items; for larger groups,
   batches across multiple transactions. Returns `{ created: number }`.
   Acceptance criteria: non-owner gets 403; group fan-out creates one item per member;
   sharing to a specific sub creates exactly one item; idempotent (re-sharing to the
   same recipient is a no-op — check before writing).

2. **(M) M7.2.2 — `DELETE /api/notes/[noteId]/shares/[recipientSub]` — revoke**
   Sets `revokedAt` = now and a `ttl` attribute (Unix timestamp 30 days out) on the
   share item. Authorised for the note owner or a group admin (whose `groupIds`
   contains the share's `groupId`). Returns 204.
   Acceptance criteria: owner can revoke their own share; admin of the share's group
   can revoke; admin of a different group gets 403; after revoke, `authoriseNoteRead`
   returns false for that recipient.

3. **(M) M7.2.3 — `GET /api/shared` — Shared tab data**
   Queries `ByRecipient` GSI for `callerSub`, newest first, limit 50, filtering out
   soft-deleted shares. Returns `SharedNoteSummary[]` from denormalised attributes
   (no extra DynamoDB read). Caches lightly with `Cache-Control: private, max-age=30`.
   Acceptance criteria: returns 401 without token; returns only notes shared with the
   caller (not shares the caller created); revoked shares absent; correct `sharedAt`
   ordering.

4. **(M) M7.2.4 — Extend `GET /api/notes/[noteId]` — recipient authorisation**
   Import and call `authoriseNoteRead` before the S3 fetch. Remove any assumption that
   the note's `PK` must equal `userKey(callerSub)`. If `authoriseNoteRead` returns
   false, return 403.
   Acceptance criteria: note owner can still read their note; valid recipient can read;
   revoked recipient gets 403; unrelated user gets 403.

5. **(M) M7.2.5 — Note delete — cascade share removal**
   Extend `DELETE /api/notes/[noteId]` (M6) to also soft-delete all share items for
   that note in the same `TransactWrite` (or follow-on batches for large fan-outs).
   Acceptance criteria: dynalite integration test confirms that after a note is deleted,
   `sharesByNoteQuery` returns no active items; a recipient who had a share can no
   longer read the note (returns 404 / 403).

## Risks / open questions

- **Fan-out write scale.** If a group grows beyond ~100 members and an owner shares a
  note with the whole group, the fan-out could require multiple `TransactWrite` batches
  (max 25 items each). This is fine for M7 group sizes; document the limit and plan a
  "group share record" abstraction for M8+ if groups scale.
- **Denormalised `ownerName` drift.** The `ownerName` field on the share item is
  denormalised at write time. If the owner updates their display name, existing share
  items retain the old name. For M7, accept this inconsistency; a future background
  job can backfill. Flag it as a known issue.
- **GSI `FilterExpression` for soft-deleted shares.** DynamoDB charges RCU for all
  items scanned before the filter is applied. If a user accumulates many revoked shares,
  the `ByRecipient` scan becomes wasteful. Mitigation for M7: TTL cleanup after 30 days
  keeps the table lean; revisit with a hard-delete strategy if needed.
- **`authoriseNoteRead` latency.** Every shared note read does an extra `GetItem` for
  the share record (on top of the note's `GetItem` and S3 fetch). Mitigate with a
  `Promise.all` parallel fetch of note metadata + share record. Document the pattern.
- **Group membership at share time vs. read time.** Fan-out on write means a member
  who joins after the share was created will not have a share item. The M7 decision is
  to make sharing an explicit action; "share with group" means "all current members".
  Communicate this clearly in the UI ("Share with all 7 current members").

## Manual test plan

Test on the deployed `pr-<N>` stage (requires two test accounts in the same group):

1. **Share to a specific member.** As user A, open a note in NoteView. Tap the share
   icon in the action bar. Expected: Share Sheet slides up with "Specific members"
   option; member B visible in the list. Select member B; tap "Share". Expected: a
   success toast; member B appears in the "Currently shared with" list.

2. **Shared tab — recipient view.** Sign in as user B. Navigate to Library → Shared
   tab. Expected: user A's shared note appears with the eyebrow "Shared by [A's name]
   · [Group name]".

3. **Read shared note.** Tap the shared NoteCard as user B. Expected: NoteView opens
   in read-only mode; the edit pencil icon is absent or disabled; action bar has no
   edit controls.

4. **Share to the whole group.** As user A, share a second note to the whole group.
   Expected: all active group members except A see it in their Shared tab.

5. **Revoke a share.** As user A, open the Share Sheet for the first note. Tap
   "Revoke" next to user B. Confirm. Expected: B's row disappears from the share list.

6. **Recipient access after revoke.** Sign in as user B. Shared tab should no longer
   show the revoked note. Navigate directly to `/notes/[noteId]`. Expected: 403 or
   "Note not found" response.

7. **Admin revoke.** Sign in as a group admin (not the note owner). Navigate to the
   note's Share Sheet (accessible via the Shared tab card). Tap "Revoke". Expected:
   revoke succeeds; recipient loses access.

8. **Non-admin, non-owner revoke attempt.** Sign in as a group member who is neither
   the owner nor an admin. Attempt to revoke via `DELETE /api/notes/[noteId]/shares/[sub]`
   (curl or browser DevTools). Expected: 403 response.

9. **Note delete cascade.** As user A, delete a note that was shared with user B.
   Expected: the note disappears from user B's Shared tab; direct URL access by B
   returns 404 / 403.

10. **Cross-group access.** Create user C in a different group. Attempt to access user
    A's note directly via URL. Expected: 403 — C has no share record and is not the
    owner.
