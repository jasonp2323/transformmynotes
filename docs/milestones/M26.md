# M26 · Multi-page note capture

> Size: M · Depends on: M4 (Capture → Transcribe), M5 (Review & editor) — both done

## Goal

Let a user capture a **multi-page note** in a single flow: a toggle on the capture
screen switches between **Single note** (the default — no action required) and
**Multi-page note**. In multi-page mode the user snaps/uploads several pages, the
existing M4 Bedrock OCR pipeline transcribes each page, and the per-page Markdown is
**stitched into one note** with page separators. The result lands in the existing M5
review screen as a single editable note (with a gallery of the captured page images),
and saves as one `NOTE#` item.

The headline UX rule: **the toggle defaults to "Single note"** so the current
one-photo → one-note experience is completely unchanged for users who do nothing.

## In scope

- **Capture-screen toggle** (`CaptureScreen.tsx`): a clearly-labelled control, default
  position **Single note**. Switching to **Multi-page note** reveals a page tray.
- **Page tray (multi-page mode only):** each shutter press / upload appends a page
  thumbnail to an ordered tray instead of immediately navigating to review. Users can
  **delete** a page and **reorder** pages; a **"Done (N pages)"** action ends capture.
  A single page in multi-page mode behaves like a single note.
- **Per-page upload, reusing M4 unchanged:** each captured page goes through the existing
  `uploadImageForTranscription` path (presign → S3 PUT → one `JOB#` per page). No change
  to `/api/notes/upload-url`, multipart routes, or `/api/transcribe`.
- **Batch transcribe + stitch:** a new `POST /api/transcribe/batch` route accepts an
  **ordered** list of `jobIds`, runs the existing `processTranscriptionJob` per job,
  concatenates the resulting Markdown with a page separator, writes the combined Markdown
  to the **primary** job's `noteMarkdown` S3 key, and returns a combined `TranscribeResult`
  keyed by the primary `jobId`. (The primary `jobId` = the first page, so the existing
  review page loads it with **zero changes** to its data-fetch.)
- **Stitching is pure logic + unit-tested:** `stitchPages(pages: { markdown: string }[])`
  in `packages/core` joins page Markdown with a configurable separator
  (`\n\n---\n\n`, i.e. a horizontal rule between pages) and aggregates `wordCount`. Pure,
  deterministic, unit-tested.
- **Note schema — additive, backward-compatible:** add `originalImageS3Keys?: string[]`
  to the `NOTE#` item to record **all** page images (ordered). The existing
  `originalImageS3Key` stays as the primary/first image for backward-compat readers.
- **Review screen gallery:** `ReviewScreen` shows the captured pages as an ordered
  gallery/carousel of originals (instead of a single image) while keeping **one** stitched
  Markdown editor. Saving persists `originalImageS3Keys` (all pages) onto the one note.
- All new pure logic ships with unit tests; any new/changed DynamoDB access pattern ships
  with a dynalite integration test; the capture + review UI change gets a real browser UI
  test.

## Out of scope

- Server-side image stitching into a single composite image (we OCR pages independently
  and stitch **text**, not pixels).
- Automatic page-break / document-boundary detection (the user explicitly toggles
  multi-page and explicitly ends capture).
- PDF/DOCX/file ingestion — that is M20 (Document sources), a different `SOURCE#` path.
- Re-ordering pages **after** the note is saved (reorder happens in the capture tray /
  review, pre-save only).
- Per-page re-transcription / per-page editing in review (review edits the stitched
  Markdown as one document).
- Changing the OCR model, prompt, or post-processing (`packages/core/src/ocr/*`
  unchanged).

## Architecture & decisions

### Why text-stitch, not a batch OCR call

Each page is an independent image; the existing `processTranscriptionJob(sub, jobId)`
already does image → Markdown → S3 for one job and is idempotent. Multi-page reuses it
per page and concatenates the **Markdown**, so the OCR/Bedrock layer
(`packages/core/src/ocr/*`) and the per-image upload routes are **untouched**. The only
new server surface is a thin batch orchestrator.

### Primary-job trick (keeps review/save unchanged)

The **first** captured page's `jobId` is the **primary**. The batch route writes the
stitched Markdown to `storageKeys.noteMarkdown(sub, primaryJobId)` — exactly where the
single-note flow already writes — so:
- `/capture/review?jobId=<primaryJobId>` loads the stitched Markdown with **no change**
  to `app/(app)/capture/review/page.tsx`'s fetch.
- `/api/notes/save` reuses `noteId = primaryJobId` as today; the only addition is
  accepting and persisting `originalImageS3Keys: string[]`.

### `stitchPages` (pure, `packages/core`)

```typescript
// packages/core/src/ocr/stitch.ts
export interface StitchedPage { markdown: string; wordCount: number; }
export interface StitchResult { markdown: string; wordCount: number; pageCount: number; }

/** Join per-page Markdown with a horizontal-rule separator; sum word counts. */
export function stitchPages(pages: StitchedPage[]): StitchResult;
```

Separator: `\n\n---\n\n`. Empty pages (OCR returned nothing) are skipped from the body
but still counted in `pageCount`. Deterministic; fully unit-tested.

### `POST /api/transcribe/batch`

- **Input:** `{ jobIds: string[] }` — ordered, 1–N (cap N, e.g. 20, fail loud over cap),
  all owned by the caller.
- **Behaviour:** for each `jobId` (in order) call `processTranscriptionJob(sub, jobId)`
  (idempotent — re-running a `done` job is a no-op read), collect
  `{ markdown, wordCount }`, run `stitchPages`, write the combined Markdown to
  `storageKeys.noteMarkdown(sub, jobIds[0])`, return
  `{ jobId: jobIds[0], markdown, wordCount, pageCount, detectedLang, ocrConfidence }`.
- **Ownership:** every `jobId` must be a `JOB#` item in the caller's `USER#<sub>`
  partition → 403 on any mismatch, 404 if any job is missing.
- Runs server-side (`export const runtime = 'nodejs'`).

### Note item change (`packages/core/src/db/notes.ts`)

```typescript
interface NoteItem {
  // …existing…
  originalImageS3Key: string;        // primary (first) page — unchanged
  originalImageS3Keys?: string[];    // NEW: all page images, ordered (incl. the primary)
}
```

`putNote()` accepts the optional array; single-note saves omit it (or pass a 1-element
array). Readers that only know `originalImageS3Key` keep working.

### `/api/notes/save` change

Accept an optional `originalImageS3Keys: string[]` (or derive from `jobIds`) and persist
it on the note. Validate every key belongs to the caller's `images/users/<sub>/` prefix.
No key strings constructed outside `storageKeys`.

### Client flow (`CaptureScreen.tsx`)

- New `mode: 'single' | 'multi'` state, default `'single'`.
- **Single mode:** unchanged — shutter/upload → `uploadImageForTranscription` → navigate
  to review (exactly as today).
- **Multi mode:** shutter/upload → `uploadImageForTranscription` (gets a `jobId`) →
  append `{ jobId, thumbnailDataUrl }` to a `pages[]` tray; stay on the capture screen.
  Tray supports delete + reorder. **"Done (N pages)"** → `POST /api/transcribe/batch`
  with the ordered `jobIds` → navigate to
  `/capture/review?jobId=<primaryJobId>` (carrying the page job ids for the gallery, e.g.
  via query or a short-lived client store).

### Review gallery (`ReviewScreen.tsx`)

Accept `originalImageUrls: string[]` (fallback to the single `originalImageUrl` when
absent). Render an ordered gallery/carousel of page originals; the editor still edits the
one stitched Markdown body. `handleSave` sends `originalImageS3Keys` so the saved note
records every page.

## Risks / open questions

- **Page ordering integrity.** The tray order is the source of truth; the batch route must
  stitch strictly in the `jobIds` order it receives. Reordering after save is out of scope
  — confirm that's acceptable.
- **Carrying page job ids into review.** The primary-job trick keeps the review fetch
  unchanged, but the gallery needs all page image keys. Decide the transport (query param
  list vs. a short-lived client store vs. reading `originalImageS3Keys` from a draft) in
  M26.2/M26.3 and keep it consistent.
- **Partial OCR failure in a batch.** If one page's `processTranscriptionJob` errors,
  decide: fail the whole batch, or stitch the successful pages and flag the failed page in
  review. Recommended: surface a per-page error in review rather than discarding work.
- **Page cap.** Cap N (e.g. 20) to bound batch latency/cost; fail loud over the cap rather
  than silently truncating.
- **Latency.** Batch transcribe is sequential OCR over N pages; for large N consider
  parallelising `processTranscriptionJob` calls (bounded concurrency) if review wait is
  too long.

## Manual test plan

Test on the deployed `pr-<N>` stage (camera or photo upload):

1. **Default is single.** Open the capture screen. Expected: the toggle reads **Single
   note** with no interaction; snapping/uploading one photo goes straight to review and
   saves as one note — identical to before this milestone.
2. **Switch to multi-page.** Toggle to **Multi-page note**. Capture/upload page 1, then
   page 2. Expected: each page appears as a thumbnail in the tray; the screen stays on
   capture (does not auto-navigate).
3. **Reorder + delete.** Reorder the two pages, then delete one and capture a replacement.
   Expected: the tray reflects the new order/count.
4. **Finish + stitch.** Tap **"Done (N pages)"**. Expected: review opens showing both page
   images in a gallery and one editor whose body is page 1's text, a separator, then page
   2's text — in tray order.
5. **Save.** Save the note. Expected: one note is created; opening it from the library
   shows the stitched body; the note records both page images.
6. **Single-page in multi mode.** In multi mode, capture exactly one page → Done. Expected:
   behaves like a normal single note (one image, one body).
7. **Regression — pure single flow.** With the toggle left on Single, run the original
   capture → review → save flow. Expected: no visible or behavioural change vs. today.
