# M20 · Document sources — PDF / DOCX / EPUB / text

> Size: XL · Depends on: M4, M13, M17

## Goal

Generalise the generation input from notes to arbitrary uploaded documents — PDFs,
Word files, EPUBs, and plain text files. A user uploads a document (article, textbook,
chapter), the system extracts its text asynchronously, and the same four study-material
types from M13–M16 (flashcards, quiz, assignment, summary) can be generated from it.
The key architectural move is a unified `SOURCE#` entity and a
`resolveSourceText(sub, ref)` adapter that makes every generator source-agnostic: a
note and a document are equally valid inputs, with no generator rewrite required.

Large books (300+ pages) reuse M17's chunked map-reduce synthesis path unchanged;
extraction for these also runs asynchronously via the `infra/jobs.ts` stream consumer.
A "Sources" library surface in the application lists uploaded documents and their
extraction status, with drag-and-drop upload and a "Generate study material" action that
reuses M13's type-picker + polling flow.

## In scope

- **`SOURCE#<sourceId>` entity** in the Notes table (single-table): PK/SK key builders,
  a recency GSI (GSI7), S3 keys for the original file and extracted Markdown.
- **`resolveSourceText(sub, ref)`** adapter in `packages/core/src/sources/resolve.ts`:
  given a `{ type: 'note' | 'document', id: string }` ref, returns
  `{ text: string, provenanceLabel: string }` — notes pull from their existing S3
  Markdown body; documents pull from `extractedTextS3Key`.
- **Generalised `sourceRefs`** on the `STUDYSET#` item: introduce
  `sourceRefs: { type: 'note' | 'document' | 'web', id: string }[]` alongside the
  existing `sourceNoteIds` (backward-compatible); M13–M17 generators consume
  `resolveSourceText()` output unchanged.
- **Presigned upload route** for documents: reuse the M4 `POST /api/notes/upload-url`
  pattern (`storageKeys.sourceOriginal` → S3 prefix `sources/users/<sub>/<id>.<ext>`).
- **Multi-format parsers**: PDF (`pdf-parse` in `packages/application` workspace),
  DOCX (`mammoth` in `packages/application` workspace), EPUB (`epub2` in
  `packages/application` workspace), TXT/MD passthrough. Each parser converts to
  normalised Markdown/plain text and runs server-side.
- **Inline extraction** for small files (≤ 2 MB / ≤ 50 pages); extracted Markdown
  written to S3 at `sources/users/<sub>/<id>.md`, status flipped `uploading→ready`.
- **Async extraction job** for large files (> 2 MB or > 50 pages): DynamoDB Streams
  Lambda consumer in `infra/jobs.ts` reads `SOURCE#` items with `status: 'extracting'`,
  runs the parser, writes `extractedTextS3Key`, flips status `extracting→ready|failed`.
- **Large-document generation**: a source whose `wordCount` implies token budget above
  `MULTI_NOTE_CONTEXT_LIMIT` is fed through M17's map-reduce path at generation time —
  `resolveSourceText()` returns the full text; `chunkNotes` and map-reduce synthesis
  handle the rest.
- **"Sources" library UI**: `/sources` page listing uploaded documents with status
  badges; drag-and-drop or file-picker upload entry point; "Generate study material"
  action per source (M13 type-picker + polling flow).
- Key builders in `packages/core/src/db/keys.ts`; dynalite integration tests for all
  new access patterns.
- Guardrails: max file size (configurable `sst.Secret("MAX_SOURCE_FILE_BYTES")`), page
  and word caps, MIME-type allowlist, per-user document count cap
  (`sst.Secret("MAX_SOURCES_PER_USER")`); all fail loud on missing config.
- All new pure logic has unit tests; all new DynamoDB access patterns have dynalite
  integration tests.

## Out of scope

- Web/URL document sources (M21 adds `type: 'web'`; the `sourceRefs` schema reserves
  the `'web'` discriminant but M20 does not implement it).
- Re-generation / refresh when a source document is replaced.
- Collaborative / shared sources (sources are always private to the owner).
- Source editing or annotation.
- PDF OCR for scanned images inside PDFs (text-layer extraction only in M20; image-page
  OCR is a future concern using the M4 Bedrock OCR path).
- Per-page/section navigation UI for extracted content.
- Source-level sharing or export.

## Architecture & decisions

### `SOURCE#` entity

Lives in the Notes table (same single-table design, same SST `UserData` table resource
or the Notes table depending on where notes live — follow the `infra/db.ts` pattern
already in place for `STUDYSET#` items from M13).

#### Item shape

```typescript
interface SourceItem {
  // DynamoDB primary keys
  pk: string;           // USER#<sub>
  sk: string;           // SOURCE#<sourceId>   (sourceId = ULID)

  // GSI7 (SourcesByUser — recency)
  gsi7pk: string;       // USER#<sub>
  gsi7sk: string;       // SOURCE#<ulid>       (newest-first desc scan, same ULID lexicographic trick as GSI4)

  // Domain fields
  sourceId: string;                          // ULID
  type: 'document' | 'web';                 // 'web' reserved for M21
  title: string;                            // filename or user-supplied title
  status: 'uploading' | 'extracting' | 'ready' | 'failed';
  originalFormat: 'pdf' | 'docx' | 'epub' | 'txt' | 'md';
  originalS3Key: string;                    // sources/users/<sub>/<id>.<ext>
  extractedTextS3Key?: string;              // sources/users/<sub>/<id>.md  (set on ready)
  pageCount?: number;
  wordCount?: number;                       // set after extraction
  byteSize: number;
  error?: string;
  createdAt: string;                        // ISO-8601
  updatedAt: string;                        // ISO-8601
}
```

#### GSI7 — `SourcesByUser` (recency)

| GSI | PK | SK | Purpose |
|-----|----|----|---------|
| `SourcesByUser` (GSI7) | `USER#<sub>` (gsi7pk) | `SOURCE#<ulid>` (gsi7sk) | List all sources for a user, newest first (ULID desc scan) |

GSI numbering follows the sequence: GSI1 (`ByToken` / `UserNotesByTime`), GSI2
(`NotesByTag`), GSI3 (`ByDue`), GSI4 (`StudySetsByUser`), GSI5 (`StudySetsByNote`),
GSI6 (`ByQuizAttempt`), **GSI7 (`SourcesByUser`)**.

`infra/db.ts`: add `gsi7pk` and `gsi7sk` to the Notes table field definitions and
declare `SourcesByUser` as a new `globalIndex`.

#### Key builders (`packages/core/src/db/keys.ts`)

```typescript
export const sourceKeys = {
  /** Primary key for a SOURCE# item. */
  item: (sub: string, sourceId: string) => ({
    pk: `USER#${sub}`,
    sk: `SOURCE#${sourceId}`,
  }),

  /** GSI7 key attributes. Attach on write. */
  recencyIndex: (sub: string, sourceId: string) => ({
    gsi7pk: `USER#${sub}`,
    gsi7sk: `SOURCE#${sourceId}`,
  }),

  /** Query: list all sources for a user via GSI7, newest first. */
  listByUser: (sub: string) => ({
    IndexName: 'SourcesByUser',
    KeyConditionExpression: 'gsi7pk = :gsi7pk',
    ExpressionAttributeValues: { ':gsi7pk': `USER#${sub}` },
    ScanIndexForward: false,
  }),
};
```

#### Storage key builders (`packages/core/src/db/keys.ts` — `storageKeys` extension)

```typescript
// Extend the existing storageKeys object:
storageKeys.sourceOriginal = (sub: string, id: string, ext: string) =>
  `sources/users/${sub}/${id}.${ext}`;
storageKeys.sourceText = (sub: string, id: string) =>
  `sources/users/${sub}/${id}.md`;
```

### `resolveSourceText()` — source-normalization adapter

File: `packages/core/src/sources/resolve.ts`

```typescript
export type SourceRef = { type: 'note'; id: string } | { type: 'document'; id: string };

export interface ResolvedSource {
  text: string;
  provenanceLabel: string;   // e.g. "My Note Title" or "chapter3.pdf"
}

export async function resolveSourceText(
  sub: string,
  ref: SourceRef,
): Promise<ResolvedSource>
```

- `type: 'note'` — reads `storageKeys.noteMarkdown(sub, ref.id)` from S3 (existing
  path); `provenanceLabel` = note title from the `NOTE#` DynamoDB item.
- `type: 'document'` — asserts `status === 'ready'`; reads `extractedTextS3Key` from
  S3; `provenanceLabel` = `source.title`.

This is what makes generators source-agnostic. `POST /api/study/generate` (M13) calls
`resolveSourceText` for each ref and hands the combined texts to `generate()` — the
generator code is untouched.

### `sourceRefs` — generalised study-set source reference

Extend `STUDYSET#` item (additive, backward-compatible):

```typescript
sourceRefs?: { type: 'note' | 'document' | 'web'; id: string }[];
// sourceNoteIds remains; if present and sourceRefs is absent, the route normalises:
//   sourceRefs = sourceNoteIds.map(id => ({ type: 'note', id }))
```

`POST /api/study/generate` accepts:
```typescript
{
  type: 'flashcards' | 'quiz' | 'assignment' | 'summary';
  sourceRefs: SourceRef[];   // 1–N, all owned by caller
  // sourceNoteIds still accepted as backward-compat; normalised to sourceRefs on receipt
  dryRun?: boolean;
}
```

Ownership check: for each ref, look up the item (`NOTE#` or `SOURCE#` in the same
`USER#<sub>` partition) and assert it belongs to the caller. Returns 403 on mismatch,
404 if not found.

### Multi-format parsers

New dependencies — declared in `packages/application/package.json` (server-side only;
not shipped to the browser):

| Format | Package | Notes |
|--------|---------|-------|
| PDF | `pdf-parse` (npm) | Text-layer extraction; no OCR. Output: plain text joined with newlines. |
| DOCX | `mammoth` (npm) | Converts to Markdown via `mammoth.convertToMarkdown`. |
| EPUB | `epub2` (npm) | Iterates spine items, extracts inner HTML, strips tags to plain text. |
| TXT / MD | passthrough | Read S3 bytes, decode UTF-8. |

Parser dispatch:

```typescript
// packages/core/src/sources/parse.ts
export async function parseDocument(
  format: SourceItem['originalFormat'],
  buffer: Buffer,
): Promise<string>  // returns normalised Markdown / plain text
```

All parsers run in Node.js (not Edge runtime); the extraction route and the async job
must both set `export const runtime = 'nodejs'`.

Post-processing after parse: normalise Unicode to NFC, collapse runs of blank lines to
a single blank line, prepend a `# <title>` heading.

### Inline vs. async extraction decision

At upload time the `POST /api/sources/upload-url` route:
1. Issues a presigned S3 PUT (TTL 5 min) — identical pattern to M4's
   `POST /api/notes/upload-url`, using `storageKeys.sourceOriginal`.
2. Writes a `SOURCE#` item with `status: 'uploading'`, `byteSize`, `originalFormat`,
   `title` (filename), `originalS3Key`.
3. Returns `{ presignedUrl, s3Key, sourceId }`.

After the client completes the PUT, it calls `POST /api/sources/[sourceId]/extract`.
That route:
- If `byteSize <= 2 MB AND pageCount <= 50` (pageCount for PDFs estimated from byte
  heuristic before real parse): parse inline, write `extractedTextS3Key`, set
  `status: 'ready'`, `wordCount`.
- Otherwise: flip `status → 'extracting'` (this triggers the DynamoDB Streams job).

### Async extraction job

`infra/jobs.ts`: add a DynamoDB Streams consumer Lambda that filters for `SOURCE#`
items where the new image has `status: 'extracting'`.

```
infra/jobs.ts additions:
- Link notesBucket (for S3 read/write of source files and extracted text).
- Link the Notes table for DynamoDB stream consumption.
- IAM: s3:GetObject on sources/users/*, s3:PutObject on sources/users/*,
       dynamodb:GetItem + UpdateItem on the Notes table.
```

Status machine:
```
uploading → extracting → ready
                       ↘ failed  (parser throws; errorMsg set)
```

On failure the job sets `status: 'failed'` and writes `error` message; the UI surfaces
a "Retry" action (calls `POST /api/sources/[sourceId]/extract` again).

### Large documents and M17 map-reduce

At generation time, after `resolveSourceText()` returns the full extracted text, the
existing `estimateTokens()` from M17 (`packages/core/src/study/tokenBudget.ts`)
determines the path:
- `<= DIRECT_LIMIT`: single-pass generation (same as a short note).
- `> DIRECT_LIMIT && <= HARD_CAP`: M17 map-reduce (`chunkNotes` + sequential map calls
  + dedup + reduce). The source text is treated as a single "note" for chunking purposes
  — `chunkNotes` receives `[{ noteId: sourceId, body: extractedText }]` and splits on
  paragraph boundaries.
- `> HARD_CAP`: `status: 'too_large'` on the STUDYSET item; UI surfaces an error.

No changes to `generate.ts`, `tokenBudget.ts`, `chunk.ts`, or `dedup.ts` — they are
source-agnostic by construction.

### Infra changes

- `infra/db.ts`: add `gsi7pk` and `gsi7sk` fields; add `SourcesByUser` global index.
- `infra/jobs.ts`: add extraction consumer Lambda; link `notesBucket`; add S3 +
  DynamoDB IAM.
- `infra/application.ts`: add `s3:GetObject` + `s3:PutObject` for
  `sources/users/*` prefix; add `dynamodb:UpdateItem` for `SOURCE#` items (already in
  scope if the IAM policy covers the Notes table).
- `infra/secrets.ts`: add `sst.Secret("MAX_SOURCE_FILE_BYTES")` (e.g. seed `52428800`
  = 50 MB) and `sst.Secret("MAX_SOURCES_PER_USER")` (e.g. seed `100`). Fail loud if
  unset.
- No new Cognito or Bedrock secrets beyond what M4/M13/M17 already require.

### MIME-type allowlist

```typescript
const ALLOWED_MIME_TYPES = [
  'application/pdf',
  'application/vnd.openxmlformats-officedocument.wordprocessingml.document',
  'application/epub+zip',
  'text/plain',
  'text/markdown',
] as const;
```

Enforced at `POST /api/sources/upload-url` (reject 400 if `contentType` not in list)
and re-validated at `POST /api/sources/[sourceId]/extract` (re-check S3 object's
Content-Type header).

## Risks / open questions

- **GSI7 provisioning time.** Adding `SourcesByUser` (GSI7) to the Notes table on a
  stage with existing data will backfill online — can take minutes on large tables. On
  `pr-<N>` this is instant (empty table). On production, plan for the backfill window
  and monitor CloudWatch metrics before routing traffic to the new sources routes.
- **`pdf-parse` memory on large PDFs.** `pdf-parse` loads the entire PDF into memory
  synchronously; a 300-page PDF at 10 MB may spike Lambda memory. Set the extraction
  job's Lambda memory to 1024 MB and monitor P99 duration + memory on `pr-<N>`. If
  memory is still a concern, switch to streaming page-by-page extraction.
- **EPUB spine order.** Some EPUBs have non-linear spine ordering or encrypted/DRM
  content. `epub2` will silently skip encrypted items; document this limitation and
  surface a warning if `wordCount < 100` after extraction (likely DRM-protected).
- **DOCX images and diagrams.** `mammoth` converts DOCX text to Markdown but drops
  embedded images (reasonable for M20). If diagrams contain key information, the
  generated study material will miss them. Document as a known limitation.
- **Backward-compat `sourceNoteIds` on generated items.** `STUDYSET#` items from a
  document source will have `sourceNoteIds: []` (empty or absent) if only document refs
  are supplied. Any code that reads `sourceNoteIds[0]` (pre-M17 pattern) must check for
  empty; add a guard in the M14 card-accept and M15 quiz routes and verify in integration
  tests.
- **Per-user storage cost.** Extracted Markdown files are stored in S3 indefinitely.
  Add a `DELETE /api/sources/[sourceId]` route (Phase 5 or follow-up) that removes both
  the original and extracted S3 objects when the user deletes a source. Without it,
  orphaned S3 objects accumulate.
- **MIME re-validation.** The presigned-URL pattern trusts the client to PUT the correct
  `Content-Type`. Re-check the S3 object's `ContentType` header in the extract route to
  prevent a client substituting a disallowed file type after receiving the presigned URL.
- **`epub2` package maintenance.** `epub2` is not actively maintained. Evaluate
  `epubjs` as an alternative if parsing reliability issues appear on real EPUB fixtures
  during Phase 2. Document the decision in the Phase 2 PR.

## Manual test plan

Test on the deployed `pr-<N>` stage (requires M13, M17 deployed; `SourcesByUser` GSI7
provisioned):

1. **Upload a PDF.** Navigate to `/sources`. Tap "Upload" or drag a PDF (≤ 5 MB, 1–10
   pages) onto the drop zone. Expected: a new row appears immediately with
   `status: uploading`, transitions to `extracting` or `ready` within 15 s; no error.

2. **Sources list — status polling.** While the PDF row shows `extracting`, leave the
   page open. Expected: the status chip updates to `ready` without a page reload (3 s
   poll); the "Generate study material" action becomes active.

3. **Multi-format: DOCX.** Upload a `.docx` file with a heading and two bullet points.
   Expected: extraction succeeds (`status: ready`); generate flashcards from it; assert
   the generated cards reference content from the DOCX (heading text visible in at least
   one card front).

4. **Multi-format: plain text.** Upload a `.txt` file (copy-paste a paragraph). Expected:
   `status: ready` within 5 s (inline extraction); generate a quiz; assert at least one
   question is drawn from the text content.

5. **Generate study material — flashcards.** On a `ready` PDF source, tap "Generate
   study material" → select "Flashcards". Expected: M13's type-picker sheet closes; the
   generation progress page appears; within 60 s the flashcard review page loads with
   cards derived from the PDF content.

6. **Generate study material — large document (map-reduce path).** Upload a PDF with
   ≥ 80 pages (or a large `.txt` file). Expected: if M17's confirm dialog is shown, it
   mentions "multi-pass processing"; after confirmation, generation completes and
   `STUDYSET#` item has `mapReduce: true` (visible in the DynamoDB console or via a dev
   log).

7. **File-size guardrail.** Attempt to upload a file > `MAX_SOURCE_FILE_BYTES` (e.g.
   60 MB if the cap is 50 MB). Expected: the upload route returns an error before the
   presigned URL is issued; the UI shows a clear error message ("File too large").

8. **MIME-type guardrail.** Attempt to upload an image file (`.jpg`). Expected: 400
   error returned before the presigned URL is issued; UI shows "File type not
   supported".

9. **Failed extraction — retry.** Simulate a parser failure (upload a zero-byte PDF).
   Expected: the source row shows `status: failed` with an error message; tapping
   "Retry" re-triggers extraction; if the file is genuinely unparseable, `failed` is
   shown again with a descriptive error.

10. **Backward compatibility — existing note generation.** Navigate to a note in the
    library and tap "Generate study material" (M13 flow). Expected: the existing
    single-note generation flow works exactly as before M20; no confirm dialog for
    single-note runs; `STUDYSET#` item has `sourceNoteIds` populated as before.
