# M16 · Assignments, summaries & study guides

> Size: L · Depends on: M13

## Goal

Extend the STUDYSET system introduced in M13 with four new generated material types:
**summaries**, **key-term glossaries**, **study guides**, and **assignments / practice
prompts**. Each is a `STUDYSET` item whose `type` field selects the per-type tool-use
schema and prompt when calling M13's `generate` wrapper. The app lists, generates, and
renders all four types from the same routes, job plumbing, and viewer shell M13 already
provides — M16 adds only the type-specific schemas, prompts, and a rendering layer for
each output shape.

## Implementation status & deviations (as built)

> ⚠️ This spec predates the M13 implementation and assumed an interface M13 did **not**
> ship. The text below records how M16.1 was actually built; treat the "Architecture &
> decisions" sections further down as the *original intent*, not the final design.

**M16.1 · Wave 1 — Generation Foundations — DONE** (#249, PR #545).

- **Conformed to the real M13 engine, not this spec.** M13 shipped a single
  `submit_study_material` tool whose JSON schema is selected per-type from
  `TOOL_SCHEMAS` in `packages/core/src/study/generate.ts` — *not* per-type named tools
  (`produce_summary`, …) or a `TOOL_FOR_TYPE` map. The job stores the raw JSON payload in
  S3 (no Markdown serialiser); the viewer renders the typed payload directly. M16.1 added
  the two genuinely-new types to that existing machinery.
- **`summary` and `assignment` already existed** in M13 with different schemas
  (`summary` = `{title, tldr, keyPoints, terms}` — already bundles a glossary;
  `assignment` = `{title, instructions, rubric}`). They were **left untouched**. M16.1.2
  (#255, "reshape assignment into open-ended prompts") was therefore **descoped** — the
  shipped `assignment` type already covers open-ended practice.
- **Two new types added:** `glossary` (`{terms:[{term,definition}]}`) and `study_guide`
  (`{title,sections:[{heading,keyPoints,body?}]}`) — added to `StudyMaterialType` /
  `MATERIAL_TYPES`, `TOOL_SCHEMAS`, `MAX_TOKENS_BY_TYPE` (2048 / 4096), `STUDY_TYPE_META`
  and the route `TYPE_LABELS`. They are intentionally **kept out of the generate picker
  (`STUDY_TYPE_ORDER`)** until M16.2 ships their viewer renderers, so M16.1 is a
  backend-only foundation.
- **Prompts are repo text files, not SST secrets.** System prompts are not secrets, and
  inlining all 7 prompts as Lambda env vars exceeded AWS's hard 4 KB env limit. The
  prompts now live as committed `prompts/*.txt` files, loaded into `process.env` at the
  generation Lambda's startup by `packages/application/jobs/study-prompts.ts` (bundled via
  `copyFiles` in `infra/jobs.ts`). `resolveAiConfig` still reads `process.env`, unchanged.
  These files are the **default-prompt fallback layer** that M19's admin-override UI will
  build on. The old `STUDY_*_PROMPT` `sst.Secret`s were removed.

**M16.2 · Wave 2 — Rendering UI + Self-check** — still open (#356, #262, #269): adds the
`glossary`/`study_guide` entries to `STUDY_TYPE_ORDER`, the viewer renderers (GlossaryView
`<dl>`, study-guide sections), the print button, and assignment self-check.

## In scope

- Four new `type` values on M13's STUDYSET model:
  `"summary" | "glossary" | "study_guide" | "assignment"`.
- Per-type tool-use schema + system prompt passed to M13's
  `packages/core/src/study/generate.ts` `generateStudySet` wrapper (Converse tool-use →
  typed JSON).
- Generated body stored in S3 alongside existing study-set types (S3 key pattern from
  M13 unchanged).
- Rendering UI for all four types:
  - summary, study\_guide, assignment → `renderMarkdown` from
    `packages/application/src/lib/markdown.ts`, styled with the `.md-body` container
    and `packages/application/src/styles/markdown.css`.
  - glossary → definition list (`<dl><dt><dd>`) built from the
    `{ term: string; definition: string }[]` array in the generated JSON.
- Print / export: a "Print" button per study-set view triggers `window.print()`; a
  `@media print` CSS block in the viewer hides the app chrome and renders only the
  study-set body. True PDF export (server-side rendered PDF) is out of scope.
- Optional self-check for assignment prompts: a per-prompt "Mark complete" checkbox
  whose checked state is persisted on the STUDYSET item (`completedPrompts: string[]`
  attribute, keyed by prompt index).
- Key builder additions in `packages/core/src/db/keys.ts` if M13 does not already
  expose studyset-level helpers for these types (add under the existing studyset block).
- Unit tests (mocked Bedrock) for all four tool-use schemas and their prompt strings.
- Dynalite integration test for the `completedPrompts` patch round-trip if M13 does not
  already cover partial attribute updates on STUDYSET items.

## Out of scope

- Auto-graded assignments or answer validation (that is M15's quiz domain; M16
  assignments are open-ended practice the user self-grades).
- True server-side PDF generation (e.g. Puppeteer, Playwright PDF mode, or a PDF
  lambda) — print-to-PDF via `window.print()` is the accepted UX for M16.
- New DynamoDB tables or GSIs (all four types reuse M13's `STUDYSET#<ulid>` item shape
  and existing indexes).
- Bulk generation of multiple study materials in a single job.
- Shared or group-visible study materials (all materials are private to the owning
  user, same as M13).
- Editing generated content inline after creation.
- Exporting to Anki, CSV, or Markdown file download.

## Architecture & decisions

### Type extension on M13's STUDYSET model

M13's `STUDYSET#<ulid>` item already carries a `type` field and a `status` machine
(`queued → generating → done | error`). The body is stored in S3 at a key derived from
the item's ULID (M13's pattern). M16 adds four `type` literals; all other item fields
(`noteId`, `userId`, `createdAt`, `updatedAt`, `status`, `s3Key`) are unchanged.

```
type StudySetType =
  | "flashcard"       // M13 — existing
  | "summary"         // M16
  | "glossary"        // M16
  | "study_guide"     // M16
  | "assignment";     // M16
```

No schema migration is required — DynamoDB stores `type` as a free-form string; the
worker and viewer already dispatch on it.

### Tool-use schemas (per type)

All four types are generated via `generateStudySet(noteMarkdown, type, opts)` in
`packages/core/src/study/generate.ts`. M13's wrapper calls `ConverseCommand` with a
`toolConfig` block; M16 adds four new tool definitions:

#### `summary` tool schema

```jsonc
{
  "name": "produce_summary",
  "description": "Produce a condensed outline of the note as structured Markdown.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "title": { "type": "string", "description": "One-line title for the summary." },
      "sections": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "heading": { "type": "string" },
            "body":    { "type": "string", "description": "Markdown body for this section." }
          },
          "required": ["heading", "body"]
        }
      }
    },
    "required": ["title", "sections"]
  }
}
```

Serialised body stored in S3: the worker calls
`sections.map(s => `## ${s.heading}\n\n${s.body}`).join('\n\n')` and writes that
Markdown string to S3. The viewer passes it to `renderMarkdown`.

#### `glossary` tool schema

```jsonc
{
  "name": "produce_glossary",
  "description": "Extract key terms and their definitions from the note.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "terms": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "term":       { "type": "string" },
            "definition": { "type": "string" }
          },
          "required": ["term", "definition"]
        },
        "minItems": 1
      }
    },
    "required": ["terms"]
  }
}
```

The `terms` array is stored as JSON in S3 (not Markdown). The viewer renders it as:

```html
<dl class="glossary-list">
  <dt class="glossary-term">subjuntivo</dt>
  <dd class="glossary-def">A verb mood that expresses doubt or desire…</dd>
  …
</dl>
```

CSS for `.glossary-list / .glossary-term / .glossary-def` lives alongside
`packages/application/src/styles/markdown.css` (add to the same file or a co-located
`glossary.css` imported by the viewer component).

#### `study_guide` tool schema

```jsonc
{
  "name": "produce_study_guide",
  "description": "Produce a structured, multi-section study guide with key points.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "title": { "type": "string" },
      "sections": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "heading":    { "type": "string" },
            "keyPoints":  { "type": "array", "items": { "type": "string" } },
            "body":       { "type": "string", "description": "Optional extended Markdown." }
          },
          "required": ["heading", "keyPoints"]
        }
      }
    },
    "required": ["title", "sections"]
  }
}
```

Serialised body: `## ${s.heading}\n\n${s.keyPoints.map(p => `- ${p}`).join('\n')}${s.body ? `\n\n${s.body}` : ''}` per section, joined with `\n\n`. Viewer uses `renderMarkdown`.

#### `assignment` tool schema

```jsonc
{
  "name": "produce_assignment",
  "description": "Generate open-ended practice prompts and problem sets derived from the note.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "title": { "type": "string" },
      "prompts": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "index":    { "type": "integer", "description": "0-based prompt index." },
            "type":     { "type": "string", "enum": ["essay", "problem", "reflection", "exercise"] },
            "question": { "type": "string" }
          },
          "required": ["index", "type", "question"]
        },
        "minItems": 1
      }
    },
    "required": ["title", "prompts"]
  }
}
```

Serialised body: Markdown with `### Prompt N` headings + prompt text. Viewer uses
`renderMarkdown` for the body and overlays a checkbox per prompt (see self-check below).

### Threading `type` through M13's generation route

M13's `POST /api/study/generate` already accepts `{ noteId, type }`. M16 requires no
new route — calling `POST /api/study/generate` with
`type: "summary" | "glossary" | "study_guide" | "assignment"` triggers the appropriate
tool schema inside `generateStudySet`. The `type` is stored on the STUDYSET DynamoDB
item (existing `type` attribute); the background job (`infra/jobs.ts`) reads it and
dispatches to the correct tool.

In `packages/core/src/study/generate.ts`, extend the tool-dispatch map:

```typescript
const TOOL_FOR_TYPE: Record<StudySetType, ToolDefinition> = {
  flashcard:   flashcardTool,   // M13 — existing
  summary:     summaryTool,     // M16
  glossary:    glossaryTool,    // M16
  study_guide: studyGuideTool,  // M16
  assignment:  assignmentTool,  // M16
};
```

The system prompt passed to Bedrock is also type-specific (a constant string per type,
defined alongside each tool, exported for unit tests).

### Self-check for assignment prompts

Assignment STUDYSET items carry an optional `completedPrompts` attribute — a `string[]`
of 0-based prompt indices (stored as strings for DynamoDB simplicity):

```
STUDYSET item additions (assignment type only):
  completedPrompts:  string[]   # e.g. ["0", "2"] — indices of completed prompts
```

`PATCH /api/study/[studySetId]/complete-prompt` (new, lightweight):
- Auth: `proxy.ts` middleware.
- Body: `{ promptIndex: number, completed: boolean }`.
- Adds or removes the index string from `completedPrompts` via a DynamoDB
  `UpdateExpression` (`list_append` / `REMOVE` element). Owner-checked (STUDYSET PK
  must match caller sub).
- Returns `{ completedPrompts: string[] }`.

Client: a `CheckboxItem` component per prompt; on change, calls the PATCH endpoint and
updates local state optimistically.

### Rendering UI

All four material types are rendered from a shared `StudySetViewer` component (or the
one M13 already provides extended with a `type`-aware body renderer). The type-switch
lives in a `StudySetBody` sub-component:

```
StudySetBody
  ├── type === "glossary"   → GlossaryView  (<dl> from JSON terms array)
  └── all others            → MarkdownView  (renderMarkdown from
                               packages/application/src/lib/markdown.ts,
                               output via dangerouslySetInnerHTML into .md-body div,
                               styled by packages/application/src/styles/markdown.css)
```

Assignment prompts render via `MarkdownView` for the body, then the `CheckboxItem`
overlay is positioned after each `### Prompt N` heading.

### Print / export

A "Print" button (ghost, `printer` icon from the DS icon set) calls `window.print()`.
A `@media print` block in the viewer's CSS (or a `print.css` imported by the viewer):

```css
@media print {
  /* hide shell chrome */
  nav, header, footer, .action-bar, .print-hidden { display: none !important; }
  /* full-width body */
  .study-set-viewer { width: 100%; padding: 0; }
}
```

No lambda, no server-side PDF generation. The test plan verifies the print dialog
opens and the preview shows only the study-set content.

### Infra changes

- No new DynamoDB tables or GSIs required.
- No new `sst.Secret` entries — the existing `BEDROCK_MODEL_ID` secret is reused.
- `infra/application.ts` already grants `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` for the inference profile; no permission changes needed.

## Risks / open questions

- **M13 generate.ts surface area unknown.** M16 is spec'd against the assumed M13 API
  (`generateStudySet(md, type, opts)`, `TOOL_FOR_TYPE` map). If M13 landed a different
  function signature or split tool definitions differently, the Phase 1 subagent must
  read M13's actual code before extending it — do NOT assume the interface.
- **Glossary JSON in S3 vs. Markdown.** Storing glossary body as raw JSON (not Markdown)
  is a deliberate exception to the "all bodies are Markdown" convention so the viewer
  can render a semantic `<dl>` rather than a faked definition list in Markdown. This
  requires the viewer to `JSON.parse` the S3 body for `type === "glossary"` and the job
  to skip Markdown serialisation for that type. The STUDYSET item should carry a
  `bodyFormat: "markdown" | "json"` attribute to make this branching explicit and
  self-documenting.
- **Bedrock output quality for assignments.** Open-ended prompts may be too generic or
  surface the source note too literally. The system prompt must emphasise higher-order
  thinking (analysis, synthesis, application) and explicitly forbid restating note
  content verbatim. Tune this iteratively after seeing real outputs on the `pr-<N>` stage.
- **Print CSS specificity.** The existing `markdown.css` may conflict with the
  `@media print` overrides. Test in Chrome, Safari, and Firefox print preview; if the
  app shell chrome bleeds through, escalate to `!important` selectors scoped to
  `.print-hidden` explicitly.
- **`window.print()` on mobile.** iOS Safari's share-sheet-based print experience is
  different from desktop. Verify the print flow on a real iOS device during the manual
  test plan; if the browser print dialog does not surface the study-set content clearly,
  note it as a known limitation for M16 and scope a "Download as PDF" server route for a
  future milestone.
- **`completedPrompts` index stability.** Prompt indices are stored as integers keyed to
  array position. If a study-set is regenerated (a new STUDYSET item is created for the
  same note), the old `completedPrompts` are discarded because the new item starts fresh.
  This is acceptable UX for M16; a future milestone could carry over completion state by
  matching prompt text.

## Manual test plan

Test on the deployed `pr-<N>` stage after `sst deploy`:

1. **Generate a summary.** Open a note with at least 200 words of content. From the
   study-materials panel, tap "Generate → Summary". Expected: a loading/generating state
   appears (M13's status machine); within 15 s the summary view opens; it shows `##`
   section headings and paragraph body text rendered via the `.md-body` styles.

2. **Generate a glossary.** On the same note, tap "Generate → Glossary". Expected:
   after generation, the view shows a styled `<dl>` — each key term in bold serif (`<dt>`)
   with its definition indented below (`<dd>`); no raw JSON visible; at least 3 terms
   extracted.

3. **Generate a study guide.** On the same note, tap "Generate → Study Guide". Expected:
   the view shows headed sections, each containing bullet-point key points rendered as
   `<ul><li>` via the `.md-body` styles.

4. **Generate an assignment.** Tap "Generate → Assignment". Expected: 4–8 numbered
   prompts appear under `### Prompt N (type)` headings; each prompt ends with an empty
   checkbox; prompt types include at least two of: essay, reflection, problem, exercise.
   No multiple-choice answers or answer keys present.

5. **Self-check — mark a prompt complete.** On the assignment view, check the checkbox
   next to Prompt 1. Expected: checkbox fills immediately (optimistic update); refreshing
   the page shows Prompt 1 still checked; the other prompts remain unchecked.

6. **Self-check — unmark a prompt.** Uncheck Prompt 1. Expected: checkbox clears
   immediately; after reload it is unchecked.

7. **Print — summary.** On the summary view, tap the "Print" button. Expected: the
   browser print dialog opens; the print preview shows only the summary content (no nav
   bar, no action bar, no DS shell chrome visible); headings and paragraphs readable.

8. **Print — glossary.** Trigger print on the glossary view. Expected: `<dl>` definition
   list visible in the print preview; app shell hidden.

9. **Glossary JSON not exposed.** On the glossary view, verify the raw S3 JSON body is
   never rendered as text; only the `<dt>` / `<dd>` pairs appear.

10. **Cross-type navigation.** From the note's study-materials list (M13's list view),
    confirm all four generated types appear with their correct type labels (Summary,
    Glossary, Study Guide, Assignment). Clicking each opens the correct renderer; the
    back button returns to the list without a full page reload.
