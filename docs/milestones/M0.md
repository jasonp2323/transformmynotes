# M0 · Monorepo & infra bootstrap

> Size: XL · Depends on: none

## Goal

Stand up the complete project skeleton so that every subsequent milestone has a working, CI-gated, continuously-deployable foundation to build on. This includes filling all `{{PLACEHOLDER}}` tokens across `CLAUDE.md` and `.claude/`, wiring the GitHub Actions workflows to the `master` branch, creating the npm workspaces monorepo (`packages/core`, `packages/application`, `packages/marketing`, `packages/scripts`), defining all SST v4 infra modules (`infra/secrets.ts`, `infra/router.ts`, `infra/auth.ts`, `infra/db.ts`, `infra/marketing.ts`, `infra/application.ts`, `infra/jobs.ts`), and shipping the offline test harnesses (dynalite integration + cognito-local E2E).

By the end of M0, a single `git push` to a feature branch opens a PR that: runs lint, typecheck, unit tests, integration tests (dynalite), and the marketing E2E suite fully offline — then deploys an ephemeral `pr-<N>` stage to AWS that serves a hello-world marketing page at the apex URL and a hello-world protected `/dashboard` page at `app.transformmynotes.com` behind real Cognito auth. The repo is ready for feature work with no further scaffolding debt.

## Architecture & decisions

### Data model (M0 baseline)

Single table: **`UserData`** (`infra/db.ts`)

| Key | Pattern | Purpose |
|---|---|---|
| PK | `USER#<cognitoSub>` | User partition |
| SK | `PROFILE` | User profile record |
| GSI | none at M0 | Added in later milestones |

`infra/db.ts` exports this table definition and links it to both `infra/application.ts` and `infra/jobs.ts`. Stream is `new-and-old-images` from day one so future jobs can subscribe without a table recreation.

Key builder in `packages/core/src/db/keys.ts`:
```ts
export const userDataKeys = {
  profile: (userId: string) => ({ pk: `USER#${userId}`, sk: 'PROFILE' }),
};
```

### API routes

- `GET /api/health` (application) — returns `{ ok: true, stage: process.env.SST_STAGE }`. Used by E2E smoke test and future uptime monitors.

### Infra changes

All SST infra is new at M0. Load order in `sst.config.ts`:
1. `infra/secrets.ts` — `sst.Secret` declarations (no defaults)
2. `infra/router.ts` — single CloudFront Router for production; ephemeral stages omit it
3. `infra/auth.ts` — Cognito user pool + app client per stage
4. `infra/db.ts` — `UserData` table
5. `infra/marketing.ts` — marketing Next.js, apex domain attachment
6. `infra/application.ts` — application Next.js, `app.` subdomain attachment, Cognito + DB links
7. `infra/jobs.ts` — scaffold only

Use `$app.stage === "production"` everywhere that gates custom domain attachment or the Hosted-UI domain — never hardcode `"master"` or a PR stage name.

### Test harnesses

**Dynalite integration** (`packages/core/test/`):
- `dynalite-global.ts` — `globalSetup` that starts dynalite on a random port, creates the `UserData` table with the exact same `AttributeDefinitions` / `KeySchema` / `StreamSpecification` as `infra/db.ts`, tears down after all tests.
- `integration-env.ts` — `setup` file that sets `AWS_ENDPOINT_URL_DYNAMODB=http://localhost:<port>`, `SST_RESOURCE_UserData_name=UserData`, and dummy AWS credentials so the production `client.ts` points at dynalite without modification.
- `user-data.integration.test.ts` — write a profile record via `ddb.put`, read it back via `ddb.get`, assert round-trip fidelity.

**cognito-local E2E** (`e2e/application/`):
- `globalSetup.ts` — starts dynalite (table creation), starts `cognito-local` on :9229, creates a test user pool + app client (`ALLOW_USER_PASSWORD_AUTH`), seeds a confirmed test user (`COGNITO_TEST_USERNAME` / `COGNITO_TEST_PASSWORD`), starts `next dev -p 3002` with all env vars pointed at local services, waits for port readiness.
- `auth.spec.ts` — calls `InitiateAuth` to mint tokens, injects as cookies, navigates to `/dashboard`, asserts greeting is visible, navigates away, asserts middleware redirects unauthenticated request to sign-in.

## Risks / open questions

- **AWS account / IAM role setup:** The OIDC trust policy for the GitHub Actions deploy role must be configured before the first CI deploy. This is a manual one-time step outside the code; document it clearly in the PR description.
- **Cloudflare DNS records for pr-<N> stages:** CLAUDE.md specifies grey-cloud (DNS-only) records so ACM can issue certs. This is a manual Cloudflare step per PR subdomain, or a wildcard if DNS provider supports it — clarify whether a `*.pr.transformmynotes.com` wildcard can be created and whether ACM can issue the cert for it.
- **SST Console secret seeding:** Both the `production` and fallback Console environments must have all secrets seeded before the first `sst deploy`. The `WEB_DOMAIN` secret in particular is read early; an unseeded secret will cause a hard build failure (by design — no silent fallback).
- **cognito-local compatibility:** The `cognito-local` npm package must support the `AdminSetUserPassword` + `AdminCreateUser` + `InitiateAuth USER_PASSWORD_AUTH` flow used by the E2E global setup. Validate against the version pinned in devDependencies before declaring the suite passing.
- **`packages/scripts/src/stamp.ts`:** The stamp helper resolves Project field IDs via the `gh` CLI at runtime. GitHub Project node IDs must be filled in CLAUDE.md (see placeholder table) before `npm run stamp` will work. This is a human setup step, not a CI gate.
- **Self-signup disabled:** `infra/auth.ts` must set `selfSignUpEnabled: false` on the Cognito user pool so that users cannot register directly. All access flows through invites or admin approval — this is a core product constraint. Verify this flag is correct in the SST Cognito resource API.

## Manual test plan

1. **Marketing page:** Open the `pr-<N>` marketing URL (surfaced by the CI "Surface deployment URLs" step). Verify the page loads, the title reads "TransformMyNotes", and a "Request access" link is present. Expected: no JS errors in console, no 404s.

3. **Health check:** `curl <app-pr-N-url>/api/health`. Expected: `{"ok":true,"stage":"pr-<N>"}` with HTTP 200.

4. **Cognito sign-in (Hosted UI):** On the login page, enter valid credentials for a user you created manually in the pr-<N> Cognito pool (or use the seeded E2E test user's credentials). Expected: successful sign-in, redirect to `/dashboard`, page renders "Welcome, {email}".

5. **Admin bootstrap:** Follow `docs/runbooks/admin-bootstrap.md` on the pr-<N> pool. Promote one user to the `admin` group. Sign out and sign back in as that user. Expected: sign-in succeeds; the JWT's `cognito:groups` claim includes `admin` (visible in browser devtools via `atob` on the ID token payload).

6. **CI gate integrity:** Verify that the deploy workflow run for the PR shows all offline gates (lint, typecheck, test:unit, test:integration, test:e2e) completed before the "Configure AWS credentials" step. Expected: if any offline gate fails, the deploy step never runs.
